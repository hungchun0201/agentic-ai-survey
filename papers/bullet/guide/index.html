A Beginner's Guide to Bullet

From zero GPU background to modeling LLM inference time — a code-and-paper-grounded walkthrough of how Bullet measures, predicts, and re-partitions streaming-multiprocessor, tensor-core, and memory-bandwidth resources to co-execute prefill and decode on one GPU.

0. How to Use This Guide

Bullet is a GPU-serving system for large language models that runs the prefill and decode phases of inference at the same time on one GPU, dividing the chip's compute units between them and adjusting that division as the workload shifts. This guide takes a reader with zero background in GPU architecture or CUDA and brings them to the point where they can reason about — and begin to model — how long LLM inference takes, with particular attention to the three quantities that govern latency: memory bandwidth, tensor-core throughput, and the allocation of streaming multiprocessors (SMs).

The problem Bullet attacks is a structural one, and the paper states it plainly at the outset.

Modern large language model (LLM) serving systems confront inefficient GPU utilization due to the fundamental mismatch between compute-intensive prefill phase and memory-bound decode phase.Abstract

That single sentence is the seed of the entire guide: prefill is hungry for arithmetic, decode is hungry for memory bandwidth, and a GPU forced to alternate between them wastes whichever resource the current phase does not need. Everything that follows — the roofline reasoning, the two-engine architecture, the SM masking — exists to repair that mismatch. This guide is grounded throughout in two primary sources: the published paper (arXiv:2504.19516) and the public source repository at /Users/linhung-chun/Project/BulletServe. We do not paraphrase from memory; every claim is tied back to one of those two.

1. The GPU, From the Ground Up

Before we can model how long an LLM takes to run on a GPU, we need a precise vocabulary for what a GPU actually is. This section builds that vocabulary one idea at a time: the unit of compute (the SM), how SMs are grouped into the partitioning unit Bullet uses (the TPC), the two kinds of arithmetic engine inside an SM (CUDA cores and Tensor Cores), the software model that maps work onto the hardware (grid, block, warp, thread), the memory hierarchy that determines whether a kernel is compute- or memory-bound, and finally the concurrency machinery (streams, concurrent kernel execution, and MPS) that lets Bullet run two phases of inference on one device at once. Every later section assumes these terms.

1.1 The streaming multiprocessor (SM): the unit of compute

A modern GPU is not one giant processor but a collection of many independent compute engines called streaming multiprocessors, or SMs. Each SM has its own arithmetic units, its own scratchpad memory, and its own scheduler for the threads it runs. A datacenter GPU has on the order of a hundred SMs, and the whole machine works by spreading a computation across all of them in parallel.

Modern GPUs employ a hierarchical architecture with hundreds of streaming multiprocessors (SMs), each containing general-purpose cores and specialized matrix units like Tensor Cores.§2.2.1, Execution Model and Theoretical Performance Bound
Background The exact SM count varies by GPU model and is the single most important number for capacity reasoning. The paper's three experimental servers fix these counts (Table 3): the Nvidia A100 has 108 SMs, the H100 has 132 SMs, and the H20 has 78 SMs. Because Bullet's whole idea is to give a fraction of the SMs to one task and the rest to another, knowing how many SMs a GPU has is the starting point for any allocation decision.

1.2 GPC, TPC, and the “1 TPC = 2 SMs” rule Bullet partitions by

SMs are not loose; the hardware organizes them into a two-level grouping. Several SMs form a Texture/Thread Processing Cluster (TPC), and several TPCs form a Graphics Processing Cluster (GPC). On the GPUs Bullet targets, a TPC contains exactly two SMs. This grouping matters for one practical reason: the low-level masking tool Bullet uses to fence off compute can only switch resources on and off at TPC granularity, never at single-SM granularity. So when Bullet “gives a task 54 TPCs”, it is really giving that task 108 SMs.

1.3 CUDA cores vs Tensor Cores: why “tensor-core utilization” is the headline metric

Inside each SM there are two distinct kinds of arithmetic engine. The general-purpose CUDA cores execute ordinary scalar and vector floating-point operations, one element at a time per lane. The Tensor Cores are specialized units that perform a small dense matrix-multiply-accumulate in a single instruction, and they deliver an order of magnitude more arithmetic throughput than the CUDA cores for that one operation. Because the overwhelming majority of an LLM's work is large matrix multiplications (GEMMs) inside the attention and feed-forward layers, those GEMMs run on the Tensor Cores. This is why “tensor-core utilization” is the compute metric that matters: it measures how busy the engine that does the real work actually is.

The reason this guide exists is precisely that GPUs are routinely under-utilized along this axis. Bullet's entire goal is to raise tensor-core and memory-bandwidth utilization by co-running work that, individually, leaves the device idle; the paper reports the size of that improvement directly.

1.4 The programming model: grid → block → warp → thread

The software side mirrors the hardware. A single GPU function is called a kernel. When you launch a kernel you launch a grid, which is divided into thread blocks (TBs, also written “blocks”); each block contains many threads that cooperate and can share fast on-chip memory. The hardware places whole blocks onto SMs to run, and several blocks can reside on one SM at once, sharing that SM's registers, shared memory, and thread slots.

GPU’s grid-block-thread programming model […] aligns with this architecture, where kernels are organized into grids of thread blocks (TBs) that each manage thousands of cooperating threads.§2.2.1, Execution Model and Theoretical Performance Bound

Background A warp is a group of 32 threads that the SM executes together in lock-step: they share one instruction stream and advance as a unit. Warps are the true unit the hardware schedules; a thread block is just a convenient bundle of warps. Keeping this in mind explains the next idea — when an SM has more warps than it can run at once, it processes them in successive batches called waves.

1.5 Warps, wavefronts, and a first look at wave quantization

An SM does not run all its resident warps simultaneously; it issues them in successive wavefronts. Likewise, the whole device runs a kernel in waves: it places one batch of thread blocks across the SMs, runs them, then places the next batch, until all blocks are done. As long as the number of blocks divides evenly across the SMs, every wave keeps the whole device busy.

The SM executes the warps (32-thread groups) in successive wavefronts to interleave different instructions and maximize hardware utilization.§2.2.1, Execution Model and Theoretical Performance Bound

The trouble begins when the blocks do not divide evenly. Then the final wave runs on only a fraction of the SMs while the rest sit idle, waiting for that tail to finish. The paper names this loss wave quantization and quantifies the wasted SM cycles exactly. It is a central reason a single kernel often cannot saturate a large GPU on its own, and it motivates Bullet's strategy of filling the idle SMs with a second task. We treat it in full in §3; here it is enough to recognize the shape of the problem.

1.6 The memory hierarchy: registers → shared memory → L2 → HBM

Compute is only half the story; data has to reach the arithmetic units, and the speed at which it does so depends on where the data lives. A GPU has a layered memory hierarchy, fastest and smallest at the top: per-thread registers, then per-SM shared memory (a small software-managed scratchpad), then a device-wide L2 cache, and finally the large but comparatively slow high-bandwidth memory (HBM), which holds the model weights and the KV cache. Each level down is larger and slower.

A kernel is memory-bound when its bottleneck is moving bytes out of HBM rather than arithmetic throughput — the decode phase, which streams the whole model and KV cache from HBM to emit one token, is the canonical case. This compute-vs-memory split is what the roofline model in §4 formalizes.

Background A kernel is memory-bound when its limiting factor is the rate at which bytes move out of HBM, not the rate at which the Tensor Cores can multiply. The decode phase of LLM inference is the classic example: it reads the entire model and KV cache to generate one token, doing very little arithmetic per byte, so it spends most of its time waiting on HBM bandwidth and leaves the Tensor Cores idle. The opposite case, compute-bound, is limited by arithmetic throughput. Knowing which side a kernel falls on is the heart of inference-time modeling, and it is exactly what the roofline model in §4 formalizes.

How a GEMM flows through the hierarchy — and why that makes it compute-bound

A matrix multiply $C = A\times B$ does not stream the matrices through once; it tiles them so each value loaded from HBM is reused many times on-chip. Each thread block claims one output tile of $C$ (say 128×128) and loops over the shared $K$ dimension. Each iteration loads a small strip of $A$ and of $B$ from HBM — through L2 — into shared memory; every thread then reads those strips from shared memory into registers, multiplies them on the Tensor Cores, and accumulates into its own small piece of $C$ that stays in registers the whole time. Only after the entire $K$ sum is finished is the $C$ tile written back to HBM — once.

The reuse is the whole point. A strip of $A$ sitting in shared memory is read by every column of the output tile, and a strip of $B$ by every row — so one HBM load feeds on the order of a hundred multiply-adds. For a 4096-cubed GEMM that is roughly a thousand FLOPs per byte fetched from HBM. That high arithmetic intensity is why the kernel sits far to the right of the roofline ridge: it is compute-bound, and (as the previous box showed) demands only about 156 GB/s of HBM even at full Tensor-Core throughput. The on-chip levels exist precisely to hold these hot tiles so the kernel does not keep returning to slow HBM.

Decode is the opposite, and the contrast makes the idea click. Generating one token (batch 1) is a matrix-by-vector product: each weight is read from HBM and used in exactly one multiply-add against the single activation vector, then discarded. There is nothing to reuse, so shared memory and registers cannot save any HBM traffic — the kernel simply streams the entire model (≈16 GB) out of HBM for every token. Arithmetic intensity ≈ 1 FLOP/byte: memory-bound. Batching many tokens together restores the reuse (each weight now multiplies many tokens at once), which raises arithmetic intensity — and is exactly why decode is run in large batches.

Figure 1.4. A tiny GEMM, C = A×B. One output cell C[i,j] is the dot product of row i of A and column j of B. The reuse is the point: that same row i of A serves every cell in C's row i (the faint orange band), and column j of B serves every cell in C's column j (the faint blue band). So each value, once loaded from HBM into shared memory, is reused N times (4 here; ~128 in a real 128×128 tile) before it is dropped — which is why a GEMM is compute-bound. The chips trace one value's path: HBM → shared memory (the strip, reused by the whole thread block) → registers (where the C accumulator lives) → Tensor Core. Decode is a matrix×vector (a single C row), so there is no reuse and it stays memory-bound.

1.7 Kernels, CUDA streams, and concurrent kernel execution (CKE)

When a program launches a kernel, the kernel does not run immediately; it is enqueued into an ordered queue called a stream. The hardware scheduler pulls kernels off these streams and dispatches them onto the SMs. Critically, kernels enqueued on different streams have no ordering constraint between them, so the scheduler may run them at the same time whenever the device has spare resources. This simultaneous execution of independent kernels is called concurrent kernel execution (CKE), and it is the precise hardware lever Bullet pulls: it places prefill work on one stream and decode work on another so the two phases overlap on the same GPU.

Upon kernel launch, it enters an asynchronous task queue (termed stream in CUDA) for scheduling. The hardware scheduler retrieves kernels from these queues and dispatches them across SMs, enabling the concurrent kernel execution (CKE) from different streams when required resources are satisfied.§2.2.1, Execution Model and Theoretical Performance Bound

CKE is a capability, not a guarantee. The hardware will overlap streams “when required resources are satisfied”, but it gives the programmer no deterministic control over how the SMs are split between concurrent kernels. In practice the device may starve one stream or refuse to overlap at all unless resources are provisioned carefully. The paper states this limitation plainly, and it is the gap Bullet has to close with explicit SM partitioning (covered in §8).

However, current GPUs lack deterministic concurrent scheduling controls […] forcing users to carefully provision resources for kernels to achieve reliable overlap.§2.2.3, on the lack of deterministic CKE control

1.8 MPS, Green Contexts, and why Bullet needs both a shared context and explicit masking

Bullet runs its prefill engine and its decode engine as two separate processes. By default, kernels from two different processes do not co-run on one GPU — each process gets the device in turn. Nvidia's Multi-Process Service (MPS) removes that barrier: it lets several processes funnel their kernels into one shared GPU context so their kernels can actually execute concurrently. MPS is therefore a hard prerequisite for Bullet, and the artifact-evaluation script starts it before launching the server.

While modern GPUs provide compute resource partitioning through Nvidia’s multi-process service (MPS), precise kernel management is still required to ensure effective resource sharing while meeting SLO requirements.§2.2.3, on MPS being insufficient alone
Background <strong>What is a CUDA Green Context?</strong> Every process that uses a GPU is given a CUDA context — the GPU-side state (its address space, streams, and memory pools) through which it launches kernels — and by default a context may dispatch work to every SM. A Green Context (added in CUDA 12.4) is a lightweight context derived from that parent but bound to a chosen subset of SMs: you split the device's SMs into groups and create a green context for a group, after which any kernel launched through it runs only on that group's SMs. It is therefore NVIDIA's official, supported API for partitioning SMs inside a single process — the sanctioned alternative to the undocumented stream-mask trick that libsmctrl uses (§8). The catch is cost: each green context carries its own context state and memory pools, so keeping several partitions resident already runs to hundreds of megabytes, and spinning up new ones is not cheap enough to redo on every scheduling step. That is exactly why Bullet, whose split changes many times per second, declines Green Contexts and reaches for libsmctrl instead.

MPS can be paired with CUDA Green Contexts to partition SMs between processes, but that mechanism is expensive at the granularity Bullet wants: the paper reports that Green Contexts cost over 700 MB of memory for only four static partition policies, which is impractical when the split must change many times per second. Bullet therefore avoids Green Contexts and instead uses the lightweight libsmctrl masking library to fence streams to specific TPC ranges with negligible overhead. We cover that mechanism in detail in §8; for now the point is that MPS provides the shared context and libsmctrl provides the cheap, fine-grained partition that CUDA does not give natively.

While MPS with CUDA Green Context supports SM partitioning, its memory overhead exceeds 700MB for only 4 static policies in LLM serving, rendering it impractical for Bullet’s fine-grained control.§3.4, on Green Context overhead

On the axes that decide serving performance — granularity, reconfiguration cost, memory, and the ability to move the split every step — libsmctrl is not marginally but decisively better, which is why Bullet uses it. Green Context's advantage is of a different kind: it is an official, version-stable API. To see why these two pull in opposite directions, look at how each one actually enforces a partition.

Green Context — through the driver

The CUDA driver models the device's SMs as a partitionable resource. cuDevSmResourceSplitByCount splits that resource into groups and cuGreenCtxCreate (CUDA 12.4) gives a green context ownership of one group; the driver's own work-distributor then refuses to place that context's thread blocks outside its group. Enforcement lives in the driver's documented path, and the driver allocates real per-context state — command buffers, memory pools, scheduling structures — to back each partition. That state is what costs the memory and makes creation a heavyweight call, but it is also what keeps the mechanism working across CUDA and driver versions.

libsmctrl — straight at the hardware knob

Every kernel launch writes a hardware descriptor (the TMD / QMD) that the driver uploads to the GPU, and that descriptor carries an undocumented per-kernel TPC-enable bitmask. libsmctrl intercepts the launch — through a callback on the driver's private pre-upload hook, or by writing into the CUDA stream's internal struct at a hardcoded byte offset — and stamps that bitmask just before upload, so the hardware itself confines the kernel's blocks to the chosen TPCs (the exact code is in §8). Nothing is allocated: it is a few bits in a descriptor that was being written anyway. That is why it costs no memory, takes microseconds, works per-stream at TPC granularity, and can change every step — and equally why it is pinned to the precise CUDA / driver versions whose internal offsets it has hardcoded.

The single move — reaching past the driver's abstraction to stamp the raw hardware descriptor — is what makes libsmctrl both faster and more fragile than the official API. Speed and fragility are two faces of the same shortcut. The table below tallies the consequences.

Bottom line So this is not a close call on capability: on every axis that affects serving performance — granularity, overhead, memory, and per-step dynamism — libsmctrl wins decisively. Green Context's only edge is robustness: it is the supported API and it keeps working when you upgrade CUDA. Those are different currencies. For a research prototype chasing the paper's throughput and goodput numbers, libsmctrl's performance win is overwhelming and the trade is clearly worth taking; the cost it pays is purely operational fragility. And that cost is real, not theoretical: libsmctrl's struct-offset trick stops working on CUDA 13, which is exactly what prevented the full SM-partitioned system from running in our reproduction (see §8 and the reproduction report). A production system that must survive driver upgrades might weigh the two differently; a paper proving a performance ceiling reasonably does not.

2. The Two Phases of LLM Inference

Before we can model how long an LLM takes to answer a prompt, we have to understand what the GPU is actually computing. Every modern LLM is built from a stack of identical Transformer blocks, and serving a request runs those blocks in two structurally different ways: a prefill pass over the prompt, then a long sequence of one-token-at-a-time decode steps. These two phases stress completely different parts of the hardware, and that asymmetry is the entire opportunity Bullet is built to exploit.

2.1 The Transformer block: four components, mostly GEMM

A Transformer block contains four core components. The QKV-projection turns each token's hidden vector into query, key and value matrices; self-attention lets every token attend to the keys and values of the tokens before it; the output projection (O-proj) mixes the attention result back into the hidden dimension; and the MLP (a two-layer feed-forward network) applies a per-token nonlinear transform. Three of these four are plain matrix multiplications; only self-attention is a special operator.

Recent LLMs […] are mainly built by stacking Transformer blocks […], with each containing four core components: QKV-projection layer, self-attention computation, Output-projection layer and multi-layer perception (MLP).§2.1, Background — LLM Inference Workflow

The reason this decomposition matters for performance is that almost everything in the block is a general matrix multiplication (GEMM). The projections and the MLP are GEMMs; only attention departs from the pure-GEMM pattern, and even it is dominated by matrix products internally. If you can model the cost of a GEMM and the cost of attention, you can model the cost of the whole network.

These components are primarily implemented through general matrix multiplications (GEMMs), with element-wise operations interspersed between layers.§2.1, Background — LLM Inference Workflow
Background A GEMM (general matrix multiplication) computes $C = A \times B$ for two dense matrices. GPUs are designed to make this extremely fast: their Tensor Cores perform many multiply-accumulate operations per clock, so a large matrix-times-matrix product reuses each loaded value across many arithmetic operations. That high ratio of compute to memory traffic is exactly what keeps the Tensor Cores busy. GEMMs dominate LLM cost simply because the model is mostly weight matrices: every token's hidden vector is multiplied by every weight matrix in every layer, and stacking dozens of layers makes those multiplications the bulk of the work.

2.2 Prefill: process the whole prompt at once

When a request arrives, the server first runs the prefill phase. It feeds the entire prompt through the network in a single parallel forward pass and emits the first output token. Because all prompt tokens are processed together, the projections and MLP become large matrix-by-matrix GEMMs — many tokens wide — which keeps the Tensor Cores well fed. The latency the user perceives here, from sending the prompt to seeing the first token, is the time-to-first-token (TTFT).

During the initial prefill phase, the system processes all input tokens in parallel to generate the first output token, with the latency measured as time-to-first-token (TTFT).§2.1, Background — LLM Inference Workflow

Prefill does one more thing that the decode phase will depend on: as it runs full attention across the prompt, it builds the KV cache, storing the key and value vectors of every prompt token so they never have to be recomputed.

This compute-intensive stage performs full attention computations across the entire sequence while building the KV cache to store intermediate key-value states.§2.1, Background — LLM Inference Workflow

2.3 Decode: one token per step

Once the first token exists, the server switches to the decode phase, which generates the rest of the answer one token at a time. Each step feeds in only the single most recent token, runs it through every layer, and produces exactly one new token; the step then repeats. Because only one token moves through the network per step, the projections and MLP degrade from matrix-by-matrix products into vector-by-matrix products — there is very little arithmetic to do. The average latency of one such step is the time-per-output-token (TPOT).

Subsequently, the decode phase generates tokens sequentially, with each iteration consuming only the most recent output token to produce the next.§2.1, Background — LLM Inference Workflow

What makes decode slow is not arithmetic but memory traffic. Every step must read the full weight matrices and the entire KV cache out of high-bandwidth memory (HBM) just to advance a single token, so the step time is governed by how fast data can be moved, not by how fast it can be multiplied. The paper states this directly:

Unlike prefill, this memory-bound phase primarily retrieves data from the KV cache and performs relatively lightweight computations for the current token's transformations.§2.1, Background — LLM Inference Workflow
Background The KV cache stores the key and value vectors produced for every token the model has already processed. Self-attention needs, at each new step, the keys and values of all earlier tokens; recomputing them every step would be quadratic and wasteful, so the system computes each token's key and value once and keeps them. The cache therefore grows linearly with the context: a longer conversation means more stored key-value pairs, and decode must read all of them on every single step. This is why a long context makes decode both slower and more memory-hungry, and it is the data structure that ties the two phases together — prefill writes the cache, decode reads it.

2.4 Why prefill is compute-bound and decode is memory-bound

The two phases sit at opposite ends of what hardware engineers call arithmetic intensity — the number of floating-point operations performed per byte of data read from memory. Prefill multiplies a large matrix (many tokens) by each weight matrix, so each loaded weight is reused across all the tokens in the batch: high FLOPs per byte, so the Tensor Cores are the bottleneck. Decode multiplies a single vector (one token) by each weight matrix, reusing each loaded weight only once: low FLOPs per byte, so memory bandwidth is the bottleneck and the arithmetic units sit largely idle. This is the central asymmetry Bullet exploits, and §3 develops it formally with the roofline model.

3. Roofline, Arithmetic Intensity & Wave Quantization

The previous section established that prefill and decode stress different parts of the GPU. To turn that qualitative asymmetry into a model of inference time, we need a small but precise toolkit: the roofline model, the notion of arithmetic intensity, and a correction term called wave quantization. These three ideas, together with the SM count, are exactly what is required to predict how long one LLM step takes and how that time changes when the work is given fewer streaming multiprocessors. The SM-scaling roofline model that Bullet introduces in §6 is a direct generalization of the classic roofline, so understanding the classic version first makes the later one almost mechanical.

3.1 The classic roofline model

The roofline model captures a simple truth about hardware: a kernel cannot run faster than two physical ceilings allow. The first ceiling is peak compute throughput $C_{peak}$, measured in FLOP/s — the maximum rate at which the arithmetic units (including Tensor Cores) can do floating-point work. The second ceiling is peak memory bandwidth $D_{peak}$, measured in bytes/s — the maximum rate at which data can be moved between high-bandwidth memory and the on-chip units. Whether a given kernel is limited by the first or the second depends on how much arithmetic it performs per byte it moves.

Background Arithmetic intensity (AI) is the ratio of useful floating-point operations to bytes transferred from memory: AI = FLOPs / bytes moved, with units of FLOP/byte. It is a property of the kernel and its inputs, not of the hardware. A kernel that reads a large weight matrix only to multiply it by a single vector moves many bytes per FLOP, so its AI is low; a kernel that multiplies two large matrices reuses each loaded byte many times, so its AI is high. The ridge point is the arithmetic intensity at which the two ceilings meet, namely AI* = C_peak/D_peak. To its left a kernel is memory-bound (limited by bandwidth); to its right it is compute-bound (limited by the arithmetic units).

Putting the two ceilings together gives the attainable performance of a kernel as the smaller of the compute ceiling and the bandwidth-scaled intensity:

$$\text{attainable FLOP/s} = \min\big(C_{peak},\ D_{peak}\cdot \text{AI}\big)$$

Once the attainable rate is known, the latency of the kernel follows directly from the amount of work it must perform:

$$T = \frac{\text{FLOPs}}{\text{attainable FLOP/s}} = \frac{\text{FLOPs}}{\min\big(C_{peak},\ D_{peak}\cdot \text{AI}\big)}$$
Careful: FLOPs vs FLOP/s These look almost identical but are not the same thing. FLOPs (lower-case s, the plural of FLOP) is a count of floating-point operations — a quantity of work, e.g. “prefilling this prompt takes about 33 TFLOPs”. FLOP/s (equivalently written FLOPS, “per second”) is a rate — operations completed per second, i.e. a speed, e.g. “the A100 peaks at about 312 TFLOP/s”. They relate the way distance and speed do: $\text{time} = \text{FLOPs} \,/\, (\text{FLOP/s})$ — which is exactly the latency equation above, a count of work divided by a rate yielding seconds. And mind the third quantity in play: arithmetic intensity is FLOP per byte, not per second. So in the figure below the y-axis “Perf. (TFLOP/s)” is a rate, while the x-axis “Arithmetic Intensity (FLOP/Byte)” is work-per-byte.

Does >30 SMs make compute-bound work memory-bound? No — and here is why

First, where the bandwidth ceiling comes from. HBM bandwidth is a fixed property of the memory system, not of the SMs: it equals the bus width times the data rate, summed over the memory stacks. The A100-80GB wires up five HBM2e stacks, each with a 1024-bit interface (5120 bits total) running near 3.2 Gb/s per pin, giving 5120 × 3.2 Gb/s ÷ 8 ≈ 2.0 TB/s. That is the width of the pipe, soldered onto the package. The SMs are merely the consumers that issue load/store requests; one SM can drive only so much traffic (roughly 2.0 TB/s ÷ 30 ≈ 67 GB/s), so it takes about $N_d\approx30$ of them, all doing pure memory work, to generate enough requests to keep that fixed pipe full. The other 78 add demand but no extra delivered bandwidth.

But — and this is the crucial point — that does not mean any kernel becomes memory-bound past 30 SMs. Compute-bound versus memory-bound is set by arithmetic intensity, not by SM count. The figure was measured with a memory-copy probe whose intensity is essentially zero, so every SM's work is pure traffic. A genuinely compute-bound kernel reuses each loaded byte thousands of times, so it generates very little traffic even at full compute. Make it concrete: a prefill GEMM at $C_{peak}\approx312$ TFLOP/s and arithmetic intensity ≈ 2000 FLOP/byte demands only $312\text{ TFLOP/s} \div 2000 \approx 156$ GB/s of HBM — under 8% of the 2.0 TB/s ceiling, even running on all 108 SMs. It is nowhere near memory-bound, and adding SMs simply makes it faster (more Tensor Cores), never memory-bound.

The two facts together are exactly Bullet's thesis. Bandwidth is a shared, fixed resource that ~30 memory-bound SMs already exhaust; compute is a per-SM resource that scales with SM count. They are independent and complementary, so the right thing to do is run a bandwidth-hungry, SM-frugal kernel next to a compute-hungry, bandwidth-frugal one: decode takes the bandwidth on ~30 SMs, prefill takes the compute on the other ~78, and because prefill only needs ~156 GB/s they barely contend for HBM. That is why co-locating them raises both Tensor-Core and memory-bandwidth utilization at once (§6, §11).

The model also makes the GPU programming model concrete. Modern GPUs are built from many streaming multiprocessors, and a kernel is launched as a grid of thread blocks that the hardware scheduler spreads across those SMs.

Modern GPUs employ a hierarchical architecture with hundreds of streaming multiprocessors (SMs), each containing general-purpose cores and specialized matrix units like Tensor Cores.§2.2.1, Execution Model and Theoretical Performance Bound

3.2 Mapping the roofline onto LLM inference

The roofline turns §2's asymmetry into a quantitative statement. Prefill processes every input token in parallel through large matrix multiplications, so each loaded weight byte is reused across the whole sequence; its arithmetic intensity is high and it sits to the right of the ridge, compute-bound. Decode advances one token per step, so it streams the KV cache and weights while doing little arithmetic per byte; its arithmetic intensity is low and it sits to the left of the ridge, memory-bound. This is precisely why a single batching strategy cannot serve both well: one phase is starved for FLOP/s and the other for bytes/s.

Unlike prefill, this memory-bound phase primarily retrieves data from the KV cache and performs relatively lightweight computations for the current token's transformations.§2.1, LLM Computational Workflow

The classic roofline assumes the kernel has the whole GPU. Bullet's central modeling move, examined in detail under §6 (the SM-scaling roofline model), is to let both ceilings become functions of the number of SMs given to a kernel. Compute scales linearly with the SM count, while bandwidth scales only up to an inflection point, beyond which it saturates. The classic roofline is therefore the special case in which every SM is available; the SRM is the general case that Bullet needs because prefill and decode are made to share the machine by partitioning its SMs.

3.3 Wave quantization — the second source of waste

The roofline gives an idealized lower bound on latency, but real kernels rarely reach it, and one structural reason is wave quantization. A kernel is launched as a fixed number of thread blocks; the hardware places several of them on each SM and runs them in successive rounds called waves. When the block count does not divide evenly across the SMs, the final wave is partial: some SMs are working while the rest sit idle, waiting for the stragglers to finish before the kernel can return.

However, if the number of TBs is not evenly divisible by the number of SMs, a workload imbalance situation called wave quantization […] occurs. Some SMs finish early and remain idle while waiting for others to complete the tail wave.§2.2.1, Execution Model and Theoretical Performance Bound

The paper formalizes this precisely. For a kernel with $g$ thread blocks, $N$ SMs, and $b$ thread blocks resident per SM, the number of waves required is

$$w = \left\lceil \frac{g}{b\,N} \right\rceil$$

In the tail (final) wave only some SMs receive a block, so the number that stay busy is

$$tail = \left\lceil \frac{g}{b} - N\,(w-1) \right\rceil$$

and the fraction of SM cycles wasted across the whole kernel is the idle SMs in the tail wave divided by all SM-cycles spent:

$$idle = \frac{N - tail}{N\,w}$$
Where do $g$, $b$, and the tile size actually come from?

All three trace back to one design choice, the tile size. A kernel splits its output into tiles and gives one tile to each thread block. The library author (cuBLAS / CUTLASS, usually auto-tuned) picks the tile to balance reuse against occupancy: a larger tile reuses each loaded value more often (higher arithmetic intensity) but costs more registers and shared memory per block and yields fewer blocks; a smaller tile makes more, lighter blocks that spread across the SMs more evenly. It is also bounded by hardware — the tile must fit in a block's register and shared-memory budget, and its shape is aligned to the Tensor Core's native matrix-multiply size. Common GEMM tiles are 64×64, 128×128, 128×256.

<strong>$g$ (the number of thread blocks)</strong> then follows mechanically — it is just the number of tiles. For a GEMM whose output $C$ is $M\times N$ with a $T_m\times T_n$ tile, $g = \lceil M/T_m\rceil\times\lceil N/T_n\rceil$. A 4096×4096 output tiled 128×128 gives $g = 32\times32 = 1024$ thread blocks.

<strong>$b$ (thread blocks per SM)</strong> is usually greater than one — that is the normal, desired case. An SM hosts as many blocks at once as its fixed budget allows: on the A100, 65536 registers, up to ~164 KB of shared memory, 2048 thread slots, and a hard cap of 32 blocks. $b$ is the smallest of (budget ÷ per-block use) across those resources. A light block lets many co-reside ($b$ large = high occupancy, which is exactly what hides memory latency by keeping many warps in flight); a register- or shared-memory-heavy block lets only one or two ($b$ small). So $b$ reflects the kernel's resource footprint, and CUDA's occupancy API reports it.

Now the waves are mechanical. On $N=108$ SMs with $b=2$, one wave runs $bN=216$ blocks, so the 1024-block GEMM takes $\lceil 1024/216\rceil=5$ waves and its tail wave puts 160 blocks on 80 SMs (28 idle) — mild waste. But shrink the work, as chunked prefill does: a 256-token prefill chunk makes $C$ only $256\times4096$, i.e. $g = 2\times32 = 64$ blocks — fewer than the 216 a single wave can hold. So just 64 blocks run, 32 SMs busy and 76 idle, and the GPU is two-thirds empty in that one wave. That is precisely why small chunks suffer severe wave quantization (§4): there are simply too few tiles to fill the SMs.

Background Why does the divisibility almost never work out? GPU kernels are usually written with grid sizes that are powers of two, because they are sized to match data dimensions (sequence lengths, hidden sizes, head counts) that are themselves powers of two. GPUs, however, ship with SM counts that are deliberately not powers of two. The repo records the per-GPU partition unit as TPCs (texture processing clusters), and on these architectures each TPC contains two SMs, so the totals are 54×2=108 SMs on the A100 and 66×2=132 on the H100. A power-of-two block grid therefore almost never lands on a multiple of 108 or 132, and the tail wave underfills the machine.

The damage from wave quantization is not uniform. A very large GEMM launches so many blocks that the partial tail wave is a negligible fraction of the total, so the idle ratio is tiny. 3.5 The modeling lesson

Pulling the pieces together yields the recipe for predicting an LLM step's time. The roofline ceiling sets the idealized latency from FLOPs, arithmetic intensity, and the two peak rates. The wave-quantization term corrects that ideal upward, by an amount that depends on the grid size, the block-per-SM count, and the SM count N. And the SM count is not a fixed constant in a spatially shared server: it is the quantity Bullet allocates. To predict one step you must combine all three — the ceiling, the wave-quantization correction, and the number of SMs — which is exactly the role of the SM-scaling roofline model that §6 builds on the foundation laid here.

Takeaway Inference time is bounded below by the roofline (min(C_peak, D_peak·AI)) and pushed above it by wave quantization (idle = (N − tail)/(Nw)). Prefill is compute-bound, decode memory-bound, and small or chunked kernels suffer the most quantization waste. The SM count N ties both effects together — making it the lever Bullet pulls in §6.

4. Why Hybrid Batching Wastes the GPU

Bullet is, before anything else, a reaction to a specific habit of modern serving systems: cramming prefill and decode into one lockstep batch and tuning a single knob to keep latency tolerable. This section explains that habit from scratch, shows precisely where it throws compute away, and then walks through the two obvious alternatives — physically separating the phases, or letting them share a GPU through coarse static quotas — and why the paper rejects both. The throughline is simple: every existing dial moves the waste somewhere else; none of them removes it.

Figure 1 (from paper): Conventional serving (a) prioritises prefill and monopolises the GPU; chunked prefill (b) interleaves a slice of one prompt with decode tokens under a fixed token budget; the ideal (c) would keep both phases progressing while saturating the device. This section is about the gap between (b) and (c).

4.1 Chunked prefill, explained for a beginner

A serving engine receives two very different kinds of work at once. A new request must first be prefilled: its whole prompt is pushed through the model in a single compute-heavy pass to populate the key–value (KV) cache. Already-running requests must be decoded: each produces one more token per step, which is cheap in compute but reads the entire model and KV cache from memory. Chunked prefill is the production-standard way to run both on the same GPU at the same time.

In practice, chunked prefill (Agrawal et al., 2023) (Figure 1b) has been pervasively adopted in production systems (Kwon et al., 2023; Zheng et al., 2023; NVIDIA, 2023; Team, 2025).§1, Introduction
This method leverages a fixed token budget to combine prefill and decode requests into hybrid batches, with longer sequences being partitioned into chunks to fit within capacity.§1, Introduction
Background A hybrid batch is one GPU run that mixes work from different requests. A token budget (the chunk size $cs$) is the fixed number of tokens that single run may process. The scheduler first fills the budget with the $ds$ tokens needed by all active decode requests, then spends whatever is left on a slice of one new prompt. Because the prompt may be far longer than the leftover room, it is cut into chunks and fed in over several consecutive runs — that is the chunked in chunked prefill. Crucially, the whole hybrid batch executes in lockstep on the full GPU: prefill and decode advance together, neither can run ahead, and the chunk size is the only lever the operator gets.
As shown in Figure 4, chunked prefill (Agrawal et al., 2023) achieves low TPOT by leveraging a fixed token budget to concatenate the prefill and decode tokens into a hybrid batch, executing in a lockstep fashion (❷).§2.3.1, Chunked Prefill Workflow

The arithmetic is unforgiving. With a chunk size $cs$ and $ds$ decode tokens reserved per run, a prompt of length $sl$ leaves $cs - ds$ tokens of room per chunk, so finishing one prefill takes

$$ N = \left\lceil \frac{sl}{cs - ds} \right\rceil \quad\text{iterations.} $$

The damage is not in the $N$ passes themselves but in what each pass must re-read. Attention over a new chunk needs the keys and values of every earlier chunk, so chunk 2 reloads chunk 1, chunk 3 reloads chunks 1–2, and so on. Summed across the sequence this is a triangular cost.

$$ \sum_{i=1}^{N} i \;=\; \frac{N\,(N+1)}{2} \quad\text{KV-cache reloads.} $$
This forces N⋅(N+1)/2 times KV cache reloads as each new chunk must reprocess previous chunks’ cached states.§2.3.1, Chunked Prefill Workflow

4.2 The biased throughput–latency trade-off

Because prefill and decode are welded together in lockstep, the chunk size becomes a single dial that trades one metric for another. Shrink it and each run carries fewer prefill tokens, so the decode tokens riding alongside come back sooner — lower TPOT (time per output token) — but the prompt now needs more chunks, inflating TTFT (time to first token) and dragging down throughput. Enlarge it and the opposite happens. The dial never finds a setting that is good on both axes; it merely chooses which axis to sacrifice.

Due to the lock-step execution of the hybrid batch, a smaller chunk size effectively decreases TPOT at the cost of increased TTFT and degraded system throughput (Agrawal et al., 2023), while larger chunks exhibit the opposite effect.§2.3.1, Chunked Prefill Workflow
Small chunk Decode tokens return quickly, so TPOT is low — but $N$ grows, TTFT rises, the GPU is left below its saturating workload, and throughput falls.
Large chunk Fewer chunks mean lower TTFT and higher throughput — but each run is heavy, so decode tokens wait longer behind it and TPOT degrades.

The paper's measured results make the imbalance concrete: at serving time, a 2048-chunk SGLang gains TTFT and throughput but pays in TPOT, exactly the seesaw the dial enforces.

While SGLang-2048 demonstrates a 3.20× TTFT improvement and 1.18× higher throughput than SGLang-1024, the 2048 chunk suffers from 0.78× worse TPOT on average, confirming the imbalanced tradeoff inherent in chunked prefill.§4.2, End-to-End Performance

4.4 Strawman 1 — disaggregation

If lockstep interference is the problem, the obvious cure is to stop co-running the phases at all. Disaggregation (DistServe, Splitwise, DeepSeek) places prefill on one pool of GPUs and decode on another, then ships each request's KV cache across the interconnect when it crosses the boundary. The interference vanishes, but three new costs appear: the pool ratio must be re-tuned for every workload, it cannot react quickly when load shifts, and the KV migration leans hard on expensive high-bandwidth links — all while compute on each device is still stranded by the very phase imbalance disaggregation was meant to fix.

However, such systems require careful tuning of GPU allocations for each phase, tailored to specific workload patterns (DeepSeek-AI et al., 2024), and struggle to reconfigure quickly under fluctuating request loads (Zhong et al., 2024).§1, Introduction
Furthermore, they impose heavy demands on high-bandwidth interconnects to support frequent state migration (Qin et al., 2025), significantly restricting the deployment scenarios.§1, Introduction

4.5 Strawman 2 — uncoordinated spatial sharing

The second instinct keeps the phases on one GPU but separates them into different processes that share the SMs spatially. MuxServe does this with NVIDIA MPS and hand-set, fixed SM quotas: prefill gets so many SMs, decode gets the rest. This does saturate the device — there is no lockstep idling — but because the split is static and chosen in advance, it cannot track the request mix as it shifts, and the resulting per-request latency becomes unpredictable. Saturation without coordination buys throughput at the price of any latency guarantee.

Apart from chunked prefill-based approaches, MuxServe (Duan et al., 2024) (Figure 4) decouples prefill and decode phases into separate processes, leveraging MPS (NVIDIA, 2025) with manually configured, fixed SM quotas to enable spatial sharing.§2.3.3, Existing Optimizations
This coarse-grained static partitioning leads to unpredictable latency despite saturating the GPU.§2.3.3, Existing Optimizations
Background <em>MPS</em> (Multi-Process Service) is NVIDIA's mechanism for letting several processes share one GPU context, so their kernels can run on the device at the same time instead of taking turns. It is the substrate Bullet itself depends on for co-locating two engines. The difference is coordination: MuxServe sets the SM quota once and leaves it; Bullet keeps MPS but adds fine-grained SM masking and a predictor so the split between prefill and decode can move with the workload. The strawman is not MPS — it is MPS without a brain.

4.6 The two takeaways Bullet builds on

The paper distils the whole motivation into two takeaways. Together they set Bullet's mandate: not merely to saturate the GPU, but to do so while keeping latency predictable through fine-grained, model-driven provisioning of SMs between the two phases.

Takeaway Takeaway 1. GPUs remain underutilized even during compute-intensive prefill. While co-locating prefill and decode saturates the resources, precise resource provisioning to orchestrate the two phases is demanded. (§2.2.3)
Takeaway Takeaway-2. Both chunked prefill and uncoordinated spatial sharing exhibit skewed throughput–latency tradeoffs. This urges for a fine-grained yet predictable execution mechanism for optimal LLM serving performance. (§2.3.3)
What the public artifact actually exercises Takeaway-2 calls for a fine-grained yet predictable mechanism — the SLO-aware scheduler and dynamic SM partition. The public artifact-evaluation script, however, launches Bullet with only --enable-bullet-engine, not --enable-bullet-full. The predictable half of Takeaway-2 is present in the code but not exercised by the bundled experiment; see the architecture and scheduler sections for that path.

With the problem framed — chunked prefill wastes the GPU through wave-quantization bubbles and triangular KV reloads, disaggregation strands compute and burdens the interconnect, and static spatial sharing trades predictability for saturation — the next section turns to Bullet's architecture, which keeps the phases co-located but replaces the single chunk-size dial with model-driven, layer-level resource control.

5. Bullet's Architecture: Two Engines, Two SM Slices

The previous sections established why GPUs sit idle during LLM serving: prefill is compute-bound, decode is memory-bound, and running them in lockstep (chunked prefill) or on different hardware (disaggregation) each leaves resources on the table. Bullet's answer is structural. This section describes its architecture from the top down — first the single design idea, then the four components that form its control loop, then what that idea becomes in the actual repository code, and finally the flag hierarchy you will use to turn each layer on.

5.1 The one-sentence design

Bullet keeps prefill and decode on the same GPU and the same GPU memory, but gives each its own CUDA stream pinned to a disjoint slice of streaming multiprocessors (SMs), with the size of each slice chosen at runtime. This is the pivot that distinguishes it from both prior families of approaches.

Background A streaming multiprocessor (SM) is the GPU's fundamental unit of execution — a self-contained block of compute lanes, registers, and tensor cores. A modern data-center GPU has many of them (an H100 has 132). A CUDA stream is an ordered queue of GPU work; kernels in different streams may run at the same time if the hardware has spare SMs. Bullet's design hinges on placing prefill work in one stream and decode work in another, and then confining each stream to a fixed subset of SMs so they do not fight over the same compute lanes.

Disaggregation places the two phases on physically separate GPUs, which forces costly state migration over the interconnect and reconfigures slowly. Chunked prefill keeps everything on one GPU but fuses prefill and decode into a single hybrid launch, which couples their latencies and caps utilization. Bullet rejects both couplings: same device and same memory as chunked prefill, but two independent launches on two independent SM slices, like a software-defined disaggregation that costs no migration.

Prior attempts have sought to address phase imbalance either by isolating prefill and decode across different GPUs, or by coordinating them on the same device through spatial multiplexing.§1, Introduction
To address GPU under-utilization and balance the trade-off between throughput and latency, we propose Bullet, an LLM serving system that saturates GPU resources through spatial-temporal orchestration with fine-grained resource provisioning.§1, Introduction

The phrase “spatial-temporal” is literal. Spatial: at any instant, the SM array is split into a prefill slice and a decode slice. Temporal: across successive scheduling cycles, the boundary between those slices moves, so a step that is prefill-heavy can hand most SMs to prefill, while the next step can hand most of them to decode. 5.2 The four components and the control loop

Bullet is built from four cooperating components that together form a closed control loop running once per layer-wise scheduling cycle. They are, in dataflow order, a performance estimator, an SLO-aware task scheduler, a computational resource manager, and a concurrent execution engine. Each is treated in depth in its own section of this guide.

The loop is the key to the design. Crucially, the paper claims all of this happens at microsecond-level overhead, so the control loop can run as often as once per layer without throttling the GPU.

6. The SM-Scaling Roofline Model (SRM)

This is the section the guide exists for. If you want one tool to model LLM inference time on a partitioned GPU, this is it. Bullet co-runs a prefill kernel on one slice of streaming multiprocessors (SMs) and a decode kernel on the rest; to choose the split intelligently it must predict how long each kernel will take under each possible slice. The SM-Scaling Roofline Model (SRM) is the analytical predictor that answers that question in microseconds. Part A teaches the model as the paper presents it; Part B is an honest account of what the public repository actually ships.

Part A — The model

6.1 Why a new model is needed: the Execution State has six factors

When prefill and decode execute concurrently on disjoint SM partitions, the latency of each is not a function of its own inputs alone. It depends on the joint configuration of both phases plus how the SMs are divided. The paper names this joint configuration the Execution State (ES) and lists exactly six factors that determine co-executed latency.

6.2 SRM (Equation 1): a roofline whose ceilings depend on SM count

Background A standard roofline model bounds a kernel's achievable throughput by two ceilings: a flat compute roof (peak FLOP/s) and a sloped memory roof (peak bytes/s times arithmetic intensity). A kernel's arithmetic intensity is $flop_k / mem_k$ — the number of arithmetic operations performed per byte moved. Compute-bound kernels sit under the flat roof; memory-bound kernels sit under the slope. The classical roofline assumes the whole GPU; SRM's contribution is to make both roofs functions of how many SMs the kernel is actually given.

The first ceiling is compute. When a kernel is confined to $N_p$ of the $N$ total SMs, its peak compute throughput drops proportionally: granting half the SMs gives roughly half the peak FLOP/s.

Theoretical compute performance scales linearly as Cp = Cpeak · Np/N.§3.2.2, SM-scaling Roofline Model (SRM)

The second ceiling is memory bandwidth, and here the scaling is subtler. Adding SMs increases memory traffic only until the SMs collectively issue enough requests to saturate the memory system's peak bandwidth. Past that inflection point $N_d$, extra SMs buy no extra bandwidth — the memory roof is capped at $D_{peak}$. Network bandwidth behaves identically with its own inflection point $N_w$.

Memory and network bandwidth exhibit proportional scaling until reaching inflection points Nd and Nw, where the SMs generate sufficient traffic to saturate the respective peak bandwidth […]§3.2.2, SM-scaling Roofline Model (SRM)

Putting both ceilings together gives Equation 1. The per-kernel latency on $N_p$ SMs is the kernel's FLOP count divided by whichever ceiling — memory or compute — binds first:

$$C_p = C_{peak}\cdot \frac{N_p}{N}, \qquad D_p = D_{peak}\cdot \min\!\Big(1,\ \frac{N_p}{N_d}\Big)$$ $$T'_{k,p} = flop_k \cdot \min\!\Big(\frac{flop_k}{mem_k}\cdot D_p,\ \ C_p\Big)^{-1}$$

Read the inner $\min$ as take the lower roof: the achievable throughput is the smaller of the memory-bound term (arithmetic intensity times the scaled bandwidth $D_p$) and the compute-bound term ($C_p$). The outer reciprocal turns throughput into time. The intuition the paper supplies is geometric: as you grant fewer SMs the whole roof slides down. Above $N_d$ the bandwidth plateau stays at peak so only the compute roof lowers; below $N_d$ both the slope and the plateau fall together.

When using 54 SMs, the attainable memory bandwidth remains at its peak, maintaining the original roofline slope while lowering the plateau. For 20 SMs, both the slope and plateau decline.§3.2.2, SM-scaling Roofline Model (SRM)

This asymmetry is exactly what makes spatial partitioning profitable. A compute-bound prefill kernel speeds up almost linearly with more SMs (its roof is $C_p \propto N_p$). A memory-bound decode kernel already saturates bandwidth at a modest $N_p \ge N_d$, so handing it more SMs is wasteful — those SMs are far better spent on prefill. Figure 3 (from paper): Speedup versus the fraction of SMs granted. Prefill rises almost linearly — its compute roof is $C_p \propto N_p$ with no plateau. Decode saturates early and flattens once $N_p$ passes the memory inflection point $N_d$, where $D_p$ hits $D_{peak}$ and stops growing. This is Equation 1 made visible.

6.3 Calibration (Equation 2): closing the gap to the roofline

A roofline is an upper bound — real kernels never reach it because of launch overhead, imperfect overlap, and tile quantization. SRM closes this gap with a single multiplicative correction. To assemble the baseline prediction the paper computes each LLM kernel's arithmetic intensity with the open-source llm-viewer analyzer, evaluates Equation 1 to get $T'_{k,p,ES}$, and sums the per-kernel times over all layers to obtain the model's total latency $T'_{p,ES}$.

For each Execution State ES, we compute the arithmetic intensity of every LLM kernel with llm-viewer […], apply SRM to obtain its baseline latency […], and aggregate these values to yield the total LLM latency […]§3.2.2, SM-scaling Roofline Model (SRM)

The calibration factor $\alpha$ is simply the ratio of the measured time to the predicted time for a sampled configuration:

$$\alpha_{p,ES} = \frac{T^{measured}_{p,ES}}{T'_{p,ES}}$$

The crucial economy is that $\alpha$ need not be measured for every state. Hardware utilization varies near-linearly between similar inputs, so a factor fitted on a few sampled configurations extrapolates to the unmeasured ones. For decode, the paper reports that as few as two samples suffice to model latency as a function of SM count.

6.4 Modeling contention: isolated SMs leave only memory and network interference

So far Equation 1 modeled a kernel alone. But in Bullet two kernels run at once. The key simplification is that because prefill and decode occupy disjoint SMs, there is no compute contention — the two never fight for the same arithmetic units. What remains is contention in the shared memory subsystem and the network. The paper's empirical claim is that this residual interference is remarkably stable, which is what makes a single calibration factor trustworthy.

Extensive evaluation of 7360 concurrent ES on A100 […] and 8×H20 […], each repeated for 30 runs, observes that 95% of latency measurements deviate less than ±6.8% from the mean of the respective repeated runs.§3.2.3, Modeling Contention

To pin the worst case, the paper bounds memory interference by co-running two unusually demanding kernels: a memory-copy kernel on $N_p$ SMs and an up-gated layer (UG), a large GEMM, on the remaining $N - N_p$ SMs. Even under this adversarial pairing the GEMM degrades by less than 8% once it holds more than 60% of the SMs. Because actual prefill and decode kernels are gentler than this pair, their latency is reliably calibrated by Equation 2 with very few samples.

Figure 10 shows that UG exhibits marginal performance degradation (¡8%) when using more than 60% SMs.§3.2.3, Modeling Contention

Network contention is dismissed as low: inter-phase traffic scales with the prefill sequence length $sl$ or the small decode batch $dbs$, and the memory-subsystem impact of those transfers is already folded into the end-to-end bandwidth calibration.

Inter-phase network contention is low since the traffic scales with either sl or dbs, where dbs is relatively small.§3.2.3, Modeling Contention

6.6 How this lets you model inference time

Now the thread the reader came for. To model the inference time of one phase under a candidate SM split, you do three things. (1) For each kernel in a layer, take its arithmetic intensity $flop_k/mem_k$ and evaluate Equation 1 at the allocated $N_p$ to get the roofline latency $T'_{k,p}$. (2) Sum over all kernels and layers to get the phase's raw predicted latency $T'_{p,ES}$. (3) Multiply by the calibration factor $\alpha_{p,ES}$ to correct for real-world inefficiency. The result is a microsecond-cost estimate of how long prefill (or decode) will take on that exact slice of the GPU.

The scheduler (see §7) calls this predictor for several candidate splits and picks the one that balances throughput against latency; the resource manager (§8) then enacts the chosen split via SM masking. A hands-on walkthrough that builds the predictor end-to-end appears in §12. Because $\alpha$ is fitted from data, the model improves as it observes more live traffic.

The model and the §2 numbers turn the partition into arithmetic. Decode is memory-bound, and the paper measures that on the A100 its bandwidth saturates at an inflection of $N_d = 30$ SMs (Figure 8b): past 30 SMs, extra SMs buy decode almost nothing. Prefill is compute-bound and uses every SM it is handed. So the SRM's advice writes itself:

decode : D_p(30 SM) = D_peak × min(1, 30/30) = full 2.0 TB/s → give decode ≈ 30 SMs (15 TPC) prefill: C_p(78 SM) = 312 × 78/108 ≈ 225 TFLOP/s (72% peak) → give prefill ≈ 78 SMs (39 TPC)

Both phases now sit near their own ceiling and neither starves the other: decode gets the ≈ 30 SMs it can actually use, prefill claims the ≈ 78 it can. Hand decode all 108 SMs instead and ≈ 78 of them would be busy on memory-bound work that gains nothing — the exact waste Bullet exists to remove. And because $N_d$ shifts with batch size and context length, this split is re-derived every step, not fixed once.

7. SLO-Aware Scheduling

The previous section described the mechanism Bullet uses to carve the GPU into spatial slices. This section describes the policy — the scheduler that decides, on every step, how many of those slices each phase receives and which requests run next. The paper frames this as an SLO-aware task scheduler: a controller that pushes prefill as hard as possible while keeping decode latency inside its target. We first present the algorithm exactly as the paper describes it, then audit, honestly, how much of that controller actually ships in the public code.

Background An SLO (service-level objective) is a latency target a serving system promises to meet. For LLM inference, two SLOs dominate. TTFT (time-to-first-token) measures how long a user waits before the first output token appears; it is governed by the prefill phase that processes the whole prompt at once. TPOT (time-per-output-token) measures the average gap between successive output tokens; it is governed by the decode phase that emits one token per step. A good scheduler must satisfy both at once, even though prefill and decode compete for the same hardware.
Since LLM serving systems generally necessitate adherence to service-level objectives (SLOs) of predefined latency requirements […], predictable and controllable execution time over the two phases is demanded.§2.2.3, GPU Resource Provisioning and Sharing

7.1 Two asynchronous schedulers, one per engine

Recall from §6 that Bullet co-locates two engine processes on one GPU: a prefill master and a decode master. Each runs its own scheduler independently. They do not call each other; instead they read and write a shared metadata buffer, so each perceives the other's state without blocking. This asynchrony is essential — a single global scheduler would serialize the two phases and reintroduce the lock-step coupling Bullet was built to escape.

Each of the prefill and decode concurrent execution engine […] runs a scheduler autonomously.§3.3.1, Scheduling Workflow

The two schedulers advance their phases at deliberately different granularities. The prefill scheduler launches a fixed number of layers per step and then synchronizes, returning control to the CPU so it can re-decide before the next group of layers. This gives fine temporal control: the system can react to a load spike between any two layer groups rather than only at request boundaries. The decode scheduler does the opposite — it issues an entire step as one CUDA Graph, because decode kernels are tiny and numerous, and per-kernel launch overhead would otherwise dominate.

Background A CUDA Graph is a way to record a whole sequence of GPU operations once and then replay it with a single submission. Normally the CPU must issue each kernel launch separately, and for the many small matrix multiplications and attention kernels in a decode step, that CPU-side launch overhead can rival the actual compute time. Capturing the step as a graph collapses dozens of launches into one, so the GPU stays busy and the CPU is freed. The trade-off is rigidity: a captured graph executes a fixed shape, which is why Bullet uses graphs for the uniform decode step but keeps prefill under flexible layer-wise CPU control.

7.2 The scheduling objective

Bullet's objective is asymmetric on purpose. It prioritizes prefill, because finishing prefill faster frees its SMs sooner and lets decode batches grow larger, which is where throughput comes from. But this priority is conditional: prefill may take SMs from decode only while decode's TPOT SLO still holds. The decode phase is therefore given the minimum number of SMs that meets its target, and no more — any surplus is better spent on prefill.

The primary scheduling objective is to prioritize prefill while respecting decode SLOs, since shorter prefill latency enlarges decode batch size and raises system throughput […].§3.3.1, Scheduling Workflow
During concurrent operation, the decode phase is provisioned with the minimum SM counts that satisfy SLO.§3.3.1, Scheduling Workflow

Two further refinements make the controller smooth rather than jerky. As the final prefill layer nears completion, SMs are handed back to decode early, so the transition from co-running to decode-only does not stall. And during any reconfiguration, the phases briefly share overlapping SMs rather than idling them — a small, bounded interference is preferable to leaving silicon dark while masks are being reset. Layer-wise prefill keeps this interference confined to small, predictable windows.

During reconfiguration, Bullet eliminates inter-phase synchronization by partially sharing SMs between phases rather than idling unused resources.§3.3.1, Scheduling Workflow

7.3 System state and per-step estimation

The scheduler operates over a system state $S=(ES, PS, RS)$: the execution state $ES$ (from §3.2, the hardware-facing model inputs), the prefill progress $PS$, and the per-request latency metrics $RS$. The prefill progress itself is a triple: the queuing-request set $Q$, the in-flight request set $P$, and the count of executed layers $L_{exe}$. Per request, the scheduler also records arrival time $a_i$ and decode-start time $d_i$, which are what let it compute normalized latencies.

To facilitate SLO-aware scheduling, Bullet monitors the system state defined as S=(ES,PS,RS), where ES denotes the execution state […], PS the prefill progress, and RS the per-request latency metrics.§3.3.2, Request Scheduling and Resource Provisioning

On every step the two schedulers estimate latencies and exchange them through the shared buffer. The prefill scheduler estimates GPU execution times for all requests in $P\cup Q$ under the current execution state, while the decode scheduler predicts the next step's latency and updates its TPOT. Each then writes its estimate to the global metadata buffer, so both perceive the holistic state before deciding.

At time t, the prefill scheduler estimates GPU execution times for all requests in P∪Q under current ES, while the decode scheduler predicts next-step latency and updates the corresponding TPOT.§3.3.2, Request Scheduling and Resource Provisioning

7.4 Algorithm 1, the prefill scheduling loop

The paper distills the prefill side into Algorithm 1, reproduced below verbatim from the paper's pseudocode (it is the paper's algorithm, not repository code). Read it in three movements. First, estimate and exchange latencies (lines 4–6). Second, build the batch: reorder the waiting queue by ascending predicted latency so long as that reordering does not violate any pending request's TTFT SLO, then pop requests into the batch until the batch reaches the arithmetic-intensity ceiling — past that point, adding tokens no longer raises utilization (lines 8–18). Third, provision SMs based on whether decode's P90 TPOT is within its SLO $\Gamma_d$ (lines 21–28).

function Schedule(S):

    WriteGlobalBuffer(ttft)
    tpot  ← ReadGlobalBuffer()

    else if P90(tpot) ≤ Γ_d then

    return next_tasks, L_exe + L_step

The three provisioning branches encode the asymmetric objective precisely. If decode's P90 TPOT is comfortably within $\Gamma_d$, ReduceDecodeSM shrinks decode's slice and gives the freed SMs to prefill — decode had spare headroom. If decode is over its TPOT SLO, ReducePrefillSM does the reverse, pulling SMs back to decode. And when both SLOs cannot hold at once — the system is past its capacity — SetBalancedSM enforces a balanced ratio so neither phase degrades catastrophically. In extreme prefill load, the paper also allows decode to be temporarily suspended (Figure 11, region ➁), but only while TPOT still meets its SLO.

When both SLOs cannot simultaneously be satisfied, indicating the system is beyond maximum capacity, a balanced SM ratio is enforced to limit excessive latency in either phase […].§3.3.2, Request Scheduling and Resource Provisioning
Takeaway The paper's scheduler is a feedback controller: estimate latencies → reorder and batch prefill up to the compute ceiling → push SMs toward prefill whenever decode has TPOT headroom, pull them back when it does not, and balance when neither SLO can hold. Every decision is gated on a predicted P90 latency compared against an SLO target.

7.5 Paper vs. public repository: what the scheduler actually does

Algorithm 1 is a clean, SLO-driven controller. The public code, however, ships only the plumbing around it, not the decision logic. The honest summary: the word scheduler in the public branch does not denote an SLO-driven queue reorderer; it denotes a per-step resource hook whose actual numbers come from a predictor that is not in the repository. 8. SM Masking via libsmctrl (A CUDA Deep Dive)

The previous sections described what Bullet wants to do: confine the prefill engine to one slice of the GPU and the decode engine to another, and to change that split from one step to the next. This section is about the actuator that physically enforces the split — the mechanism that takes an abstract decision such as "give prefill TPCs [0, k) and decode the rest" and turns it into a hardware state the GPU obeys. That actuator is libsmctrl SM masking, and unlike the latency predictor (which is absent from the public repository), the masking machinery is fully present and is the part of Bullet that a beginner can read end-to-end.

8.1 The requirement: cheap, reconfigurable SM partitioning

Bullet runs two engines on one GPU and is designed to rebalance their share of the compute units per step (see §7); whether the split actually changes every step depends on the external predictor discussed in §6, but the actuator below is built to support it. For this to be useful, the partitioning primitive must satisfy three properties at once: it must confine a kernel to a chosen subset of streaming multiprocessors; it must be reconfigurable on the fly without relaunching the engine; and it must cost essentially nothing in time and memory, because it fires on every forward pass. The obvious vendor-supported route — NVIDIA MPS combined with CUDA Green Context — can partition SMs, but its cost makes per-step control impractical.

While MPS (NVIDIA, 2025) with CUDA Green Context (gre, 2025) supports SM partitioning, its memory overhead exceeds 700MB for only 4 static policies in LLM serving (Cui et al., 2025), rendering it impractical for Bullet's fine-grained control.§3.4, Computational Resource Manager

The number is the crux: more than 700 MB for only four static policies. Bullet does not want four fixed splits; it wants a continuum of splits chosen per step, which under the MPS/Green-Context model would be unaffordable. So Bullet drops the vendor path and adopts the libsmctrl SM-masking library of Bakita and Anderson, which writes the partition directly into CUDA's internal state at near-zero cost.

The libsmctrl_set_stream_mask API sets the metadata of a CUDA stream (Corporation, 2025) to restrict all kernels launched within it to execute on a specified SM subset.§3.4, Computational Resource Manager

8.2 What an SM mask is

Background A CUDA stream is an ordered queue of GPU work: every kernel you launch into a stream runs after the previous one in that same stream, while different streams may run concurrently. An SM mask is a per-stream bitmask that the hardware consults when it decides where to place a kernel's thread blocks. By tagging a stream with a mask, libsmctrl tells the GPU scheduler: for any kernel launched on this stream, only schedule its blocks onto the unmasked compute units. Because the mask travels with the stream, Bullet does not have to modify a single kernel — it simply masks the stream that the prefill engine and the decode engine each launch into.
Background: TPC vs SM The mask does not address individual SMs; it addresses Thread Processing Clusters (TPCs). A TPC is the next unit up from an SM in NVIDIA's hierarchy, and on every GPU Bullet targets (Ampere, Ada, Hopper) one TPC contains exactly two SMs. So a 66-TPC H100 has 132 SMs, and a mask bit that disables TPC 0 removes SMs 0 and 1 together. Keeping this 1 TPC = 2 SMs identity in mind is essential: every TPC index in the code corresponds to two physical SMs.

The library even derives that count for you. libsmctrl_get_tpc_info_cuda reads the SM count from the driver and divides by the SMs-per-TPC of the architecture; for everything Bullet runs on, that divisor is two.

8.3 Bitmask polarity: a SET bit DISABLES a TPC

The single most load-bearing detail in the whole library is its inverted polarity. One naturally reads a mask as "a 1 means use this unit". libsmctrl does the opposite: a SET bit means the corresponding TPC is disabled. The header states it in plain words.

BulletServe · csrc/src/libsmctrl.h:34–47
/**
 * Notes on Bitmasks
 *
 * All of the core partitioning functions take a `uint64_t mask` parameter. A
 * set bit in the mask indicates that the respective Thread Processing Cluster
 * (TPC) is to be __disabled__.
 *
 * Examples
 * To prohibit the next kernel from using TPC 0:
 *     libsmctrl_set_next_mask(0x1);
 * Allow kernels to only use TPC 0 by default:
 *     libsmctrl_set_global_mask(~0x1ull);
 * Allow kernels in a stream to only use TPCs 2, 3, and 4:
 *     libsmctrl_set_stream_mask(stream, ~0b00111100ull);
 */

Because of this convention, the natural human request "enable exactly TPCs [low, high)" has to be turned into "disable everything except [low, high)". That is precisely what the helper libsmctrl_make_mask does: it builds a run of high − low set bits to represent the enabled range, shifts them up into position, and then bit-inverts the whole word so that the enabled range becomes zeros and everything else becomes ones.

BulletServe · csrc/src/libsmctrl_core.c:531–542
int libsmctrl_make_mask(uint64_t *result, uint32_t low, uint32_t high_exlusive) {
  uint64_t mask = 0ULL;
  int num_enabled = high_exlusive - low;
  for (int i = 0; i < num_enabled; ++i) {
    mask = (mask << 1) | 1ULL;
  }
  for (int i = 0; i < low; ++i) {
    mask <<= 1;
  }
  *result = ~mask;
  return 0;
}
Footgun The header itself warns that the inversion operator must be applied to 64-bit literals: ~0x1 is not ~0x1ull. A 32-bit inversion silently leaves the top 32 TPCs enabled. The parameter name high_exlusive is also misspelled in the source; it is copied verbatim here so a reader grepping for high_exclusive is not confused.

8.4 Carving the GPU from opposite ends: the reversed decode window

The Python wrapper SMController.set_stream_mask is where Bullet's spatial-sharing strategy becomes concrete. Given a TPC range and a CUDA stream it calls make_mask then hands the inverted mask to the C setter. The subtle piece is the reversed argument. Prefill is masked into the range [0, k) starting from the bottom of the TPC space; decode, when reversed is true, is reflected to the top of the space by mapping [low, high) to [total − high, total − low). The two engines therefore grow toward each other from opposite ends, which keeps each engine's slice contiguous and minimises the chance that they collide as the split shifts step to step.

8.5 How the mask actually rewrites hardware state

There is no public CUDA API for "restrict this stream to these SMs". libsmctrl manufactures one by reverse-engineering CUDA's internals along two paths. The per-stream path writes the mask directly into the opaque driver stream struct at a hardcoded byte offset that depends on the exact CUDA version; CUDA then copies that field into the launch descriptor of every kernel on the stream. The global/next path instead subscribes a callback to a private CUDA export table and rewrites the descriptor's SM-mask fields just before each kernel is uploaded to the GPU.

Background: the TMD / QMD Every kernel launch is described to the GPU front-end by a small hardware structure — the Task Metadata Descriptor (TMD), called the QMD on older hardware. It records grid and block dimensions, shared-memory size, and, on capable architectures, an SM/TPC enable mask. The driver builds this descriptor and uploads it for every launch. libsmctrl cannot see it through any documented interface, so it hooks an internal "pre-upload" callback that fires after the driver has written the descriptor but before it reaches the GPU, then overwrites the mask fields in place. The field offsets differ by TMD version: 84 and 88 on Kepler-class V01_06 descriptors, 304 and 308 on the Hopper-class V04_00 descriptor.

The masking half of the loop is short and entirely in this repository: a per-step hook, tp_worker.update_bullet_before_forward, runs before every forward pass and can re-mask the stream — it computes a desired TPC count, and only when that count differs from the previous one (num_tpcs != self.last_num_tpc) does it call set_stream_mask to build the inverted mask and write it to the stream, after which every subsequent kernel on that stream inherits the restriction. 8.6 The ≥128-SM / Hopper caveat

The two paths are not equally capable. The global and next masks are each a single uint64_t, so they can only address 64 TPCs; there is no 128-bit variant of them in this branch. Worse, on a Hopper-class TMD the callback shown above force-disables the upper 64 TPCs on every launch (*(uint32_t*)(tmd + 312) = -1), with an in-source comment admitting it is a stopgap. Only the per-stream path writes all four mask words and so scales past 64 TPCs. That is the concrete reason Bullet drives its prefill/decode partitioning through set_stream_mask rather than the global mask.

The Python wrapper even refuses to use the global path on large GPUs: set_global_mask raises when the device has 128 or more SMs (which is 64 or more TPCs), the exact regime in which the global path is unsafe.

The previous sections established why Bullet runs prefill and decode at the same time and how it partitions the streaming multiprocessors between them. The design goal throughout is that a request which finishes prefill should reach the decode engine by transferring metadata only, never the KV tensors themselves.

9.1 Two processes, one GPU

Bullet does not run prefill and decode as two threads inside one Python process; it runs them as two genuinely independent OS processes, each with its own Scheduler instance, both pinned to the same physical GPU. In the launcher, the decode server-arguments are produced by cloning the prefill arguments and flipping the role bits, and when the Bullet engine is enabled the spawn loop runs twice instead of once.

Background Why two processes rather than two threads? In Python, a single interpreter has one Global Interpreter Lock, so two threads cannot truly run Python control flow in parallel — the prefill loop and the decode loop would constantly contend for the same lock. Two separate processes have independent interpreters and independent control flow, so each scheduler can drive its phase without coupling. The cost is that the two processes no longer share an address space, which is exactly why the GPU memory and the control state must be shared explicitly (the rest of this section).
Background Two independent processes cannot ordinarily run kernels on one GPU at the same time — by default each process gets its own GPU context and the hardware time-slices between them. CUDA Multi-Process Service (MPS) removes that restriction: it funnels kernels from several processes into a single shared GPU context so their kernels can occupy different SMs concurrently. MPS is therefore a hard prerequisite for Bullet, and the launcher sets the MPS pipe directory before each spawn.

9.2 The shared GPU memory pool

Because the two processes do not share an address space, the paged KV cache must be allocated once and then made visible to both. Bullet allocates the K/V buffers, the per-token free-list, and the request-to-token pool on the prefill side, and the decode side reconstructs the same physical GPU buffers without any new allocation. The paper frames this as a single shared GPU memory region with no copy at handoff.

Background CUDA inter-process communication (IPC) is the mechanism for sharing a GPU allocation across process boundaries. The KV pool, however, is mutated by both engines: each can allocate or free slots at any moment. To keep the shared free-list consistent, Bullet serialises every allocation and deallocation behind one cross-process lock.

Background flock is an operating-system advisory lock taken on a file descriptor. When one process holds an exclusive lock (LOCK_EX) on a well-known path, any other process asking for the same lock blocks until it is released. Because the lock is enforced by the kernel rather than by shared program memory, it works between completely unrelated processes — which is exactly Bullet's situation, two separately spawned engines that must not corrupt one free-list.

9.4 Request handoff over ZeroMQ

When prefill finishes a request, decode must learn about it. Because the KV cache already lives in shared GPU memory, the handoff need only carry which slot and the request's sampling and timing state — a small dictionary, not tensors. Bullet sends this over a ZeroMQ socket, which is the source of the paper's “microsecond overhead”.

Once prefill completes, the request migrates to decode without KV-cache transfer, and only metadata is asynchronously sent to the decode engine via ZeroMQ […], enabling microsecond overhead.§3.5.2, Execution Workflow
Background ZeroMQ is a lightweight messaging library that provides socket-like channels between processes (over TCP or a local IPC endpoint) without a broker. Two socket patterns appear here: a PAIR socket is an exclusive one-to-one pipe — perfect for the single prefill→decode data channel — while ROUTER/DEALER sockets form an addressable hub-and-spoke bus, used for named control messages. Bullet uses both, for two different jobs.

The wire schema for the data plane is req_to_dict_v2. Notice what crosses the socket: the request ids, the output ids, sampling parameters, the shared-pool slot req_pool_idx, and the timing state — but never the K/V tensors, which are already shared (§9.2).

Background Three metric names recur throughout this section. TTFT (time-to-first-token) is how long a user waits before the first output token appears — it is dominated by the prefill phase. A serving system is good when it pushes throughput up without pushing these latencies past their SLOs.

11.6 Sensitivity and ablation: why dynamic, and why both halves

Two studies justify the design choices. The sensitivity study fixes the prefill SM count at a constant and lets decode use all SMs. No single fixed split wins. Running prefill on all 108 SMs (SM-108, i.e. no partitioning) achieves low TPOT but suffers 1.20× higher average TTFT and 1.19× worse P90 tail, cutting throughput and SLO attainment by 13%. A small static partition is worse still: SM-84 inflates TTFT by 1.78× — worse even than the chunked-prefill baselines — and reduces throughput by 5.9%. The conclusion is that any fixed allocation trades one phase against the other, which is exactly the case for making the split adaptive.

Therefore, there is no optimal fixed SM allocation, as smaller partitions improve TPOT but degrade TTFT and introduce tail latency violations, and vice versa.§4.4, Sensitivity Studies

The ablation study then isolates the two halves of Bullet's design. The Naive variant — concurrent execution with neither partitioning nor scheduling — shows the expected latency imbalance from unpartitioned contention. Adding partitioning alone (w/Partition) improves Azure-Code TPOT but suffers unacceptable TTFT degradation, because it cannot reorder pending requests. Adding scheduling alone (w/Scheduler) keeps latency comparable while reducing TPOT through contention alleviation. Only the complete design — partitioning and scheduling together — achieves balanced latency across all workloads. Neither half is sufficient; the result is a property of the combination.

Only the complete Bullet design, combining both partitioning and scheduling, achieves balanced latency across all workloads.§4.5, Ablation Studies
This sensitivity result is the system-level echo of the kernel-level curves in §6, Figure 3: prefill speed scales almost linearly with the SM count it is given, whereas decode saturates after only a few SMs, so the two curves cross at a point that shifts with the live load. 12.1 The inference-time model, in one place

Bullet does not enumerate the millions of possible execution states; it builds a lightweight analytical model that runs in microseconds and is corrected by a small number of measurements. The starting point is the SM-scaling roofline model (SRM), which predicts the latency of a single Transformer-layer kernel $k$ when only $N_p$ of the GPU's $N$ streaming multiprocessors are available to it.

Therefore, we build a lightweight analytical model with a minimal profile and runtime overhead.§3.2.1, Problem Formulation

For a kernel with $flop_k$ arithmetic operations and $mem_k$ bytes of memory traffic, the SRM predicts

$$ T'_{k,p}=flop_k\cdot\min\!\left(\tfrac{flop_k}{mem_k}\,D_p,\;C_p\right)^{-1},\quad C_p=C_{peak}\tfrac{N_p}{N},\quad D_p=D_{peak}\min\!\left(1,\tfrac{N_p}{N_d}\right). $$

The two ceilings scale differently with the SM count. Compute capacity $C_p$ falls linearly as you take SMs away, because each SM contributes a fixed slice of peak FLOP/s. Memory bandwidth $D_p$ rises with the SM count only until an inflection point $N_d$, beyond which the SMs already generate enough traffic to saturate the peak bandwidth $D_{peak}$, so adding more SMs no longer helps the memory-bound term.

Memory and network bandwidth exhibit proportional scaling until reaching inflection points $N_d$ and $N_w$, where the SMs generate sufficient traffic to saturate the respective peak bandwidth $D_{peak}$ and $W_{peak}$.§3.2.2, SM-scaling Roofline Model (SRM)
Background The arithmetic intensity of a kernel is the ratio $flop_k/mem_k$, in FLOP per byte. A roofline model says a kernel's achievable rate is the smaller of two limits: the compute ceiling, and the bandwidth ceiling multiplied by intensity. A kernel with high intensity (a large matrix multiply) is compute-bound; a kernel with low intensity (decode attention reading the whole KV cache to emit one token) is memory-bound. The SRM is a roofline whose two ceilings are themselves functions of how many SMs you grant the kernel.

The raw roofline is optimistic, because real kernels never hit the theoretical bound exactly. Bullet therefore measures the true latency at a few execution states and forms a per-state calibration factor $\alpha_{p,ES}=T^{measured}_{p,ES}/T'_{p,ES}$, which is extrapolated to the unmeasured states because the utilization pattern is near-linear between similar inputs. To get a whole-phase latency you compute the SRM latency of every layer kernel for the chosen $N_p$, sum them, and multiply by $\alpha$; the whole-step latency is then the prefill-phase and decode-phase latencies under the SM split the scheduler has selected.

For each Execution State […], we compute the arithmetic intensity of every LLM kernel with llm-viewer […], apply SRM to obtain its baseline latency […] on Np SMs, and aggregate these values to yield the total LLM latency […].§3.2.2, SM-scaling Roofline Model (SRM)
Takeaway Modeling inference time in Bullet is the product of three factors: a roofline ceiling expressed as a function of SM count (the SRM), a correction for wave quantization and contention, and an empirical calibration $\alpha$ fitted from a handful of samples. Each factor is cheap, and each is independently checkable with the micro-benchmarks below.

The calibration is genuinely lightweight. The paper reports that the decode latency curve over SM counts can be fitted from only two measured points, and that prediction and online update cost almost nothing because they rely only on the calibration equation and linear extrapolation.

Each exercise below isolates one term of the model so you can verify it on your own hardware. The SM-masking exercises use the engine's `set_stream_mask` API — the same call the engine's per-step hook (`tp_worker.py`) issues each forward step after picking a TPC count. One caveat: under the default and AE settings (`enable_sm_partition` off), that per-step hook returns the FIXED `fixed_decode_tpcs` value every step, so the partition does not actually change from step to step. The mask only varies dynamically once you supply the predictor `.so` of §12.2; in the exercises you call `set_stream_mask` directly, so you control the window regardless.

That API is `SMController.set_stream_mask`, which assigns a contiguous TPC window `[low, high_exclusive)` to one CUDA stream (recall 1 TPC = 2 SMs on these GPUs):

12.4 Research directions for AI-infra optimization

Each direction below extends one component of Bullet, and most are grounded in the paper's own future-work statements. They are ordered roughly from the most direct contribution (the missing predictor) to the most exploratory (an offline capacity-planning simulator).

(a) Train and ship the missing SRM predictor

The most valuable single contribution is the `.so` of §12.2 itself: an SRM-plus-$\alpha$ model exposing `predic_duration` and `set_adaptive_num_tpcs`. Because calibration is reported to need only two decode samples and the online update is negligible, this is a small, well-scoped artifact that immediately unlocks Bullet's dynamic SM-provisioning path.

Continuous online data collection for recalibration is straightforward.§3.2.4, Profiling and Online Calibration

(b) Relax SM isolation toward partial sharing

Bullet partitions SMs into disjoint sets. The paper lists partial sharing — letting prefill and decode overlap on some SMs — as orthogonal future work that fits without architectural change. This would require extending the contention model of §3.2.3 beyond the worst-case isolated assumption.

Bullet's SM isolation policy could be relaxed to partial sharing, yet such exploration is orthogonal to the paper's core contribution […] and can be retrofitted without architectural changes.§4.6, Discussion / Future Work

(c) Extend the latency model to MLA and LoRA

The SRM treats a kernel only through its $flop_k$ and $mem_k$, so new attention variants (such as multi-head latent attention) or LoRA adapters enter the model simply as new arithmetic intensities. The paper calls this extension straightforward; the work is in profiling the new kernels and re-fitting $\alpha$, not in changing the model.

Extending the latency model to cover new attention variants or LoRA adapters […] is straightforward and left to future work.§4.6, Discussion / Future Work

(d) Port libsmctrl to CUDA 12.8 / Blackwell

The hard SM partition depends on libsmctrl finding a per-driver-version offset into an opaque CUDA driver structure; the bundled offsets stop at CUDA 12.6. Discovering and adding the offsets for CUDA 12.8 and newer (including Blackwell) is what would let the dynamic path run on current hardware. This was the exact blocker in our reproduction.

(e) Build an offline per-step latency simulator

Because the SRM runs in microseconds, the same predictor can drive an offline simulator that, given a workload trace, emits per-step prefill and decode latencies under any SM split. Such a simulator turns the latency model into a capacity-planning tool: sizing clusters, choosing SLO targets, and exploring scheduling policies without occupying a GPU.

At runtime, the model executes within microseconds and continuously refines with online statistics.§3.2.1, Problem Formulation

The thread running through all five directions is the same one this guide has followed from the start: once inference time is a model with named factors — SM count, arithmetic intensity, an inflection, and a calibration — the system around it becomes an exercise in feeding that model good numbers and acting on its predictions. Reading Bullet is learning that model; building on Bullet is shipping the missing pieces that connect it to real hardware.

13. Glossary & References

This closing section gathers the vocabulary the guide relies on and the works it stands on. The terms are grouped by theme, from raw GPU hardware up through the CUDA programming model, the latency-modeling concepts, the LLM-serving primitives, and finally the names that are specific to Bullet itself. A beginner can read the glossary top-to-bottom as a compact primer, or jump back to a single entry while reading an earlier section.

13.1 Hardware terms

SM (Streaming Multiprocessor)
The fundamental compute unit of an NVIDIA GPU. A modern GPU contains tens to over a hundred SMs (an H100 has 132); each SM holds its own CUDA cores, Tensor Cores, register file, shared memory and warp schedulers. Bullet partitions the GPU by handing different counts of SMs to the prefill and decode phases.
TPC (Texture/Processing Cluster)
A cluster of exactly two SMs. The SM-masking substrate Bullet uses controls allocation at TPC granularity, so the code counts in TPCs and multiplies by two to report SMs (see the low * 2 logging in set_stream_mask). On an H100, 132 SMs correspond to 66 TPCs.
GPC (Graphics Processing Cluster)
The next level up in the GPU hierarchy: a GPC groups several TPCs together and shares some fixed-function and routing resources. It matters here because hardware partition tools must respect GPC/TPC boundaries when masking SMs.
CUDA core
A scalar arithmetic lane inside an SM that executes general FP32/INT operations. CUDA cores carry pointwise and elementwise work; the heavy matrix multiplications of an LLM are instead routed to the Tensor Cores.
Tensor Core
A specialized unit inside each SM that performs small matrix-multiply-accumulate operations at very high throughput. Tensor Cores dominate the compute peak $C_{peak}$ of an LLM workload, which is why prefill (compute-bound) benefits from more SMs while decode (memory-bound) does not.
Warp
A group of 32 threads that the SM schedules and executes in lockstep — the true granularity of GPU execution. Threads inside a warp share an instruction stream; divergence between them costs throughput.
Wave / wavefront
One full round in which every SM is given a thread block to run. A kernel with more thread blocks than SMs executes in several successive waves; the last wave is often only partially filled.
Wave quantization
The utilization loss that occurs when the number of thread blocks does not divide evenly by the number of SMs, leaving idle SMs during the final, partly-filled wave. It is a central source of prefill waste that Bullet targets.
However, if the number of TBs is not evenly divisible by the number of SMs, a workload imbalance situation called wave quantization […] occurs.§2.2.1, Execution Model and Theoretical Performance Bound
HBM (High-Bandwidth Memory)
The large off-chip device memory of the GPU (tens of GB), connected by a very wide bus. Its bandwidth $D_{peak}$ is the binding resource for decode, where every generated token must re-read the model weights and the KV cache from HBM.
L2 cache
A single on-chip cache shared by all SMs that sits between HBM and the SMs. It absorbs some repeated reads, but its capacity is far smaller than the working set of LLM weights, so decode still falls back to HBM bandwidth.
Shared memory
A small, fast, software-managed scratchpad private to each SM, used by a thread block to stage data (for example the tiles in FlashAttention) and to communicate between its threads.
Register file
The largest and fastest on-SM storage, partitioned among the resident warps. Register pressure caps how many warps can be in flight on an SM at once, which in turn bounds the SM's achievable occupancy.
Background The hierarchy reads from the inside out: threads are grouped into a warp of 32; warps form a thread block that runs on one SM; two SMs form a TPC; several TPCs form a GPC; and all GPCs together form the GPU, fed by a shared L2 cache and off-chip HBM. Keeping this ladder in mind makes the rest of the glossary — and the masking mechanism in particular — much easier to follow.

13.2 CUDA programming model

Kernel
A function compiled to run on the GPU. One kernel launch spawns many threads. An LLM forward pass is a long sequence of kernel launches (GEMMs, attention, normalization, etc.).
Grid
The full set of thread blocks produced by a single kernel launch. The grid size, divided by the number of available SMs, determines how many waves the kernel needs.
Thread block (TB)
The unit of work the hardware places onto a single SM. A thread block cannot span SMs; its threads share that SM's shared memory and can synchronize with one another.
CUDA stream
An ordered queue of GPU operations. Kernels in different streams may run concurrently. Bullet places prefill and decode on separate streams and then masks each stream to a different SM subset.
CUDA Graph
A pre-recorded, replayable sequence of kernel launches that removes per-launch CPU overhead. Bullet captures the step-wise decode loop as a CUDA Graph and replays it, while prefill is launched layer-by-layer.
Concurrent Kernel Execution (CKE)
The GPU capability of running two or more independent kernels at the same time when resources allow. Bullet relies on CKE so that masked prefill and decode kernels co-execute on disjoint SM partitions.
MPS (Multi-Process Service)
An NVIDIA daemon that lets kernels from multiple processes share one GPU concurrently. Bullet runs prefill and decode as two processes under MPS; the paper notes that MPS-with-Green-Context partitioning is too coarse and memory-heavy for Bullet's needs, motivating libsmctrl instead.
CUDA Green Context
NVIDIA's official API (added in CUDA 12.4) for SM partitioning inside one process: a lightweight context bound to a chosen subset of SMs, so kernels launched through it run only on those SMs. It is the supported alternative to libsmctrl's stream mask, but each partition carries context state and memory pools — the paper measures over 700 MB for only four static policies — so Bullet avoids it for fine-grained, frequently-changing control.
CUDA IPC
Inter-process sharing of a GPU memory allocation via cudaIpcGetMemHandle / cudaIpcOpenMemHandle, so two processes can reference the same device buffer. In the paper's design this is described as sharing weights between the prefill and decode engines; in the public BulletServe, however, the PyTorch CUDA-IPC path shares the KV cache and the req_to_token pools, not the model weights.
TMD / QMD (kernel descriptor)
The Task/Queue Metadata structure the GPU driver writes for each kernel launch, encoding the launch parameters and the SM-affinity bits. libsmctrl works by intercepting and editing these descriptors so a kernel only schedules onto the permitted SMs.

13.3 Latency-modeling terms

Roofline model
A performance model that bounds a kernel's achievable throughput by either compute peak or memory bandwidth, whichever is the tighter limit for its arithmetic intensity. It produces the characteristic flat compute ‘roof’ and sloped memory ‘ramp’.
Arithmetic intensity
The ratio of floating-point operations to bytes moved from memory, $flop_k / mem_k$ for a kernel. Low intensity (decode) is memory-bound; high intensity (prefill GEMMs) is compute-bound.
Ridge point
The arithmetic intensity at which the memory ramp meets the compute roof, i.e. $C_{peak} / D_{peak}$. Kernels to its left are memory-bound; to its right, compute-bound.
Peak compute $C_{peak}$
The maximum sustainable floating-point throughput of the GPU at full SM count, dominated by Tensor-Core capacity. It sets the flat roof of the roofline.
Peak bandwidth $D_{peak}$
The maximum HBM read/write bandwidth of the GPU. It sets the slope of the memory ramp and is the binding limit for decode.
Memory inflection $N_d$
The SM count above which adding more SMs no longer raises achievable memory bandwidth — bandwidth has saturated. Below $N_d$ bandwidth scales roughly with SM count; this is why decode stops benefiting from extra SMs early. (The paper also defines a network inflection $N_w$ for inter-GPU transfers.)
SM-scaling roofline model (SRM)
Bullet's core analytical model. It extends the classic roofline so that both the compute roof and the memory slope scale with the number of allocated SMs $N_p$ (bandwidth scaling capped at the inflection $N_d$), giving a per-kernel latency estimate as a function of how many SMs the kernel is granted.
Calibration factor $\alpha$
A multiplicative correction applied to the SRM's analytical latency so the model matches measured behavior, fitted from a sparse set of profiled Execution States. It absorbs second-order effects the pure roofline ignores.
MAPE (Mean Absolute Percentage Error)
The accuracy metric the paper reports for its latency predictions — the average absolute relative error between predicted and measured latency, expressed as a percentage.
Given a kernel with $flop_k$ operations and $mem_k$ bytes of memory transactions, we construct an SM-scaling roofline model (SRM) in Equation 1 to estimate the theoretical latency on $N_p$ SMs.§3.2.2, SM-scaling Roofline Model (SRM)
Absent in repo The SRM, the arithmetic-intensity math, the $\alpha$ calibration and the predictor itself are not present in the public Python or C source. The runtime only declares a ctypes FFI to an external compiled library named by --predictor-param-file, and that .so is not shipped; with it absent the code falls back to FIXED TPC counts. See §11 and the reproduction report for the verified gap.

13.4 LLM-serving terms

Prefill
The first phase of inference, which processes the entire input prompt in parallel to produce the first token and the initial KV cache. It is compute-bound and dominated by large GEMMs, so it scales well with more SMs.
Decode
The autoregressive phase that generates one token per step, each step re-reading weights and the KV cache. It is memory-bound and saturates at a small SM count, leaving SMs idle that prefill could use.
KV cache
The stored key and value tensors of all previously processed tokens. Each decode step reads the whole KV cache from HBM, which is why decode is bandwidth-bound and why the cache size limits batch size.
TTFT (Time To First Token)
The latency from request arrival to the first generated token — essentially the prefill latency plus queuing. It is the user-facing responsiveness metric for prompt processing.
TPOT / ITL (Time Per Output Token / Inter-Token Latency)
The average time between successive generated tokens during decode. It governs perceived streaming speed; a small chunk size lowers TPOT but raises TTFT, a tension Bullet aims to dissolve.
Throughput
The total tokens (or requests) the server completes per unit time. Spatial-temporal orchestration raises throughput by keeping otherwise-idle SMs busy with prefill while decode runs.
SLO / Goodput
A Service-Level Objective is a latency target (for example a TTFT or TPOT bound); goodput is the throughput counting only requests that meet their SLO. Bullet's aim is to raise throughput without violating per-request SLOs.
Hybrid batch
A single batch that mixes prefill and decode tokens, executed in lockstep. It is the conventional way to keep the GPU busy, but it forces a throughput-versus-latency trade-off that Bullet replaces with spatial co-execution.
Chunked prefill
The Sarathi technique of splitting a long prompt into fixed-size chunks so each can join a hybrid batch. It bounds TPOT but increases TTFT and total prefill iterations — the baseline Bullet outperforms.
Token budget
A fixed per-iteration cap on the number of tokens in a hybrid batch; decode tokens are placed first and the remainder is filled with prefill tokens. The paper shows this budget is what couples the two phases and degrades both.
Prefill/decode disaggregation
The alternative design (DistServe, Splitwise) of running prefill and decode on separate GPU groups to remove interference, at the cost of KV-cache migration and load imbalance. Bullet instead co-locates them on one GPU.
Tensor parallelism
Splitting each layer's weight matrices across multiple GPUs so they jointly compute one forward pass, communicating partial results. It is orthogonal to Bullet's single-GPU SM partitioning but interacts with the network inflection $N_w$.

13.5 Bullet-specific terms

Spatial-temporal orchestration
Bullet's central idea: co-execute prefill and decode on disjoint SM partitions (spatial) while continuously re-balancing those partitions over time as load shifts (temporal), so the GPU stays saturated without a fixed token budget.
SM mask / TPC mask
A bitmask, one bit per TPC, attached to a CUDA stream so that every kernel launched in that stream may only run on the enabled TPCs (hence SMs). This is the actuator that realizes the spatial partition.
libsmctrl
The Bakita & Anderson library Bullet integrates to perform SM masking by intercepting kernel descriptors (TMD/QMD). Its set_stream_mask entry point restricts a stream to a chosen TPC range — the substrate beneath every Bullet partition decision.
Layer-wise prefill
Launching the prefill of a request one transformer layer at a time, with progress checked between layers. This confines prefill-decode interference to small, predictable windows and lets the scheduler reallocate SMs mid-request.
Execution State (ES)
The six-tuple that, for a given model and GPU, determines co-execution latency: prefill sequence length, prefill batch size and prefill SMs, plus decode context length, decode batch size and decode SMs. The predictor takes the ES as input.
--enable-bullet-engine / --enable-bullet-full
The two top-level flags. --enable-bullet-engine turns on concurrent prefill/decode processes only; --enable-bullet-full additionally turns on the scheduler and SM partitioning. The official artifact-evaluation script enables only the engine flag.
Predictor .so
The external compiled library, named by --predictor-param-file and loaded via ctypes, that holds the actual SRM-based SM-allocation policy. It is not included in the public repository, so the published code path defaults to fixed TPC counts.
