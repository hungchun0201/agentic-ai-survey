Bullet: Boosting GPU Utilization for LLM Serving

A spatial-temporal orchestration system that co-executes the compute-bound prefill phase and the memory-bound decode phase on one GPU, provisioning streaming multiprocessors at runtime under an SM-scaling roofline model

arXiv:2504.19516 ASPLOS 2026 A100 · H100 · H20 Dense & MoE Prefill + Decode
↻ Our 5-GPU Reproduction Report →

Zejia Lin, Hongxin Xu, Guanyi Chen, Zhiguang Chen, Yutong Lu, Xianwei Zhang

Sun Yat-sen University

1. Overview & Motivation

A large-language-model serving step is composed of two phases with opposite hardware appetites. The prefill phase processes the entire input prompt in a single forward pass and is compute-intensive, saturating the GPU's tensor cores. The decode phase generates one token at a time and is memory-bound, spending most of its time reading model weights and the KV cache out of high-bandwidth memory while the tensor cores sit largely idle. A single GPU executing a serving workload must interleave these two phases, and the way that interleaving is organized determines whether the device runs near its hardware ceiling or far below it. Bullet is a serving system that stops treating the two phases as competitors for a shared time slice and instead runs them concurrently, partitioning the GPU's streaming multiprocessors (SMs) between them at runtime so that prefill consumes the compute capacity that decode cannot use.

1.1 Why Now: Hybrid Batching Has Hit a Structural Ceiling

The serving systems that dominate 2025 deployments — vLLM and SGLang among them — converged on chunked prefill, a scheme in which a long prompt is split into fixed-size chunks and each chunk is co-batched with the ongoing decode tokens into a single hybrid batch. Chunked prefill was introduced to stop a long prefill from monopolizing a step and stalling decode, and it succeeds at that narrow goal. The difficulty is that a hybrid batch is still one batch executing on the full GPU at one time, so the compute-bound prefill chunk and the memory-bound decode tokens share the same kernel launch and the same set of SMs. When the chunk is large, prefill dominates the step and inflates decode latency; when the chunk is small, the launch is dominated by decode and the abundant tensor-core capacity that prefill would have used is left idle. The serving operator is therefore handed a single chunk-size dial that trades throughput against latency, and no setting of that dial recovers the compute that the two phases waste on each other. As model sizes and context lengths have grown through 2024 and 2025, the fraction of a step spent in this mismatched co-batching has grown with them, which is why a scheme that merely tunes one batch is no longer sufficient.

Conventional serving stalls decode behind a monolithic prefill; chunked prefill interleaves chunks but still serializes the two phases on the full device; the ideal schedule runs prefill and decode at the same time on disjoint slices of GPU compute.

1.2 A Concrete Bad Scenario: One Prefill Chunk on an A100

Consider an operator serving Llama-3.1-8B on a single NVIDIA A100-80GB, which exposes 108 SMs, under a chunked-prefill configuration with a 1024-token chunk. A user submits a 4096-token document for summarization; the runtime splits it into four chunks and admits the first chunk into a hybrid batch alongside the decode tokens of several conversations already in flight. During that step the prefill chunk drives the tensor cores hard, and the paper's measurements of the prefill phase on this exact device show that compute utilization climbs while memory-bandwidth utilization stays low — the prefill chunk leaves the memory subsystem under-used. In the next step the operator shrinks the chunk to protect the decode tokens' per-token latency; now the step is dominated by the memory-bound decode work, and the tensor cores that the prefill chunk had been driving fall idle. Across the four chunks the device alternates between a compute-saturated step that hurts decode latency and a memory-bound step that wastes compute, and neither step uses both subsystems at once. The user waiting on the summary and the users waiting on their decode tokens are both served by a device that is, at every instant, leaving one of its two major subsystems unused.

The gap between the two curves is the compute capacity that decode cannot consume.

1.3 The Quantified Baseline Pain

The paper supplies the numbers that turn this picture into a first-order problem. Profiling the prefill phase of Llama-3.1-8B on an A100 shows that, within a chunked-prefill step, the GPU sustains neither full compute nor full memory-bandwidth utilization: each step uses one subsystem heavily and leaves the other slack. Two structural causes are identified. The first is wave quantization — when the thread blocks of a kernel do not divide evenly across the 108 SMs, the final wave runs on only a fraction of the device and the remaining SMs stall, so a prefill kernel that needs, say, five waves spends part of its time on a partly empty machine. The second is the attention bottleneck, which keeps prefill from reaching the compute ceiling even when all SMs are nominally busy. The combined effect is that the hybrid batch, the very mechanism intended to keep the device busy, leaves a measurable fraction of the A100's compute and bandwidth unused on every step, and the only knob the operator can turn — chunk size — moves the waste from one subsystem to the other rather than removing it.

1.4 Strawman: Disaggregate Prefill and Decode onto Separate GPUs

An obvious response is prefill-decode disaggregation, the design adopted by systems such as DistServe and Splitwise, in which prefill runs on one pool of GPUs and decode on another so that each phase owns hardware matched to its profile. This removes the interference between phases, but it does so by relocating the problem rather than dissolving it. Disaggregation transfers the KV cache produced by prefill across the interconnect to the decode GPUs, which costs bandwidth and adds latency that grows with context length, and it requires the operator to provision two separate GPU pools whose ratio must be re-tuned whenever the workload's prefill-to-decode balance shifts. On a single device the two phases still share no compute, because they live on different devices; the compute that decode cannot use on a decode GPU remains idle there, and the prefill GPUs are starved of the memory-bandwidth-bound work that would have filled their slack. Disaggregation answers the interference question but reintroduces the under-utilization it was meant to fix, now spread across two device pools and a network link.

1.5 The Fundamental Obstacle: SM Demand Varies and the Schedule Is Online

The reason a fixed fix does not exist is that the right split of SMs between prefill and decode is not a constant — it depends on quantities that are known only at runtime. The number of SMs at which prefill stops gaining speed, and the point at which decode saturates memory bandwidth, both depend on the model, the layer, the current batch size, and the context length, all of which change continuously as requests arrive and complete. A static partition that reserves, for instance, two-thirds of the SMs for prefill is correct only for the workload mix it was tuned on, and becomes wrong the moment the prefill-to-decode ratio shifts. Determining the correct split online requires predicting how long a phase will take on a given number of SMs before that phase has run, which is a performance-modeling problem under contention rather than a measurement that can be read off a profiler after the fact. The design space therefore reduces to a system that estimates per-phase latency as a function of SM count in real time and reallocates SMs each step, and that estimator must be cheap enough to run inside the serving loop. Bullet's architecture is organized entirely around supplying this online estimate and acting on it.

1.6 Position vs Immediate Prior Work

Bullet sits among four families of recent serving work, each of which improved on the chunked-prefill baseline along one axis but left the SM-level co-execution problem open. The table pairs each predecessor with the dimension it advanced and the structural gap it did not close.

2. Contributions and Headline Numbers

With the problem and its obstacle established, Bullet's contributions can be stated as four coordinated components. Each addresses one requirement of online SM provisioning: predicting per-phase latency, deciding the split, enforcing it on hardware, and running the two phases without serializing them.

SM-Scaling Roofline Model

A roofline model that predicts a kernel's latency as a function of the number of SMs allocated to it, calibrated from a small number of profiled samples and accounting for wave quantization. It supplies the per-phase latency estimate the scheduler needs before a phase runs.

SLO-Aware Scheduling

A scheduler that reads the model's latency estimates and reallocates SMs each step to satisfy both the TTFT target for prefill and the TPOT target for decode, prioritizing prefill only insofar as decode's SLO permits.

SM Masking via libsmctrl

Hardware enforcement of the split using a CUDA-stream SM mask, which restricts every kernel on a stream to a chosen SM subset with microsecond-level reconfiguration cost and no extra memory.

Concurrent Execution Engine

Separate prefill and decode processes that share GPU weights and KV cache through a single address space, so a completed prefill migrates to decode by passing metadata only, with no KV-cache copy.

Across ShareGPT, Azure-Code, and arXiv-Summary workloads on A100, H100, and H20 hardware, Bullet reports a 1.26x average throughput gain (up to 1.55x) over vLLM, SGLang, and NanoFlow while meeting the latency targets; the baseline counterparts of these gains are developed in the results section, where the device under Bullet sustains 86.2% active SM cycles against a lower figure for SGLang.

3. Architecture: One Device, Two Engines, Two SM Slices

Bullet's architecture realizes the online-provisioning requirement from Section 1.5 with a deliberately decentralized layout. The prefill phase and the decode phase each run in their own operating-system process with their own CUDA stream, and the two streams are pinned to disjoint subsets of the GPU's SMs. Both processes map the same model weights and the same KV-cache memory into their address spaces, so the partition is purely a compute partition: the data is shared, only the streaming multiprocessors are divided. A scheduler observes the system state each step, consults the SM-scaling roofline model for the latency each phase would incur on a candidate SM split, and issues a new mask through libsmctrl when the split should change. The result is a system that behaves like disaggregation in its freedom from interference but like a single shared device in its memory economy.

Architectural insight: The decision to share memory while dividing compute is what makes Bullet distinct from disaggregation. Because both engines address one copy of the weights and KV cache, the only thing that crosses the prefill-to-decode boundary when a request finishes prefilling is a small metadata record, not the KV cache itself. The expensive transfer that disaggregation must pay over an interconnect is therefore eliminated, and the compute that decode cannot use becomes available to prefill on the same chip rather than stranded on a different one.

Bullet's four components form a control loop: the roofline model turns a candidate SM split into a latency prediction, the scheduler turns latency predictions and SLO targets into a chosen split, the masking layer turns the chosen split into a hardware constraint, and the execution engine turns the constraint into two concurrently running phases. 4.1 The SM-Scaling Roofline Model

The classical roofline model bounds a kernel's achievable performance by the smaller of two ceilings — peak compute and peak memory bandwidth — chosen according to the kernel's arithmetic intensity. Bullet's contribution is to make both ceilings depend on the number of SMs allocated to the kernel rather than treating the whole GPU as the unit of resource. A kernel running on a fraction of the SMs sees a proportionally lower compute ceiling and, up to a saturation point, a lower memory-bandwidth ceiling; the model captures this so the scheduler can ask what a phase would cost on any candidate slice. The plain idea is a roofline whose roof slides down as fewer SMs are granted.

Prefill (compute-bound)

scales with SMs
Adding SMs raises the compute ceiling almost linearly, so prefill keeps speeding up as its slice grows.

Decode (memory-bound)

saturates early
Bandwidth saturates at an inflection point $N_d$; beyond it, extra SMs give decode no further speedup and are better given to prefill.

Formally, let $N$ be the total number of SMs on the device and $N_p$ the number allocated to a kernel. The model scales the peak compute throughput $C_{peak}$ linearly with the SM fraction, while the attainable memory bandwidth $D_{peak}$ rises with the SM fraction only until it reaches the saturation point $N_d$, after which it is capped. These two SM-dependent ceilings are written as follows.

(1) $$C_p = C_{peak} \cdot \frac{N_p}{N}, \qquad D_p = D_{peak} \cdot \min\!\left(1, \frac{N_p}{N_d}\right)$$

Given these ceilings, a kernel's estimated latency on $N_p$ SMs follows from its FLOP count $flop_k$ and its memory-traffic count $mem_k$. The kernel's arithmetic intensity $flop_k / mem_k$ selects whether it is bounded by the sliding compute roof $C_p$ or the sliding bandwidth roof $D_p$; the achievable rate is the smaller of the two, and the latency is the work divided by that rate.

(2) $$T'_{k,p} = flop_k \cdot \min\!\left(\frac{flop_k}{mem_k} \cdot D_p,\; C_p\right)^{-1}$$

4.1.1 Wave Quantization

The idealized rate in Equation (2) is optimistic because GPU kernels execute in waves: thread blocks are assigned to SMs in rounds, and when the block count does not divide evenly across the SMs, the final wave occupies only some of them while the rest stall. Bullet models this loss explicitly so that the latency estimate reflects the partly empty machine the final wave runs on, rather than assuming every SM is busy for the whole kernel.

Let $g$ be the total number of thread blocks the kernel launches and $b$ the number of blocks an SM can hold concurrently. The kernel then runs in $w = \lceil g / (b \cdot N) \rceil$ waves, and the final wave occupies $tail = \lceil g/b - N\cdot(w-1) \rceil$ active SMs. The fraction of SM-cycles wasted to the partly filled final wave is then expressed below.

(3) $$idle = \frac{N - tail}{N \cdot w}$$

The waste is largest when $w$ is small, that is, for kernels with few waves where one partly filled wave is a large share of the total, which is precisely the small-batch decode regime the scheduler cares about. Accounting for this term is what lets the model recommend, for example, allocating decode a number of SMs that divides its block count evenly rather than a larger number that leaves a near-empty tail wave.

4.1.2 Calibration From a Handful of Samples

The analytic ceilings predict the shape of the latency-versus-SM curve but not its exact height, because real kernels fall short of the theoretical roofs by a model-and-kernel-specific factor. Bullet closes this gap with a small calibration step rather than an exhaustive profiling sweep.

For an execution state $ES$, the system measures the true latency $T^{measured}_{p,ES}$ at one or two SM settings and divides it by the model's theoretical prediction $T'^{theoretical}_{p,ES}$ to obtain a scaling factor that corrects the curve at every other SM count by linear interpolation.

(4) $$\alpha_{p,ES} = \frac{T^{measured}_{p,ES}}{T'^{theoretical}_{p,ES}}$$

The payoff of this calibration is that the model reaches usable accuracy from very few measurements. The paper reports that with only two samples the decode latency curve is already well calibrated, that an 18-sample decode profile reaches 9.1% mean absolute relative error, and that expanding to 30 samples reduces the error to 5.3%; over a full sweep of 7,360 profiled configurations with context length up to 16k and batch size up to 128, the decode model's mean absolute relative error is 10.5%. An estimator this cheap can run inside the per-step scheduling loop, which is the property Section 1.5 identified as essential.

4.2 SLO-Aware Scheduling

The scheduler is the component that turns latency predictions into an SM allocation, once per step, under two service-level objectives: a time-to-first-token (TTFT) target $\Gamma_p$ that bounds how long a prompt may wait for its first output, and a time-per-output-token (TPOT) target $\Gamma_d$ that bounds the per-token latency of decode. The scheduler reads the system state, estimates the latency each phase would incur on a candidate split using the roofline model, and chooses the split. Its guiding principle is to prioritize prefill as far as the decode SLO allows, because a shorter prefill latency admits requests into decode sooner and thereby enlarges the decode batch, which in turn raises decode efficiency.

The decision rule reduces to three cases keyed on whether each SLO is currently being met. The pseudocode below sketches the per-step logic; it is a faithful condensation of the paper's Algorithm 1 rather than the system's source, and the engine-specific calls are named only where the algorithm names them.

# Per-step SM provisioning (condensed from Algorithm 1)
def provision_sms(state):
    ttft, tpot = predict_latency(state)   # via SM-scaling roofline model
    if ttft <= GAMMA_p and tpot <= GAMMA_d:
        # both SLOs met: shrink decode, give freed SMs to prefill
        shift_sms(frm="decode", to="prefill")
    elif ttft > GAMMA_p and tpot <= GAMMA_d:
        # TTFT at risk, decode has slack: suspend decode, maximize prefill
        suspend_decode(); maximize_prefill_sms()
    else:
        # neither comfortably achievable: balance both phases
        set_balanced_sm()

The first branch is the steady state under light load: both targets hold, so the scheduler reclaims SMs from decode — which gains nothing past its saturation point — and gives them to prefill, raising throughput at no cost to latency. The second branch handles a burst of arrivals that threatens TTFT while decode still has headroom; the scheduler temporarily suspends decode and pushes the SM allocation toward prefill to clear the prompt backlog. The third branch, invoked when neither objective is comfortably reachable, calls a balancing routine that divides SMs so that both phases degrade gracefully rather than letting one SLO fail outright. Because each branch is selected from cheap latency predictions, the whole decision costs microseconds and runs every step.

Scheduling subtlety: The asymmetry between the two phases is what makes the policy work. Decode gains nothing from SMs beyond its bandwidth-saturation point, so handing those SMs to prefill is close to free; prefill, being compute-bound, converts every SM it receives into a shorter TTFT. The scheduler therefore treats decode's saturation point as the natural reservation floor and lets prefill absorb the remainder, falling back to balancing only when the prefill demand is so heavy that even decode's reserved floor cannot be left intact.

4.3 SM Masking via libsmctrl

A scheduling decision is only useful if the hardware actually confines each engine to its assigned SMs. NVIDIA's GPUs do not expose a public API for restricting a kernel to a chosen subset of SMs, so a partition that exists only in the scheduler's intent would be ignored by the hardware block scheduler, which is free to place any thread block on any idle SM. Bullet enforces the partition with libsmctrl, a research library that writes an SM-mask into the metadata of a CUDA stream so that every kernel subsequently launched on that stream is confined to the masked SM subset.

The mechanism is a single call that associates a mask with a stream. Because the prefill engine and the decode engine each own a stream, masking the two streams to complementary SM subsets is exactly the spatial partition the scheduler computed. The call below is the operation Bullet invokes whenever the scheduler decides the split should change.

// libsmctrl: confine every kernel on `stream` to the chosen SM subset
libsmctrl_set_stream_mask(stream, sm_subset);

// Bullet usage: complementary masks for the two engines
libsmctrl_set_stream_mask(prefill_stream, prefill_sms);
libsmctrl_set_stream_mask(decode_stream,  decode_sms);

What makes this practical for a per-step scheduler is its cost profile. Setting a stream mask is a metadata write rather than a kernel relaunch or a context reconfiguration, so it incurs no extra GPU memory and its mean reconfiguration latency is about 4.1 microseconds, as the paper's microbenchmark in Table 5 reports. A reconfiguration this cheap can be issued every step without perceptibly disturbing the GPU pipeline, which is why the scheduler is free to move the prefill-decode boundary as often as the workload demands rather than committing to a static split. The library does require CUDA 12.6 or earlier, a constraint that the reproduction section returns to.

4.4 Concurrent Execution Engine

The final component is the runtime that lets the two masked streams make progress at the same time without serializing on shared state. Bullet runs prefill and decode as separate processes so that their CPU-side control flow does not contend on a single Python interpreter, and it gives the two processes a shared view of the GPU so that no data has to move between them. The engine's job is to keep the CPU control flow and the GPU execution asynchronous on both sides, so that neither the scheduler's decisions nor a request migration ever stalls a running kernel.

4.4.1 Shared Address Space, Metadata-Only Migration

The two engines need to operate on the same model weights and the same KV cache, but they live in different processes. Bullet bridges them with CUDA's inter-process memory-handle API, which lets one process export a GPU allocation and another import it into its own address space. The result is that the weights and the paged KV cache exist once in GPU memory and are visible to both engines, so when a request finishes prefilling, its KV-cache blocks are already where the decode engine can read them.

# Export the KV-cache / weight allocation from the prefill process
handle = cuda.cudaIpcGetMemHandle(kv_cache_ptr)

# Import it into the decode process; same physical GPU memory, no copy
kv_cache_ptr = cuda.cudaIpcOpenMemHandle(handle, cuda.cudaIpcMemLazyEnablePeerAccess)

With the data already shared, migrating a request from prefill to decode reduces to transferring a metadata record — which KV-cache blocks belong to the request, and its decoding position — rather than the cache contents themselves. Bullet sends this record asynchronously over a ZeroMQ channel, so the prefill engine does not block on the hand-off and the migration overhead stays at the microsecond level. This is the concrete payoff of sharing memory: the KV-cache transfer that prefill-decode disaggregation must pay over an interconnect simply does not occur here.

4.4.2 Layer-Wise Prefill, Step-Wise Decode Graphs

The two engines launch their work in deliberately different units because their control needs differ. The prefill engine issues a fixed group of layers per step and then synchronizes, which gives the CPU a frequent opportunity to re-decide the SM split as a long prompt advances through the network; this layer-wise granularity is what lets the scheduler react within a single prefill rather than waiting for it to finish. The decode engine, by contrast, issues an entire decode step as one CUDA Graph, collapsing the many small kernels of a decode step into a single launch so that the per-kernel launch overhead — which is significant for the small kernels of memory-bound decode — is paid once rather than once per kernel.

Figure 12 (from paper): Concurrent execution engine with shared KV-cache and weight GPU address spaces. The prefill and decode processes map the same GPU memory, exchange execution state through an OS-managed shared buffer with compact control bits, and migrate finished requests by metadata over ZeroMQ rather than by copying the cache.

The two processes coordinate through a small OS-managed shared-memory buffer that carries compact control bits indicating data availability, so each side can proceed as soon as the other has produced what it needs without a heavyweight synchronization primitive. The combined effect of the shared address space, the asynchronous metadata migration, and the differentiated launch granularity is that the prefill and decode kernels genuinely overlap on their respective SM slices, which is the behavior the architecture promised and the source of the utilization gains reported next.

5. Performance Results

Bullet is evaluated against vLLM v0.8.5 (1024-token chunk), SGLang v0.4.6 (1024- and 2048-token chunks), and NanoFlow, across three workloads with Poisson arrivals — ShareGPT conversational traffic, the Azure-Code production code-completion trace, and an arXiv-Summary long-context task — on four hardware testbeds: a single A100, 8×A100-80GB, 8×H100, and 8×H20, all on CUDA 12.4 with tensor parallelism for the multi-GPU runs. The headline claim is a 1.26x average throughput gain, up to 1.55x, while meeting the latency SLOs; the numbers below trace where that gain comes from and where it is largest.

5.2 Where the Gain Comes From: Device Utilization

The throughput and latency numbers are downstream of a single mechanism: the device spends more of every step doing useful work. A timeline analysis of the ShareGPT workload shows that under Bullet the GPU sustains 86.2% active SM cycles, 11.2 percentage points above SGLang, with Tensor Core utilization 11.8% higher and memory-bandwidth utilization 19.3% higher. These three numbers are the direct expression of the design goal — prefill driving the tensor cores while decode drives the memory subsystem, on disjoint SMs, at the same time — and they explain why the throughput gain holds without a latency penalty.

5.3 Ablation: Partitioning and Scheduling Are Both Necessary

An ablation isolates the two halves of the design — the spatial SM partitioning and the SLO-aware scheduling — by disabling each in turn. The paper reports that resource partitioning alone, without the scheduler that resizes the split each step, does not achieve balanced performance, and that scheduling alone, without the hardware partition to enforce its decisions, fares no better. Only the complete design, combining the partition with the per-step scheduler that resizes it, achieves balanced latency across all three workloads. This confirms that the contribution is the closed control loop rather than either of its parts in isolation: the model and scheduler are ineffective without a way to enforce the split, and the masking is ineffective without a policy to decide what to enforce.

Caveats on reading these numbers: The largest reported speedups attach to the most adversarial baseline configuration — a large MoE model on H20 where vLLM's chunked-prefill schedule is least suited to the workload — so the 17.7x mean-latency reduction characterizes that specific configuration rather than a typical deployment. The aggregate 1.26x throughput figure is the more representative headline, and the single-GPU dense gain of 1.09x sets the lower end. The roofline model's 10.5% decode error is a mean over thousands of configurations; individual predictions, particularly in the small-wave regime where quantization dominates, will deviate further, and the scheduler's balancing branch exists precisely to tolerate that prediction error.

6. Claims vs Implementation

The authors released the system as the BulletServe repository under an Apache-2.0 license. Inspecting the repository confirms that the system is built as a fork of SGLang rather than vLLM — the tree contains sgl-kernel, sgl-router, and sgl-pdlb components alongside a python package, and the server is launched through sglang.launch_server with an added --enable-bullet-engine flag. The libsmctrl source is vendored under csrc and built separately. The repository substantiates the system-level claims — the masking library, the concurrent engine, and the launch path are all present and documented — while the quantitative claims are reproducible only with additional configuration that the README does not fully script. The following two columns summarize the strengths the artifact demonstrates and the limitations a prospective adopter should weigh.

Strengths

  • Open-source under Apache-2.0, built on the widely deployed SGLang runtime, lowering adoption cost for existing SGLang users.
  • The masking enforcement carries microsecond-level reconfiguration cost and no extra GPU memory, so the partition can be re-sized every step.
  • Memory sharing removes the KV-cache transfer that disaggregation incurs, keeping the design within a single device's memory budget.
  • Validated across dense and MoE models and three GPU generations, indicating the approach is not tied to one hardware target.

Limitations

  • libsmctrl pins the system to CUDA 12.6 or earlier; a newer driver or toolkit cannot run the masking layer without a library update.
  • Spatial sharing depends on NVIDIA MPS being enabled, which adds an operational prerequisite and its own failure modes.
  • The roofline model is calibrated per GPU generation; moving to an unprofiled device requires re-collecting calibration samples rather than reusing a closed-form predictor.
  • The headline 17.7× latency figure is configuration-specific; reproducing the full result set requires request-rate and SLO settings not fully scripted in the public README.

7. How to Reproduce

The repository documents a three-stage setup: building the vendored libsmctrl library, installing the Bullet package into a fresh Python environment, and launching the server with MPS enabled. The commands below are reproduced from the project README and should be read as the documented happy path rather than a guarantee that they run unchanged on an arbitrary machine; the hardware and version constraints in the warning box apply throughout.

Hardware and version prerequisites: An NVIDIA GPU with the SM counts the paper assumes (A100 with 108 SMs, H100 with 132, or H20 with 78); CUDA 12.6 or earlier, required by libsmctrl; Python 3.12.9 or newer, strongly recommended by the authors; and NVIDIA MPS, which Bullet relies on for spatial sharing between the prefill and decode instances. A newer CUDA toolkit will not build libsmctrl, and multi-GPU experiments additionally require the tensor-parallel interconnect used in the paper.

7.1 Build libsmctrl and Install Bullet

The masking layer is compiled first because the Python package links against it. The adapted libsmctrl source ships under csrc, and the project is then installed editable into a Python 3.12.9 environment created with conda or uv. The two blocks below cover the library build and the package install in turn.

# 1. Build the vendored libsmctrl SM-masking library
git clone https://github.com/zejia-lin/Bullet.git
cd Bullet/csrc
make config
make build

With the library built, the second block creates an isolated environment and installs Bullet with all optional dependencies. Either conda or uv works; the conda path is shown, and the uv equivalent is documented in the README.

# 2. Create the environment and install Bullet (conda path)
conda create -n bullet python==3.12.9
conda activate bullet
pip install -e "python[all]"

The editable install keeps the working tree as the live source, which is convenient for inspecting the scheduler and roofline-model logic in the python package while a server is running. The install pulls the SGLang-derived runtime, since Bullet is implemented as an extension to SGLang rather than a standalone stack.

7.2 Start MPS and Launch the Server

Spatial sharing between the prefill and decode instances depends on NVIDIA MPS, so the daemon is started with the provided script before the server. The server is then launched through SGLang's entry point with the radix cache disabled and the Bullet engine enabled; the radix cache is disabled because Bullet manages the KV cache through its shared-address-space engine rather than SGLang's prefix tree.

# Start NVIDIA MPS (required for GPU spatial sharing)
bash ./scripts/start_mps.sh

# Launch the Bullet-enabled server
python -m sglang.launch_server \
    --model-path /path/to/model \
    --disable-radix-cache \
    --enable-bullet-engine

Once the server is accepting requests, the evaluation uses SGLang's built-in benchmark driver to replay a workload at a chosen request rate. The block below runs the ShareGPT trace at ten requests per second against the local server; swapping the dataset name and path reproduces the Azure-Code and arXiv-Summary configurations the paper reports.

# Replay a workload and measure TTFT / TPOT / throughput
python ./python/sglang/bench_serving.py \
    --backend sglang \
    --dataset-name sharegpt \
    --num-prompts 1000 \
    --host 127.0.0.1 --port 30000 \
    --model /path/to/model \
    --dataset-path /path/to/sharegpt/dataset \
    --request-rate 10

The benchmark driver emits the TTFT, TPOT, and throughput series that populate the per-workload figures; sweeping --request-rate across a range and recording SLO attainment at each point reconstructs the curves of Figure 14. When the experiments are finished, the companion script kill_mps.sh stops the MPS daemon to release the GPU. Reproducing the exact figures additionally requires the SLO thresholds from the paper's Table 4, which set the TTFT and TPOT targets the scheduler reads as $\Gamma_p$ and $\Gamma_d$.
