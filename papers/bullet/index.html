GPU partitioning for prefill/decode interference

Bullet: Spatial-Temporal GPU Sharing for LLM Serving

Concurrent prefill and decode on one GPU by allocating SM resources over time.

Authors Zejia Lin, Hongxin Xu, Guanyi Chen, Zhiguang Chen, Yutong Lu, Xianwei Zhang
Affiliation Sun Yat-sen University
Venue and version ASPLOS 2026, arXiv 2504.19516v4
Page scope Spatial GPU sharing, predictor-driven scheduling, and SGLang implementation path

Core Question

Bullet asks whether prefill and decode must take turns on a GPU. Its answer is to split the GPU spatially so compute-heavy prefill and bandwidth-heavy decode can run together under a scheduler that changes the split as the workload changes.

The important distinction is between overlap as a batching illusion and overlap as an enforced resource partition. Bullet implements the latter through SM/TPC masking, shared prefill/decode state, and a latency predictor that estimates each phase under partial GPU allocation.

Motivation Ladder

The motivation chain is a conflict between two SLOs: TTFT wants prefill progress, while TPOT wants decode not to be blocked. Bullet’s design follows from refusing to protect either metric only by shrinking the other phase.

The six stages move from that conflict to the implementation constraint: once prefill and decode run concurrently, the system must predict cost, enforce a partition, and keep memory state coherent across two workers.

1

Why now

LLM serving traffic now mixes long prompts, long generations, and strict token latency targets on the same accelerator fleet. The paper observes that prefill is mostly compute bound while decode is often memory bound, so a single static batching policy leaves one resource dimension idle while protecting another.

This makes GPU sharing a first-order serving problem: the system must reason about prefill and decode at the same time instead of choosing one fixed batch shape.

2

Concrete bad scenario

A batch of long prompts arrives while many users are already waiting for decode tokens. If the system sends the prefill work as large chunks, decode pauses and TPOT violates the service target; if the system cuts prefill into small chunks, kernel efficiency drops and TTFT stretches.

The scenario explains why TTFT and TPOT cannot be optimized independently. A scheduler that protects one metric by shrinking the other phase can still waste GPU capacity.

3

Baseline pain

Chunked prefill and hybrid batching serialize phases at the batch level, so they approximate sharing by time slicing. The paper reports that smaller chunks reduce attention efficiency, and that the final chunk can take 1.9 times the latency of the first chunk because it attends to a longer context.

That baseline behavior motivates Bullet's spatial split: preserve larger prefill work units while letting decode continue with its own resource slice.

4

Strawman

A fixed SM split between prefill and decode looks attractive because the two phases use different bottlenecks. The problem is that request mix, sequence length, layer progress, and queue pressure change continuously, so the fixed split can starve either phase.

The strawman fails because SM demand changes across layers and request mix. Bullet therefore needs a runtime decision loop instead of a static partition.

5

Fundamental obstacle

The hard part is not only launching two CUDA streams. The serving engine needs a latency predictor that understands partial SM allocation, a scheduler that respects TTFT and TPOT, and memory sharing across separate prefill and decode processes.

The obstacle links three mechanisms that must agree: latency prediction, SM masking, and shared state between prefill and decode workers.

6

Position against nearby systems

vLLM, SGLang, and Nanoflow improve batching and disaggregation, but they still make prefill and decode contend through coarse scheduling decisions. Bullet instead treats one GPU as a spatially partitioned device and revises that partition as the workload evolves.

This position clarifies why the paper is not just another batching policy. Its claim depends on enforcing spatial isolation inside a single GPU.

Paper Snapshot

The main numbers describe a serving regime where phase overlap improves both latency and utilization. The reported 1.26x average throughput gain is not a generic batching result; it comes from exploiting complementary resource pressure between prefill and decode.

Claim Boundaries

Bullet’s numbers apply when enough prefill and decode pressure coexist to benefit from spatial sharing. If traffic is dominated by a single phase, the extra scheduler and predictor have less room to pay off.

The portability boundary is also concrete. The design depends on CUDA/MPS-style stream control and SM/TPC masking, so it is not a pure framework-level optimization that automatically transfers to every accelerator stack.

System Map

The system map is a closed loop: measure queue and phase state, predict the latency of candidate splits, apply stream masks, and feed observed timing back into later decisions.

The fragile boundary is between policy and enforcement. A scheduler can decide an SM split, but Bullet becomes a system only when that decision reaches streams, shared memory metadata, and separate prefill/decode workers.

Mechanism Deep Dive

Bullet decomposes into a predictor, a controller, and shared state. The predictor estimates phase cost under partial SM allocation; the controller applies masks; the shared manager coordinates the two serving processes.

The design is not simply “run prefill and decode together.” It is a control loop that chooses how much GPU each phase receives, enforces the choice, and updates it before workload drift becomes interference.

SM-scaling roofline model

Bullet extends roofline reasoning with the number of allocated SMs and with attention-specific memory behavior. The model is used online, so its purpose is scheduling accuracy rather than offline postmortem explanation.

SLO-aware scheduler

The scheduler separates TTFT and TPOT pressure and uses normalized service targets to decide when prefill can take more of the device. This keeps decode latency visible while still allowing large prefill bursts when slack exists.

libsmctrl enforcement

The codebase wraps libsmctrl and sets stream masks over TPC ranges, including a reversed range option for decode. This confirms that the implementation uses explicit hardware partitioning rather than only software queue priority.

Process-level phase separation

The public code keeps Bullet-specific request RPC, shared arrays, memory-pool RPC, and separate prefill/decode roles inside SGLang. That structure matches the paper’s claim that engines execute autonomously while sharing device state.

Interaction Among Pieces

The mechanism is useful only when all three layers close the loop: the predictor estimates phase cost, the controller translates that estimate into a TPC mask, and shared state keeps both engines synchronized.

If any layer is removed, the system falls back to a weaker idea: batching without partitioning, partitioning without SLO awareness, or two engines racing without a consistent queue view.

Implementation Trace

The Bullet fork exposes the mechanism through SGLang server flags and worker paths. `--enable-bullet-engine`, scheduler toggles, fixed TPC controls, and predictor-path arguments turn the design into runtime behavior.

The code path mirrors the paper’s split between policy and enforcement: `shared_mng.py` maintains cross-phase state, `sm_controller.py` applies masks, and worker code routes forward passes through Bullet timing and stream control.

  • `python/sglang/srt/server_args.py` exposes `--enable-bullet-engine`, `--enable-bullet-scheduler`, `--enable-sm-partition`, fixed TPC settings, and predictor-path arguments.
  • `python/sglang/srt/bullet/shared_mng.py` stores shared prefill/decode state and calls a predictor library for adaptive TPC allocation.
  • `python/sglang/srt/bullet/sm_controller.py` loads libsmctrl and applies stream masks to selected TPC ranges.
  • `python/sglang/srt/managers/tp_worker.py` routes model forward through a Bullet stream and records predictor/timing entries around each forward step.

Prototype Boundary

The public implementation supports the architectural claim but does not make Bullet a drop-in production SGLang replacement. The README frames it as a research fork, and feature parity is outside the claim.

Reproducing the headline numbers still requires the same GPU generation, MPS behavior, workloads, predictor calibration, and measurement setup. The implementation shows mechanism; the evaluation measures one regime.

Evaluation Reading

The evaluation asks whether spatial sharing improves throughput without sacrificing token latency. Throughput, TTFT, TPOT, and active-SM counters must be read together; any one alone leaves a loophole.

The strongest comparison is against chunked prefill. Chunking protects decode by reducing prefill granularity; Bullet tries to preserve prefill efficiency by using a spatial rather than temporal split.

Evaluation Discipline

Bullet’s evaluation should be read across latency and hardware counters together. Throughput gains without TTFT/TPOT protection would not prove the spatial split works.

The chunked-prefill baseline is the key comparison because it protects decode temporally; Bullet’s claim is that spatial sharing can protect decode while preserving larger prefill progress.

Limitations and Failure Modes

Bullet’s limits follow directly from its mechanism. A system that relies on GPU partition control is sensitive to driver support, GPU architecture, and predictor accuracy under contention.

The design is most compelling when prefill and decode have complementary bottlenecks at the same time. Mostly-prefill or mostly-decode traffic leaves the partition with less leverage.

Hardware dependency

Bullet depends on MPS and libsmctrl-style SM/TPC masking, so portability follows GPU driver and architecture support rather than a pure framework abstraction.

Predictor calibration

The scheduler is only as strong as the latency estimator under the target model, context distribution, and contention regime.

Feature parity

The GitHub README states that Bullet is a research prototype forked from SGLang and does not have complete feature parity with open-source SGLang.

Takeaways

The main lesson is that LLM serving has phase-level resource structure that ordinary batching hides. Bullet turns that structure into a GPU partitioning policy.

The implementation cost is part of the result: scheduler policy, predictor calibration, and low-level enforcement must agree. A description that only says “overlap prefill and decode” misses the hard part.

  • Treat prefill and decode as complementary phases, not only as queue entries.
  • A working design needs enforcement, prediction, and shared serving state at the same time.
  • Bullet’s largest lesson is that phase overlap is a resource allocation problem, not only a batching problem.

Bottom Line

Bullet’s contribution is to make phase coexistence explicit: prefill and decode become simultaneous tenants of one GPU, with SMs allocated between them by a runtime loop.

Its limitation is equally clear: the control loop is only as good as the predictor and the GPU mechanisms that enforce the partition.

Best use case

Mixed prefill/decode pressure where static batching leaves compute or bandwidth underused.

Main risk

Predictor error or unsupported partition enforcement can turn overlap into interference.
