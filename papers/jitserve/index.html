JITServe

SLO-aware LLM Serving with Imprecise Request Information — just-in-time bandwidth allocation for diverse SLO classes (latency-sensitive, deadline-sensitive, compound)

arXiv:2504.20068 v3 · Dec 2025 SLO-aware Scheduling Service Goodput vLLM-based

Wei Zhang, Zhiyu Wu, Yi Mu, Rui Ning, Banruo Liu, Nikhil Sarda, Myungjin Lee, Fan Lai

University of Illinois Urbana-Champaign · Cisco Research · Google

1. Overview & Core Insight

Modern LLM serving stacks (vLLM, Sarathi-Serve, DistServe, Autellix) optimize one aggregate metric — usually average latency or throughput — under the assumption that all requests share a single SLO. JITServe's measurement of millions of real production requests plus 550+ user surveys finds the opposite: requests bring three fundamentally different SLO classes, and a real workload mixes all three at once.

1.1 Why now? — what changed in 2024–2025

Through 2023, production LLM serving was overwhelmingly single-class chatbot streaming — vLLM's FCFS scheduler with paged attention was sufficient. Two shifts in 2024–2025 broke that assumption simultaneously: (a) agentic frameworks (MetaGPT, deep research, GAIA, AutoGen) issue tens to hundreds of inter-dependent calls per program under a single end-to-end deadline, and (b) LLM-as-tool patterns (RAG ingestion, batch summarization APIs, AIOps) need full responses by hard deadlines, not streaming. JITServe's measurement across six organizations, over 550 LLM users, and millions of requests — sourced from LMSys Chatbot Arena, WildChat, MetaGPT, GAIA, and deep-research traces — confirms what every SaaS LLM provider now sees: a single SLO no longer exists in the same queue. Three SLO classes coexist; any single-objective scheduler now violates someone's contract on every batch.

1.2 What earlier serving systems left on the table

Each of the immediate prior generation solved one piece of the puzzle and left the rest exposed. JITServe argues that combining their solutions does not work — the assumptions are mutually inconsistent.

System (year) What it solved What it left on the table
vLLM (SOSP'23) High-throughput single-class serving via PagedAttention Assumes one SLO; FCFS HOL-blocks compound jobs
Sarathi-Serve (OSDI'24) Decode-prefill interleaving via chunked-prefill Throughput-optimal; chunk size is global, not per-SLO-class

None of these handles three coexisting SLO classes simultaneously — and on a real workload, they coexist by default.

2.2 Type B — Deadline-Sensitive

2.3 Type C — Compound (the agentic case)

A deep-research agent answers “build me a market analysis of company X” by issuing 12 inter-dependent calls (planner LLM → web search → reader LLM → reflector LLM → writer LLM → ...) under a single 240-second program deadline. Per-call latency is irrelevant; only the program deadline matters. A 7-second wait on the planner directly steals from the budget of the remaining 11 calls — and a single straggler at any stage cascades into a missed program. Per-stage SJF (Autellix's PLAS) does not see this dependency: it can starve the critical-path planner while greedily completing a downstream summarization.

3. Why State-of-the-Art Schedulers Fail

The motivation experiments hold workload composition steady but increase request diversity (mix of the three SLO classes). Every existing policy degrades — most by 4×–10× — once the workload is no longer monolithic.

A concrete failure trace — what FCFS does to a mixed workload

Before the figure, here is the same effect at the granularity of a single second of queue. Suppose at $t=0$ the queue receives, in arrival order: 50 streaming chats (TTFT SLO 2s, TBT SLO 100ms), 5 batch summary jobs (E2EL SLO 20s), and 2 deep-research agents (each 12 stages, program SLO $20s \times 12 = 240s$). All three classes are within the design space of vLLM today.

t = 0s: queue accepts 57 mixed-class requests 50 chat + 5 batch + 2 agent. FCFS sorts purely by arrival time; the SLO class metadata sits unused.
↓
t = 2s: 47 chats already breached A long batch summary at the head of the queue is mid-decode. The 47 chats behind it cannot stream a first token in time — TTFT SLO is breached for all of them. Both agents' planner-stage calls are still queued.
↓
t = 15s: agent#1 is mathematically late Agent#1 enters stage 4 of 12. Remaining program budget is $240 - 15 = 225$s, but the predicted cost of the 9 remaining stages exceeds that. The program is already destined to miss. FCFS continues to allocate decode bandwidth to it for ~225s — every token spent here is a token stolen from a request that could still meet its SLO.
↓
t = 240s: cascade. Two SLO classes destroyed. Both agents miss their program deadlines. The 50 chats lost first-token guarantees long ago. The 5 batch jobs — the only class FCFS prioritized correctly — meet deadlines, but at the cost of capacity that should have served everyone else. Net goodput: one SLO class honored, two destroyed. Critically, no parameter tuning of FCFS can fix this — the policy itself ignores SLO class.

3.2 Why the obvious fixes don't work

A practitioner reading this far is likely thinking "why not just patch X into vLLM?" The two most common Xs are per-class queues and better length prediction. Both fail for structural reasons, not implementation gaps — which is why the paper has to design something different rather than tuning.

Strawman 1 — three queues, one per SLO class

Capacity must be split a priori. If 80% of an hour's arrivals are compound, the latency queue idles while compound burns hot. Worse, deadlines age: a compound request that began with 60s slack now has 5s — at what point does it migrate to a higher-priority emergency queue? Per-second rebalancing across queues is the original scheduling problem in disguise.

Strawman 2 — predict length more accurately, then SJF

The paper's measurement (§2.2) shows that even fine-tuned BERT- and Llama3-based predictors miss heavily at the tails (P5–P95 spread >5× the true length on agent / deep-research workloads, see §3.1 above). Worse, the predictor itself is on the request's critical path: running an 8B-parameter forward pass to estimate one request's output length costs an order of magnitude more than the kernels that would just start producing the response. The cost of being right and the cost of being wrong are roughly the same — there is no Pareto win in this direction. JITServe's answer (§5) is to abandon point estimates: predict a conservative upper bound via a cheap QRF, and refine it as decoded tokens accumulate.

The paper's design starts from accepting these two facts: scheduling cannot be queue-partitioned, and prediction cannot be made cheap-and-accurate. The next subsection catalogs what existing schedulers actually do under these constraints — each one represents a different Pareto choice that fails on at least one SLO class.

3.3 What the existing policies actually do

Each policy below was a reasonable choice for the workload it was originally designed for. None of them is a bad scheduling rule on its own; the failure is that the production workload of 2025 no longer matches the workload these systems were validated on. The table is a quick comparison; the per-policy deep-dives below the table are where the geometric structure of each failure becomes visible. JITServe's evaluation (§6.2) deploys all six against the same trace on the same hardware (16× A100s, 4 LLM families).

Per-policy deep dive — when each was a sensible choice and where it cracks today

FCFS (vLLM default, SOSP'23)

Decision rule: serve requests strictly in arrival order; admission throttled by the paged-attention KV-cache budget; no preemption.

Why it was a fine choice in 2022–2023: production traffic was overwhelmingly chatbot streaming. Most requests had similar output length distribution; arrival order roughly equaled SLO-fairness. Throughput was the only metric anyone tracked, and FCFS gives optimal throughput because there is no priority inversion overhead.

Why it cracks on a 3-class queue: the head of the queue can be a 7-second batch summary while 47 streaming chats wait behind it. The chats' TTFT is breached at $t = 2s$, before FCFS has even looked at them. No FCFS parameter — admission rate, KV-block budget, max batch size — can fix this; the policy itself is structurally SLO-blind. The §3 trace above shows this at the granularity of seconds; in long deployments (paper §6.2) the cascading violations grow over time.

SJF / SRTF (classical)

Decision rule: at each scheduling tick, pick the request with the shortest predicted (or known) remaining response length; preempt longer running requests if a shorter one arrives.

The classical guarantee: SJF is provably optimal for mean response time when lengths are known exactly and the only objective is to minimize mean completion time. This is one of the foundational results of scheduling theory.

Why it cracks on a 3-class queue: two reasons. First, length is not knowable — the paper measures predictor P5–P95 spread >5× the true length on agent and deep-research traces (§3.1 above). Second, even with a perfect oracle, SJF is SLO-blind: a 30-second deadline-sensitive job with 30 seconds of slack is repeatedly bumped by a stream of 1-second chats and ends up missing the deadline. Compound jobs are worst hit because they're long by definition and accumulate slack-loss across stages. Appendix D.1 of the paper proves the competitive ratio is unbounded as workload diversity grows.

LTR (Length-To-Run; QRF / BERT / Llama-3.1 variants)

Decision rule: a learned length predictor (Quantile Regression Forest, fine-tuned BERT, or Llama-3.1-as-oracle) ranks pending requests; the scheduler runs them in shortest-predicted-first order.

Why it was a fine choice for deadline-sensitive workloads: if all jobs are deadline-sensitive and prediction error is bounded, LTR converges toward SJF-with-oracle behavior. The paper notes (§6.3) that LTR is competitive with JITServe on the deadline-sensitive class alone.

Why it cracks on a 3-class queue: LTR is the best baseline in the paper's evaluation (1.3–1.7× behind JITServe, Fig 11) — but it loses on diverse workloads because it oversubscribes bandwidth to deadline-sensitive at the cost of streaming TTFT and compound program-level deadlines. Two structural problems: (1) the predictor itself sits on the request's critical path — running an 8B forward pass to estimate a single request's length costs an order of magnitude more than the kernels that would just start producing the response; (2) per-call length is the wrong target — the binding constraint for compound is the sum across remaining stages, not any single call.

LAS / Autellix PLAS (arXiv'25)

Decision rule: Program-level Least Attained Service — at each tick, give the next slot to the program (top-level request) that has received the smallest total compute so far. Imitates SJF but at program granularity instead of request granularity.

Why it was a fine choice for the agentic-only setting: if every program is a multi-call agent of similar shape, Autellix's LAS-of-programs is fair and approximately minimizes mean program completion time. It was the first system to make scheduling program-aware rather than request-aware.

Why it cracks on a 3-class queue: PLAS is the worst baseline in the paper's evaluation (5.3–6.1× behind JITServe, Fig 11). Per-stage fairness is the wrong proxy for everything except programs of similar shape. A 1-stage streaming chat and a 100-stage deep-research agent receive equal cumulative service — but the chat needs only ~50 tok/s of TBT while the agent needs ~100× more compute total, so neither's SLO is honored: the chat's TBT is starved (PLAS gives it just 1/N of decode bandwidth), and the agent's program deadline is missed (PLAS doesn't see it). PLAS has no notion of streaming TTFT/TBT, no notion of hard deadline, no notion of program-stage criticality.

EDF (earliest deadline first, classical real-time)

Decision rule: at each tick, pick the request whose deadline is closest in absolute time. Liu and Layland (1973) proved EDF is optimal for hard real-time systems.

Why it was a fine choice in real-time scheduling: EDF achieves 100% schedulable utilization on uniprocessors when every job carries an explicit deadline, and is the canonical answer for avionics, industrial control, and similar hard real-time domains.

Why it cracks on a 3-class queue: the assumption breaks. Streaming chats have no deadline at all — they have a TBT bound (per-token rate), which is a fundamentally different SLO shape; you cannot order a chat against a batch summary by ‘deadline’. Compound program deadlines exist but are not directly comparable to per-call deadlines: a 240s program deadline does not become 12× more urgent than a 20s batch deadline just because it expires later. EDF also burns bandwidth on jobs that already would have made it on slack alone, instead of redistributing that capacity to the streaming chats who would have used it at their TBT rate. Appendix D.1 proves an unbounded competitive ratio.

Chunked-prefill (Sarathi-Serve, OSDI'24)

Decision rule: not really a scheduling policy — a pacing technique. Split each request's prefill into chunks and interleave them with decode steps so prefill no longer blocks decode latency. Coupled with FIFO admission for ordering.

Why it was the right answer for streaming chat: Sarathi-Serve's chunked-prefill achieves the lowest TBT of any production system — that's its design objective. For a chatbot-only workload, low TBT translates almost directly into goodput. JITServe's evaluation confirms Sarathi's throughput is essentially optimal: JITServe matches it at 96–98% (Fig 14).

Why it cracks on a 3-class queue: chunk size is a global parameter, not per-SLO-class. A chunk size tuned for streaming chat (say 64 tokens) is too small for a deadline-sensitive batch summary that needs to finish prefill in one shot to land at its E2EL deadline — Sarathi spreads its prefill across many decode steps, inflating TTLT (Time-To-Last-Token) and breaching deadline-sensitive SLOs. The paper's Fig 3 shows Sarathi achieving low TBT but high TTLT violations. JITServe argues this is fundamental: any single chunk size optimizes one class at the expense of another.

Notice the pattern: every policy above is a local optimum. FCFS optimizes against the assumption that arrival order encodes priority. SJF and LTR optimize against the assumption that length is knowable (or at least usefully predictable on the request's critical path). PLAS optimizes against the assumption that program-stage fairness is the right proxy for program deadline. EDF optimizes against the assumption that every job has a deadline. Chunked-prefill optimizes against the assumption that throughput uniformly translates into goodput. None of these five assumptions holds simultaneously on a 2025 production workload — and a single scheduler can satisfy at most one of them at a time. JITServe's design (§4 onward) is built around rejecting all five assumptions and replacing them with a per-request, per-second goodput-margin computation that admits genuine uncertainty rather than trying to engineer it away.

Theorem (informal, Appendix D.1): For each of FCFS, SJF, LAS, EDF, there exists an instance whose competitive ratio against the offline optimum is unbounded as the diversity ratio grows. The proof constructs adversarial mixes of the three SLO classes; the lower bound is matched empirically by the goodput collapse observed in Figure 11 of the paper.

6.2 Pseudocode

# Algorithm 1 — GMAX (one scheduling tick)
def gmax_schedule(active_requests, capacity_C, batch_size_B):
    # 1. compute per-request demand
    for r in active_requests:
        r.b_min      = (r.L_up_hat - r.L_done) / r.delta_t
        r.priority   = r.b_min                      # tighter requests first
        r.margin_gp  = marginal_goodput(r)        # dgoodput / dbandwidth

    # 2. reserve b_min for every reachable request (SLO compliance)
    reachable = [r for r in active_requests
                 if r.delta_t > 0 and r.b_min <= capacity_C]
    reachable.sort(key=lambda r: -r.priority)
    chosen, used = [], 0
    for r in reachable:
        if used + r.b_min <= capacity_C and len(chosen) < batch_size_B:
            chosen.append(r); used += r.b_min

    # 3. distribute SURPLUS by marginal goodput
    surplus = capacity_C - used
    while surplus > 0:
        candidates = [r for r in chosen if r.can_take_more()]
        if not candidates: break
        winner = max(candidates, key=lambda r: r.margin_gp)
        share  = min(surplus, winner.cap_increment())
        winner.bandwidth += share
        surplus          -= share

    # 4. compose a batch of similar input lengths
    return group_by_input_length(chosen)

# conceptual integration with vLLM
class JITServeScheduler(vllm.scheduler.Scheduler):
    def _get_next_batch(self):
        active = self.running + self.waiting
        for r in active:
            self.analyzer.refine(r)               # QRF + graph match
        return self.gmax.schedule(active,
                                  capacity_C=self.free_cap(),
                                  batch_size_B=self.max_batch)

class RequestAnalyzer:
    qrf:           QRFModel                    # sklearn-quantile, ~10MB
    pattern_db:    GraphIndex                  # LSH over recent workflows
    def refine(self, r):
        r.L_up_hat = self.qrf.predict_quantile(r.features, q=0.95)
        if r.is_compound:
            r.next_stages = self.pattern_db.match(r.partial_graph)
