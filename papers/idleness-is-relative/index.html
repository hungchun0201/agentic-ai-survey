Idleness is Relative

Exploiting Tool-Call Idle Windows for Offloading in Agentic Systems with MORI

arXiv:2606.00866 arXiv 2026 Agentic KV Offloading Program-aware Scheduling

Tian Xia1, Hanchen Li1, Zhifei Li2, Xiaokun Chen3, Hao Kang4, Yifan Qiao1, Yi Xu1, Ion Stoica1

1University of California, Berkeley · 2Renmin University of China · 3Stanford University · 4Georgia Institute of Technology

1. Why Memory Idleness Became a Scheduling Problem

LLM serving is shifting from isolated chat turns to long-running agent programs whose model calls share a growing prefix. The paper's Claude Code workload contains 16,886 tool calls across a phase study of 532 programs, while a single 32K-token Llama-3-70B request already occupies roughly 5 GB of FP16 KV cache. Consequently, tens of concurrent programs can exceed GPU HBM even while many of them are temporarily executing tools rather than using the accelerator. The interval between model calls is therefore no longer disposable silence: it is a period during which valuable state must be retained, moved, or deliberately discarded.

1.1 A concrete failure under recency-based eviction

The following sequence is an illustrative synthesis of the paper's measured percentiles, rather than a verbatim trace selected by the authors. It shows why a locally reasonable LRU decision can be globally incorrect when a recently active program has just entered a long tool call.

Program A: recently active, now waiting

A coding agent completes inference and starts a test near the measured P99 duration: 19,980 ms. Its accumulated 32K-token, 70B-model cache may occupy about 5 GB, but it will not request a GPU for almost twenty seconds.

→

Program B: older access, imminent return

A second program entered a routine file operation slightly earlier; a median tool call lasts only 1,096 ms. LRU selects this older cache for eviction, so the program returns roughly one second later to a reload or full-prefix recomputation.

The resulting placement retains Program A's inactive state in scarce HBM while imposing recovery work on Program B, which is ready to resume. The mismatch is not caused by a poor cache implementation; it follows from using elapsed recency as a proxy for future readiness when tool duration is controlled by filesystems, test suites, humans, and child agents.

1.2 The baseline degradation is measurable

The high-load experiments expose the cost before MORI's improvements are considered. On B200 with Llama-3.1 70B and a 1× CPU-memory budget, ThunderAgent plus uncoordinated offloading rises from 147 to 181 tokens/s between 20 and 50 programs, then falls to 146 tokens/s at 80 programs; its average TTFT reaches 56 seconds, while SGLang Model Gateway reaches 108 seconds. Doubling host-memory capacity does not repair the placement policy: at 80 programs the same offloading baseline provides only 124 tokens/s and its TTFT changes from 56 to 58 seconds. In the three-replica experiment, its throughput similarly decreases from 1,395 to 920 tokens/s as concurrency rises from 50 to 80 programs per replica, while phase-oblivious schedulers use only 59–76% of the GPUs.

Baseline lesson. Additional DRAM increases nominal capacity, but capacity without coordinated placement may preserve the wrong programs and therefore provide little latency benefit.

2. Why the Obvious Policies Do Not Close the Gap

The natural remedies are to offload every paused program, retain the most recent program, or classify each program as simply busy or idle. Each remedy observes one useful property, but none jointly accounts for unknown return time, non-negligible transfer cost, and finite capacity in both memory tiers. This section isolates those structural limitations before introducing MORI's design.

2.1 Strawman: offload every tool call or use a fixed threshold

Immediate offloading appears safe because every tool call creates an interval during which its program does not execute on the GPU. However, cache transfer time grows with context size, and the paper's median tool call lasts only 1,096 ms; moving a multi-gigabyte cache down to DRAM and back can consume a substantial share of such a gap. Waiting for a fixed duration, such as two seconds, is also incomplete: although 87% of measured calls finish below that threshold, the remaining 13% account for 58% of all tool-call wall time, and the scheduler does not know which group contains a new call until time has elapsed.

A binary phase label introduces a second mismatch. The aggregate memory occupied by busy and idle programs changes as contexts grow and programs change phase, whereas the machine presents a fixed capacity ratio; the paper contrasts approximately 1:1.6 HBM-to-DRAM capacity on an eight-GPU H100 node with 1 TB of host memory against approximately 1:3.1 with 2 TB. A threshold that fills both tiers in one configuration can over-subscribe one tier and leave the other underused in another configuration.

2.2 The fundamental obstacle is online uncertainty

The scheduler must commit memory before the environment reveals when a tool call will finish. Exact duration depends on external state such as repository size, test behavior, human approval, and subagent execution, so neither request metadata nor recent access time provides the missing future information. At the same time, correcting a decision is not free because every GPU–CPU transition transfers a cache whose size grows with the program's prefix. MORI therefore cannot solve the problem by predicting each next duration more precisely; it must make an online placement decision that is robust to uncertainty and changes its boundary according to actual tier capacity.

2.3 Position relative to immediate prior systems

Five neighboring systems establish the pieces from which MORI departs. The comparison below distinguishes program awareness, offloading capacity, and phase-sensitive placement; the paper's contribution lies in coordinating all three rather than introducing KV transfer itself.

InferCept Preserves or restores KV state around external-call interruptions. A single call's duration remains difficult to anticipate; no continuous cross-tier program ranking is provided.

Taken together, the prior systems either understand program structure without coordinating a host-memory tier, or expose a memory hierarchy without understanding program phase. MORI connects the two layers through one ranking signal and a capacity-aware control policy.

2.4 MORI's answer: rank first, place second

After establishing the failure mode, the design can be summarized compactly. MORI estimates each program's recent fraction of time in tool execution, ranks all active programs on that continuous spectrum, and lets physical capacity determine where the ranking is partitioned. The following contributions separate the signal, the placement mechanism, admission control, and multi-replica routing.

1. Continuous relative idleness

A five-cycle window converts recent Reasoning and Acting durations into one comparable score without predicting the next tool call.

2. Sticky capacity-aware placement

Programs retain their current tier until pressure or newly available capacity justifies a transfer, limiting PCIe movement.

3. Admission at both memory tiers

Per-replica GPU and CPU queues obey separate budgets; overflow enters a global Waiting queue rather than inducing uncontrolled eviction.

4. Affinity across GPU and CPU state

The router remembers which replica owns each cache even after offloading, so a returning program can reload locally instead of recomputing elsewhere.

3. Execution Model: The Program, Not the Request

MORI begins by changing the object that the serving system remembers. An individual request ends after decode, but an agent program continues through a sequence of dependent requests, tool executions, and an increasingly valuable prefix; consequently, placement state must survive request boundaries. The distinction also separates an instantaneous execution status from a longer-lived behavioral phase, which is the signal MORI ultimately schedules.

3.1 One program is a chain of prefix-dependent steps

A program comprises the complete agent session, including every model invocation and the tool-call gap that follows it. Each tool result is appended to the next prompt, so the next request shares the full prefix of preceding requests and the associated cache grows monotonically.

Figure 2 (from paper): The lifecycle alternates GPU inference with environment-side tool execution. Tool outputs extend the shared prefix, so the KV cache remains useful even while the program is not using the GPU.

Figure 2 clarifies why request-local reclamation is insufficient: a completed response is not the end of the logical computation. When several tools run in parallel, the paper treats their maximum completion time as one gap; when a parent spawns a subagent, the child is a separate program, while the parent's wait is modeled as a potentially long tool call.

3.2 Status is instantaneous; phase is persistent

The scheduler records two immediate statuses. Reasoning means that inference is executing, while Acting means that the program is waiting for its environment; neither status alone predicts whether the current gap will be short. A phase instead summarizes a sustained pattern across several cycles: busy programs alternate rapidly, whereas idle programs remain in Acting for a substantial interval.

Reasoning GPU active
short Acting busy phase
Reasoning returns soon
long Acting interval idle phase
Reasoning eventual return

This separation prevents the system from equating every Acting interval with idleness. The placement decision is derived from the program's recent balance of both statuses, while the immediate status remains useful for safe movement: an Acting program can be demoted at once, whereas a Reasoning program completes its current inference step first.

3.3 Three storage outcomes, not merely two locations

The physical hierarchy has GPU HBM and CPU DRAM, but finite capacity creates a third logical outcome: no retained cache. The table distinguishes the latency and admission consequences of each state, which is essential because a CPU-resident return requires transfer while a Waiting return requires full-prefix prefill.

Logical tier Physical state When the program returns
GPU queue KV blocks remain in HBM. The request can enter inference directly, subject to batch scheduling.
CPU queue KV blocks remain in local host DRAM. The request is gated until a same-replica reload restores HBM residency.
Waiting queue The retained cache has been discarded. The request waits for admission and recomputes the full prefix by prefill.

Admission control must therefore cover CPU DRAM as well as HBM. Treating DRAM as unlimited merely moves eviction contention down one tier, and a later return still pays full recomputation once the host copy has been displaced.

4. Workload Evidence: Calls Are Unpredictable, Phases Persist

MORI depends on a subtle empirical distinction. Individual tool-call duration spans more than three orders of magnitude and is unsuitable as a directly predicted scheduling target, yet short calls cluster into busy episodes and long calls create sustained idle episodes. The trace analysis supplies both halves of that claim and thereby justifies a recent-history metric rather than a next-call oracle.

4.1 The heavy tail creates two distinct scheduling regimes

Across 16,886 observed tool calls, the median is 1,096 ms and P90 is 2,034 ms, but P99 reaches 19,980 ms and P99.95 reaches 83,626 ms. This distribution means that most calls offer little time for a round-trip cache transfer, while a small tail provides ample opportunity to reclaim HBM.

Figure 3 (from paper): The CDF exposes a dense body near one second and a long tail extending beyond one minute. A single absolute retention rule must therefore compromise between needless transfers in the body and wasted HBM in the tail.

The same tool type can inhabit both regimes: a shell command may return in hundreds of milliseconds, whereas a test suite invoked through the same interface may run for tens of seconds or minutes. Consequently, semantic labels such as file operation or shell command cannot replace an observed behavioral signal.

4.2 Idle periods arise from tools, humans, and subagents

The paper groups long waits by their effect on the parent program rather than by implementation details. A test or compilation occupies the environment, human interaction postpones the next prompt, and a parent awaiting child agents remains inactive even if the children themselves are computation-intensive.

Figure 4 (from paper): Long-running tools, human approval, and child-agent joins all create sustained idle phases for the affected program. The red and green frames identify behavioral episodes rather than instantaneous request states.

This definition preserves compositionality in multi-agent systems. Each child receives its own program identifier and cache placement, while the parent accumulates Acting time until the join completes; the scheduler can therefore offload the parent without misclassifying active children.

4.3 Phase persistence makes recent history useful

The phase analysis covers 532 programs and remains qualitatively stable across short-call thresholds of one, two, and five seconds. Median busy-phase durations are approximately 4, 20, and 41 seconds, with corresponding P90 values of 15, 81, and 185 seconds; at the two-second threshold, short calls form 87% of events while long calls consume 58% of total tool time.

Figure 5 (from paper): Short tool calls cluster into episodes that last long enough for a five-second control loop to observe. The threshold changes the measured episode length, but not the existence of sustained busy behavior.

The evidence supports phase estimation, not deterministic forecasting. A recent window can react when an ongoing tool call becomes dominant and can forget a stale long call after several short cycles, but it cannot guarantee the next return time; MORI's sticky placement and capacity checks are therefore necessary companions to the metric.

5. Architecture: A Ranking Across Three Logical Tiers

MORI is a scheduler and router positioned between agent clients and one or more SGLang inference replicas. It tracks program-level history, assigns each program to GPU, CPU, or Waiting state, and sends typed placement hints to the engine that owns the actual radix-tree blocks. The architecture deliberately separates policy from mechanism: the router decides which programs deserve each tier, while SGLang and HiCache execute block placement and transfer.

5.1 End-to-end control path

The complete path has three responsibilities. First, a continuous idleness score orders programs by likely near-term GPU demand; second, a capacity-aware scheduler selects the cut between HBM and DRAM; third, an affinity-aware router preserves ownership of cached state across replicas.

Figure 1 (from paper): MORI converts program histories into a relative spectrum, packs the least-idle working set into HBM, retains more-idle state in DRAM, and routes subsequent calls toward the replica that already owns the program's cache.

The spectrum is relative rather than calibrated to a universal threshold. A program with moderate idleness may remain in HBM on a lightly loaded server, move to DRAM when HBM pressure rises, and enter Waiting only when both budgets are exhausted; the same score can therefore operate across hardware with different capacity ratios.

5.2 Per-replica memory queues and a global Waiting queue

Each inference replica owns one GPU queue and one CPU queue because both cache copies are physically local to that replica. By contrast, programs with no retained state occupy a global Waiting queue and can be assigned through cluster-level packing, since no existing cache constrains their destination.

Figure 6 (from paper): GPU and CPU queues belong to individual replicas, while Waiting is shared. Promotion from a CPU queue restores state locally; promotion from Waiting performs a new admission and may require full prefill.

The local CPU queue is therefore more than a capacity extension: it records where a reusable copy resides. A program that returns from a tool call is preferentially promoted on the same replica, avoiding a route that would abandon a valid DRAM copy and recompute the prefix elsewhere.

5.3 Architectural invariants

The scheduler maintains four invariants that turn a heuristic score into a safe resource policy. These constraints prevent the ranking from admitting more state than either physical tier can hold and prevent a request from reaching inference before its cache placement is valid.

Invariant 1 — HBM budget

The aggregate estimated context of GPU-queue programs on each replica does not exceed its configured GPU cache capacity.
↓

Invariant 2 — DRAM budget

The corresponding CPU queue obeys a separate host-cache limit; excess state is not admitted merely because it has left HBM.
↓

Invariant 3 — safe transition

A Reasoning program completes its current inference step before a demotion becomes effective.

Invariant 4 — gated return

A CPU or Waiting request remains blocked until promotion establishes capacity and valid HBM state.
Architectural insight. Relative idleness determines priority, but capacity invariants determine feasibility. This separation allows the same ranking rule to adapt to a different HBM-to-DRAM ratio without retraining a predictor or selecting a new absolute phase threshold.

6. Core Mechanisms: Measure, Rebalance, and Enforce

The architecture becomes operational through three coupled mechanisms. A windowed metric estimates sustained behavior, a sticky control loop moves only the programs needed to restore capacity and priority order, and typed engine hints make block-level eviction agree with program-level placement. Their interaction matters: the metric alone does not enforce memory safety, while tier movement without typed eviction can be undone by the engine's local LRU policy.

6.1 Windowed relative idleness

For each program, MORI totals intrinsic Reasoning and Acting time over the most recent $k$ inference–tool cycles. Scheduler-imposed waiting is excluded, because including it would create a feedback loop in which a program appears idle merely because the scheduler delayed it.

(1) $$\iota = \frac{T_{\mathrm{acting}}^{(k)}}{T_{\mathrm{reasoning}}^{(k)} + T_{\mathrm{acting}}^{(k)}} \qquad \text{with } k=5$$

An idleness value $\iota$ near zero identifies an inference-heavy program, whereas a value near one identifies a tool-heavy program. The elapsed time of an ongoing Acting interval continues to enter $T_{\mathrm{acting}}^{(k)}$, so a genuinely long call raises the score before completion; conversely, a new burst of short calls gradually removes stale idle history from the five-cycle window.

Interpretation. The score estimates the fraction of recent intrinsic execution time during which HBM residency produced no GPU work. It is a ranking feature, not a calibrated probability that the next call will exceed a particular duration.

6.2 Sticky rebalancing

The controller does not sort the entire population and transfer every program on each tick. Instead, current placement is retained until a capacity violation or an available higher-tier slot creates a concrete reason to move, which preserves most of the benefit of relative ranking without paying continuous PCIe churn. The following pseudocode is a faithful high-level reconstruction of Sections 4.2–4.3, not released source code. 

every control_tick:
    update_recent_idleness(active_programs, window=5)

    for replica in replicas:
        while replica.gpu_bytes > replica.gpu_budget:
            victim = highest_idleness(
                replica.gpu_queue,
                prefer_status="Acting"
            )
            if victim.status == "Reasoning":
                demote_after_current_step(victim)
            elif replica.cpu_has_space(victim):
                offload_to_local_cpu(victim)
            else:
                discard_to_waiting(victim)

        while replica.gpu_has_space():
            candidate = lowest_idleness_ready_program(
                cpu_returns_first=True,
                waiting_returns_second=True,
                new_arrivals_last=True
            )
            promote_with_affinity(candidate, replica)

Demotion first prefers programs already in Acting status and then chooses the highest idleness within a status; if only Reasoning candidates remain, lazy demotion preserves the in-progress inference step. Promotion reverses the ranking and preserves a strict service order: ready CPU-resident returns precede Waiting returns, returning work precedes new work, and small new contexts are preferred when no retained cache differentiates candidates. The five-second default tick bounds reaction speed, but the paper does not report a sensitivity study for that interval.

6.3 Typed offloading aligns block eviction with program placement

The router's decision can be violated if the engine continues to evict blocks using undifferentiated LRU. MORI therefore stamps each program's radix-tree nodes as busy, idle, or inactive and uses type as the primary eviction key, with recency only breaking ties within a type.

Tier Evict first Then Retain longest Rationale
GPU HBM inactive idle busy The least-idle programs are expected to request inference soon.
CPU DRAM inactive busy idle Host capacity is reserved for programs expected to remain away from the GPU longer.

Reversing the type order between tiers is the essential detail. If both caches used the same priority, HBM and DRAM would compete to retain the same programs; the reversed order makes the two capacities complementary, while LRU still provides a deterministic local policy inside each class. Busy-typed waiting requests also receive batch-admission priority so that scheduler-selected GPU residents are served promptly.

6.4 Affinity-aware promotion across replicas

A CPU-resident cache remains tied to the replica that created it, whereas a Waiting program has no cache locality to preserve. MORI therefore promotes CPU returns on their owner replica and applies Best-Fit-Decreasing-style packing only to global Waiting candidates, selecting replicas with available capacity while preferring returning work over new arrivals.

Replica 1 · GPU queue

P1 · busy P4 · busy

Immediate service path; HBM budget enforced locally.

Replica 1 · CPU queue

P2 · idle P7 · idle

Local DRAM copy preserves reload affinity to Replica 1.

Global Waiting queue

P3 · inactive new P8

No retained copy; placement may use any replica with capacity.

This distinction prevents a subtle loss of locality in phase-oblivious routing. A baseline may regard a GPU-evicted program as uncached and send it to the lightest replica even though the original replica still holds a DRAM copy; MORI keeps that ownership visible to the router until the cache is truly discarded.

8. Evaluation: Benefits Emerge Under Memory Pressure

The evaluation replays real Claude Code request lengths and tool durations while varying concurrency, model size, accelerator, CPU-cache budget, and replica count. Its central result is conditional rather than uniform: when the combined working set fits, phase-aware placement adds little; when HBM and DRAM both become contested, the relative ranking prevents phase-oblivious eviction and preserves replica utilization. The exact configuration matters because model, hardware, and parallelism change together across the four reported settings.

8.2 Single-replica stress: B200 with Llama-3.1 70B

The B200 configuration places the 70B model across two tensor-parallel GPUs and creates the strongest reported pressure on retained context. Under the one-times CPU budget, TA+O throughput rises from 147 to 181 tokens/s between 20 and 50 programs but declines to 146 tokens/s at 80; MORI records 136, 191, and 189 tokens/s over the same concurrency levels. Under the two-times CPU budget at 80 programs, MORI reaches 213 tokens/s while TA+O reaches 124 tokens/s, a reported 71% improvement.

Figure 9 (from paper): Rows compare one-times and two-times CPU-to-GPU cache budgets; columns report output throughput, completed steps per second, and average TTFT. The largest separation appears at high concurrency, where placement rather than nominal capacity determines which cached prefixes remain useful.

Average TTFT exhibits the same effect. At 80 programs in the figure-aligned one-times condition, SMG, TA, TA+O, and MORI report 108, 73, 56, and 38 seconds respectively; after the CPU budget doubles, MORI improves from 38 to 33 seconds while TA+O changes from 56 to 58 seconds. Additional host capacity benefits the policy that coordinates both tiers, whereas independent CPU LRU does not consistently convert capacity into readiness.

8.3 Multi-replica scheduling: utilization and cache affinity

The DP=3 experiment uses H200 replicas with Qwen-3 30B-A3B and tests 20, 50, and 80 programs per replica, corresponding to 60, 150, and 240 concurrent programs in total. At the highest load, MORI reports 54–79% higher throughput than TA+O, 66–75% higher throughput than SMG, 36–43% lower TTFT, and more than 99% GPU utilization; TA and TA+O use only 59–76% of the GPUs.

Figure 10 (from paper): The DP=3 result combines tier placement with routing. Phase-oblivious baselines lose throughput as per-replica concurrency rises, whereas MORI maintains a balanced active set and preserves the replica that owns offloaded state.

The routing evidence is visible in program churn. At 20 programs per replica, TA and TA+O cause 14–15% of programs to switch backend at least once, averaging 0.35–0.38 switches per program; MORI records 0.3–2.9% and 0.00–0.04 respectively. At 80 programs with the two-times CPU budget, MORI, TA+O, and TA switch 2.0%, 5.5%, and 7.6% of programs, with 0.02, 0.10, and 0.13 switches per program.

9. Critical Assessment: What the Evidence Establishes

MORI presents a coherent systems argument: agent programs exhibit persistent phases, a relative score identifies which state is least urgent, and coordinated tier management improves high-pressure serving. The evaluation strongly supports that argument within its replayed coding-agent setting, but it does not establish universal phase behavior, tail-latency improvement, or source-level reproducibility. Distinguishing those scopes is important because the paper combines an empirically grounded mechanism with several extensions that remain future work.

9.2 Strengths and limitations

The design's strengths concern abstraction and coordination, while the limitations concern evaluation breadth and artifact availability. The paired cards state both sides at the same level of specificity.

Strengths

  • The signal matches the program-level timescale demonstrated by the trace rather than predicting an unknowable next-call duration.
  • Relative ranking separates workload behavior from hardware-specific partition thresholds.
  • Admission control covers both HBM and DRAM, preventing host memory from becoming an unmanaged overflow area.
  • Tier-specific eviction and replica affinity align router policy with engine behavior.

Limitations

  • Replay preserves lengths and sleeps but not live agent decisions, task success, or feedback between generated output and later tools.
  • Only average TTFT is reported; no tail distribution, variance, confidence interval, or statistical test is provided.
  • No sensitivity or ablation isolates k=5, the five-second tick, typed eviction, dual-tier admission, and affinity.
  • SSD, remote DRAM, heterogeneous GPUs, multi-node scale, and workloads beyond Claude Code remain untested.

The H200 configuration capped at 80 GB deserves particular care. It emulates H100-class capacity, not H100 hardware, and HBM bandwidth differs; this distinction matters for a system whose transfers and cache pressure are central to performance.

10. Takeaways and Research Questions

MORI's lasting idea is not a particular two-second cutoff or a claim that tool duration can be forecast exactly. It reframes idle memory as a relative scheduling resource: programs are ordered by recent intrinsic behavior, then hardware capacity selects the feasible frontier and the engine enforces that decision consistently. This perspective is most valuable when reusable prefixes are large, tool gaps form persistent phases, and both HBM and host memory are shared under pressure.

10.1 The compact mental model

The complete design can be remembered as five dependent decisions. Removing any one of them weakens the chain: program identity supplies continuity, history supplies the signal, capacity supplies the boundary, typed eviction supplies enforcement, and affinity supplies cluster locality.

This sequence also clarifies when MORI provides little additional value. A single-turn workload has no reusable inter-call state; a lightly loaded system does not require a difficult partition; and a workload without persistent phases gives recent history little predictive content.

10.2 Questions opened by MORI

The paper resolves two-tier placement for one observed workload, but its abstraction suggests several testable extensions. Each question below preserves the relative-ranking principle while relaxing one fixed design choice.

Adaptive observation horizon

Can the window expand for stable programs and contract after a detected phase transition, replacing the fixed k=5 choice?

Transfer-aware ranking

Should idleness be combined with cache bytes, PCIe bandwidth, and expected prefill cost so equal scores do not imply equal movement value?

More than two physical tiers

Can multiple ranking cuts coordinate HBM, local DRAM, remote DRAM, and SSD without making transfer churn dominate?

Open-loop and tail objectives

Does the same policy preserve p99 TTFT and admission fairness under bursty arrivals, heterogeneous SLOs, and longer multi-node runs?

Answering these questions requires a public artifact and broader traces. In particular, component ablations should distinguish the benefit of the idleness score from dual-tier admission, typed eviction, and replica affinity before the mechanism is generalized to additional storage tiers.
