ASPLOS 2026 · Dynamic Multi-GPU Parallelism

Shift Parallelism: Low-Latency, High-Throughput LLM Inference for Dynamic Workloads

A production-oriented runtime that shifts between tensor parallelism and sequence parallelism as traffic changes.

Mert Hidayetoglu, Aurick Qiao, Michael Wyatt, Jeff Rasley, Yuxiong He, Samyam Rajbhandari · Snowflake AI Research

arXiv:2509.16495H200TP + SPProduction tracesOpen source

1. Problem

Tensor parallelism reduces per-request latency but can lose throughput to GPU communication. Data parallelism maximises aggregate throughput but makes each request slower. Traditional serving systems cannot freely switch because the KV cache layout differs across parallelism modes.

Figure 1 from the paper: Shift Parallelism changes the response-speed, generation-rate, and throughput tradeoff.
Figure 2 from the paper: bursty traffic motivates switching rather than a single fixed parallelism mode.

2. Method

The key observation is that Ulysses-style sequence parallelism can be adapted to inference while preserving KV-cache invariance with TP. Shift Parallelism uses TP when traffic is low and latency dominates, then shifts to SP when traffic is high and throughput dominates.

SP modeImproves throughput when the system is saturated.

The paper uses synthetic arrivals, Azure LLM Code traces, Mooncake conversation traces, and code-agent style evaluations. This makes it unusually close to real dynamic serving compared with static microbenchmarks.

4. Relation to This Repo

  • The current predictor is mostly single-GPU and kernel/step focused; Shift identifies the next boundary: parallelism mode and communication can dominate at cluster scale.
  • KV-cache layout assumptions should be explicit when discussing TP, SP, PP, or disaggregated serving extensions.
  • The repo can cite Shift as evidence that latency-throughput prediction must condition on traffic regime, not only model and hardware shape.

5. Limitations

Shift Parallelism is a multi-GPU runtime system rather than a closed-form latency model. It is strongest for H200-class deployments where TP/SP communication tradeoffs dominate; it does not address single-GPU framework overhead or kernel-level attention efficiency.
