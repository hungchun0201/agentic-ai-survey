Dynamic TP/SP mode switching for serving fleets

Shift Parallelism: Dynamic TP and SP for LLM Inference

A vLLM plugin that shifts between tensor parallel latency mode and sequence parallel throughput mode.

Authors Samyam Rajbhandari, Mert Hidayetoglu, Aurick Qiao, Ye Wang, Juncheng Yang, Jeff Rasley, Michael Wyatt, Yuxiong He
Affiliation Snowflake AI Research
Venue and version ASPLOS 2026, arXiv 2509.16495v2
Page scope KV-cache-invariant parallelism, Arctic Inference plugin path, and bursty workload evaluation

Core Question

Shift Parallelism asks whether one deployment can cover both latency-oriented and throughput-oriented traffic. Static TP favors low latency, while DP/SP-like modes improve throughput under larger batches.

The paper’s answer is runtime mode switching under a cache-invariance constraint: change the execution shape without moving or rebuilding KV-cache state.

Motivation Ladder

The result is not a new attention kernel; it is a serving parallelism policy. Batch size controls the mode, while the cache-invariance property keeps switching from becoming a data-movement problem.

The code path matters because it changes vLLM execution through the Arctic Inference plugin rather than only simulating a scheduler. Config, argument parsing, Ulysses logic, and model-runner patches all participate.

1

Why now

Enterprise LLM traffic alternates between interactive requests and large background batches. A serving deployment tuned only for tensor parallelism or only for data parallelism wastes one side of the latency-throughput tradeoff.

The motivation is fleet-level adaptability. The same deployment needs to move between latency-oriented and throughput-oriented execution without rebuilding serving state.

2

Concrete bad scenario

At low concurrency, a request needs low per-token latency and benefits from full tensor parallelism. Minutes later, batch load rises and the same full-TP setting pays all-reduce overhead that depresses throughput.

This scenario makes static parallelism brittle. A plan that is right for one concurrency regime can become communication-heavy or latency-heavy when the load shifts.

3

Baseline pain

TP is fast for a single request but expensive in communication; DP is throughput oriented but slower per request. Static deployments force operators to choose one, or to maintain separate fleets with imperfect routing.

The TP and DP tradeoff motivates a mode that changes execution shape while preserving cache layout. That is the reason sequence parallelism becomes central here.

4

Strawman

Switching between TP and DP seems direct until KV cache layout is considered. If each mode shards heads and sequence positions differently, mode switching requires moving or rebuilding cache state.

Naive switching fails because cache movement would dominate the transition. Shift Parallelism is useful only if the same KV cache can remain valid across modes.

5

Fundamental obstacle

The core challenge is preserving cache invariance while changing parallel execution. Shift Parallelism adapts Ulysses-style sequence parallelism so the same KV cache can serve both high-throughput SP mode and low-latency full-TP mode.

The invariance condition is therefore the paper's main systems hinge. It lets scheduling choose a parallel mode without treating cached tokens as mode-specific state.

6

Position against nearby systems

The work is a deployment-level parallelism mechanism, not a new attention kernel or scheduler policy alone. It complements vLLM and Arctic Inference by adding a mode switch controlled by observed batch size.

This scope distinguishes the paper from kernel-level attention work. It changes serving parallelism policy while leaving the model computation semantics intact.

Claim Boundaries

The claim is about switching between two execution shapes inside one deployment, not arbitrary dynamic repartitioning.

Threshold choice, communication topology, and CUDA graph coverage decide whether the mode switch improves latency and throughput in a new setting.

System Map

The system watches batch size and chooses a parallel mode. The hard part is making that decision cheap enough that switching does not erase the gain.

KV-cache invariance is the center of the design. It lets the same cached tokens remain valid when the execution mode changes.

Base SP mode Run with Ulysses sequence parallelism and tensor parallelism for efficient large batches.
Monitor tokens Count scheduled tokens or batch size to infer when latency mode should activate.
Shift threshold Use `shift_parallel_threshold` to select full-TP mode for small batches.
Reuse KV cache Keep cache layout invariant across SP and TP so switching avoids migration.
Capture graphs Maintain CUDA graph variants for both base and shift models.

Design Equation

The equation states the deployment invariant: total parallelism is fixed, while the split between tensor and sequence dimensions changes at the threshold.

The formula captures the policy shape but hides the communication constants. The threshold has to be calibrated to model size, context length, and interconnect cost.

The switching rule keeps total parallelism fixed while changing how it is expressed by tensor and sequence dimensions.

Mechanism Deep Dive

Shift Parallelism has three moving pieces: a mode policy tied to batch size, a sequence-parallel execution form, and a KV-cache layout that remains valid across modes.

The core risk is transition cost. If switching requires moving KV blocks, the mode policy collapses into another static deployment choice.

Ulysses adaptation

The code patches vLLM attention so sequence-parallel ranks exchange QKV via all-to-all before and after attention. It also handles GQA by dividing or replicating KV heads when needed.

Dual model runners

The implementation loads a base Ulysses model and a shift model whose tensor parallel size is multiplied by the sequence parallel size. Runtime execution swaps to the shift model below the threshold.

KV cache binding

After initialization, the code binds shift attention layers to the base attention KV cache when the shift context exists. This is the code-level counterpart of cache invariance.

CUDA graph split

The code builds separate graph capture sizes for base SP mode and shift TP mode, excluding below-threshold sizes from the base capture set to avoid collective mismatch.

Interaction Among Pieces

Shift’s pieces are coupled by the cache-invariance requirement. The batch-size policy is only useful because the distributed-attention path can change mode without invalidating cached tokens.

The threshold is therefore not an isolated heuristic. It sits on top of a layout constraint, a communication tradeoff, and CUDA-graph execution choices.

Implementation Trace

The implementation path runs through Arctic Inference’s vLLM plugin. Config flags, argument parsing, Ulysses helpers, and model-runner patches all participate in the mode change.

The code makes the paper’s scope concrete: it is not a standalone scheduler outside the serving engine, but a modification to how vLLM executes distributed attention and cache layout.

  • `docs/shift-parallel.rst` documents `--enable-shift-parallel` and `--shift-parallel-threshold`, with TP mode used below the threshold and SP plus TP above it.
  • `arctic_inference/vllm/args.py` adds Arctic CLI arguments to vLLM engine args.
  • `arctic_inference/vllm/ulysses.py` patches model parallel groups, attention all-to-all, and CUDA graph sizing.
  • `arctic_inference/vllm/model_runner.py` chooses the shift model when scheduled tokens are at or below the threshold.

Prototype Boundary

The implementation does not remove the need for workload-dependent tuning. The threshold that chooses modes still reflects assumptions about batch size, model shape, and hardware communication cost.

The reported result therefore depends on the burst structure in the workload. Smooth low-concurrency traffic or permanently high-concurrency traffic gives the switching policy less room to matter.

Evaluation Reading

The evaluation asks whether one deployment can cover both latency and throughput regimes. The right baseline is not only faster TP or faster DP, but the cost of maintaining separate fleets for each regime.

The context-length experiments are important because KV layout pressure grows with sequence length. A mode switch that is cheap for short contexts can become costly if cache invariance is broken.

Evaluation Discipline

Read the evaluation by regime. Shift is not claiming to outperform every static mode at every instant; it claims that one deployment can move between regimes without rebuilding cache state.

The burst results and context-length sweep are the critical checks because they expose when the threshold policy helps and when communication or cache footprint dominates.

Limitations and Failure Modes

The main limitation is that invariance is a strict requirement. Any model feature or runtime change that alters KV partitioning can make the switching strategy harder to apply.

Communication topology also matters. The TP/SP balance depends on all-reduce and sequence-shard communication cost, so hardware fabric changes the best threshold.

Memory overhead

The paper discusses memory overhead from KV replication and reports it as a function of the sequence parallel degree. This matters for very large models near memory capacity.

Threshold sensitivity

The threshold is simple and practical, but it is still a policy knob that should match model size, traffic distribution, and CUDA graph capture sizes.

Framework coupling

The GitHub implementation is a vLLM plugin with patches to config, parallel state, attention, executor, model runner, and CUDA graph handling.

Takeaways

The main lesson is that parallelism should be treated as a runtime mode, not only a deployment-time choice.

The second lesson is that runtime mode switching is only useful when state layout is invariant. Otherwise the data movement cost consumes the scheduling benefit.

  • Parallelism can be a runtime mode, not a deployment-time constant.
  • KV cache invariance is the enabling condition; without it, switching would become data migration.
  • The Arctic Inference repository implements the vLLM plugin path, so the mode switch is not only a paper-level scheduler sketch.

Bottom Line

Shift Parallelism turns parallelism from a deployment-time constant into a runtime mode.

Its value depends on cache invariance and communication cost; if either breaks, separate static deployments become competitive again.

Best use case

Traffic that alternates between interactive low-batch serving and high-batch throughput phases.

Main risk

If cache invariance or mode-switch overhead breaks, the policy loses its advantage over separate static deployments.
