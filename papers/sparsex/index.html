SparseX

Efficient Segment-Level KV Cache Sharing for Interleaved LLM Serving — reusing repeated text that appears anywhere in the prompt, not only as a prefix

arXiv:2606.01751 arXiv preprint (2026) Segment-Level KV Reuse SparseQ + Sparse-KV Recompute vLLM v1 0.11.0

Quqing Zhang, Kai Chen, Ning Liao, Zehao Lin, Bo Tang, Feiyu Xiong, Zhiyu Li, Xiaoxing Wang

Code released at github.com/MemTensor/SparseX (MemTensor)

1. The Interleaved-Reuse Problem

By 2026 the dominant long-context serving workloads — multi-round chat, retrieval-augmented generation (RAG), and multi-agent workflows — all reprocess large amounts of text that the serving stack has already seen. A chat assistant re-reads the entire dialogue history on every turn; a RAG service re-encodes the same knowledge snippets for thousands of different questions; a group of collaborating agents each re-reads another agent's intermediate reasoning, tool output, or draft. In every case the prefill stage, which must run multi-layer self-attention over the full context of length N and write the Key/Value (KV) tensors for every token, dominates end-to-end latency and compute cost. The natural remedy is to reuse the KV of text that has already been encoded rather than recomputing it.

Figure 1 (from paper): Three common KV reuse scenarios supported by SparseX — multi-round chat, RAG, and multi-agent systems. Reusable content appears as segment-level repeated text distributed across different positions in the prompt, not as a clean shared prefix.

The catch is that today's production systems can only reuse KV when the repeated text is an exact prompt prefix. vLLM's Automatic Prefix Caching hashes blocks and reuses them when a new request shares an identical leading token sequence; SGLang's RadixAttention keeps prefixes in a radix tree. Both preserve output quality exactly, but both fire only on token-level prefix equality. The repeated content in real traffic does not obey this shape: it arrives as non-prefix, cross-request, cross-turn, and cross-agent segments scattered through the middle of the prompt.

1.1 A concrete failure trace

Consider a multi-agent debate over a hard reasoning problem. A first agent produces a 3,000-token analysis. A second agent's prompt is [system instruction] + [problem statement] + [Agent-1 analysis] + [new debate instruction]. The 3,000-token analysis is textually identical to what Agent-1 already encoded, but it now sits after a different system instruction and a different problem framing, and it is wrapped by fresh instructions on both sides. Because it is not a leading prefix, vLLM's Prefix Cache misses on it entirely, so the engine re-prefills all ~3,300 tokens from scratch. The reused analysis is byte-for-byte the same text the cluster computed seconds ago, yet the system pays the full quadratic attention cost again.

The general form of such a prompt is an interleaving of original and reused segments rather than a single reused block followed by original text. SparseX writes it as the pattern below, where each Reuse segment is cached text at an arbitrary position and each Original segment is fresh text specific to the current request:

Original₁ Reuse₁ Original₂ Reuse₂ … Reuseₖ Originalₖ

Prefix Cache can only reuse a leading run; every reused segment after the first Original block is invisible to it. The number of interleavings grows with dialogue depth, RAG concatenation policy, and agent-trajectory length.

1.2 What the status quo costs

The paper's own measurements quantify the pain at both ends of the trade-off. When Prefix Cache misses on interleaved reuse, the fallback is full recomputation, whose time-to-first-token (TTFT) is 9.23 s on LOCOMO with Qwen3-32B and 15.58 s on LongMemEval with Qwen3-30B-A3B. The opposite extreme, naively reusing cached KV without any correction, drops TTFT to well under a second but degrades quality sharply: the LOCOMO score falls from 0.68 to 0.54, and the RULER average on Qwen3-8B collapses from 0.96 to 0.69. Neither corner is acceptable: full recompute is too slow for interactive serving, and naive reuse fails on exactly the retrieval and tracking tasks these workloads depend on.

2. Why Reuse Is Hard: Prefix Coupling

The reason naive reuse fails is not an implementation bug — it is a structural property of self-attention. The KV of a token is not a fixed function of that token alone; it is a function of the token together with everything that precedes it. SparseX states this obstacle almost verbatim as the premise our own line of work is built on, and this page treats the sentence below as the motivating citation to lock:

“Because self-attention couples a segment representation with its prefix context, the hidden states and KV tensors of the same text segment often differ under different prefixes and different concatenation positions.”
— SparseX, Section 1.1 (Background)

From this single fact the paper derives a clean problem statement. Because the same text produces different KV under different prefixes and positions, reuse cannot be a memory copy. SparseX therefore reframes it as an approximation problem to be solved per token:

“Reuse in realistic settings is a context-dependent and position-dependent approximate computation problem: under an output-quality constraint, the system must determine which tokens can directly reuse cached KV tensors, which tokens must be recomputed, and how this mechanism can be reliably integrated into a high-performance inference engine.”
— SparseX, Section 1.1 (Background)

2.1 Two obvious fixes, and why they are not enough

A reader familiar with the KV-reuse literature will immediately propose two remedies; the paper pre-empts both. The first is to recompute a small, fixed subset of tokens to patch the missing cross-segment interaction — the CacheBlend/EPIC route. This works when reuse is a small number of contiguous chunks, but it assumes a regular structure. Under heavily interleaved inputs an original segment can alter the attention distribution of several downstream reused segments at once, so a local patch chosen from fixed boundaries becomes unstable and hit rates fall. The second is to pick recompute tokens from the deviation of the first attention layer, on the assumption that early layers already reveal token importance. The paper's layer-wise analysis (Section 6.4) shows that this assumption is false in general: where the important signal stabilizes depends strongly on prompt layout, so an early-layer selection can miss the tokens that actually matter.

The fundamental obstacle. Reuse is neither free (prefix coupling makes cached KV wrong at the new position) nor cheap to fix by a fixed rule (interleaving makes the set of tokens that need correction request-specific and layout-dependent). Any workable method must (a) realign the cached KV to the new position and (b) decide, at runtime and per request, which reused tokens still need to interact with the fresh context. SparseX's design is a direct answer to exactly these two requirements.

3. Position vs Prior Work

SparseX places itself in a crowded conversation on non-prefix KV reuse. The paper groups prior methods into three lines — direct segment alignment, auxiliary-model token selection, and sparse-recomputation — and argues that each leaves the general interleaved case on the table. The comparison below names the five works a knowledgeable reader expects to be addressed and states what each does not cover; SparseX's claim is that it is the first to support arbitrary interleaving of reused and non-reuse text inside a mainstream engine.

The cards below restate that taxonomy in the paper's own terms; SparseX positions itself as taking the third, sparse-recomputation route while removing its structural assumptions.

Line 1 · Direct segment alignment

Reuse or align KV at segment/chunk granularity without sparse attention. EPIC does position-independent chunk caching for RAG; KVCOMM keeps an online anchor pool to correct KV offset across prefixes. Low recompute cost, but they depend on stable structure and cannot fully restore cross-attention among segments.

Line 2 · Auxiliary-model selection

Use a small proxy model to predict which tokens to recompute. CacheClip uses a small model's last-layer attention to select tokens critical for cross-chunk restoration. This raises the selection ceiling but adds a second model, which increases scheduling complexity and creates pipeline bubbles under mixed high-concurrency traffic.

Line 3 · Sparse recomputation (SparseX's route)

Recompute a small token subset to compensate missing cross-attention. CacheBlend patches multi-chunk RAG; DroidSpeak recomputes a few layers for cross-model sharing; KVShare and KVLink add deviation-based selection or trainable tokens. The paper argues this is the most promising route for balancing quality and prefill cost — and builds SparseX on it without the contiguous-chunk assumption.

Two of these are load-bearing for the rest of this page. MInference supplies the mechanism SparseX generalizes: SparseX keeps MInference's idea of probing a subset of queries to build sparse indices, but replaces the fixed last-Q tail with the non-reuse query positions that arise naturally in reuse workloads. KVCOMM is the closest prior method to our own thesis, and Section 9 returns to how SparseX positions itself against it — and against us.

4. Contributions & Headline Results

With the problem framed — interleaved non-prefix reuse, made hard by prefix coupling and unsolved by fixed-rule patching — SparseX makes three contributions. The first is an observation turned into an algorithm; the second is the reuse method built on it; the third is a deep engine integration that turns the algorithm into throughput.

C1 · SparseQ-driven token selection

Under segment-level reuse, the non-reuse (original) tokens are exactly the queries that must run attention this pass. SparseX uses these queries as a probe to estimate which reused tokens matter most to the current output — a runtime sparse-pattern estimator that needs no auxiliary model.

C2 · Sparse-KV Recomputation

Arbitrary-position reuse is turned into a sparse-recomputation problem: RoPE-align every reused segment to its new position, then recompute only the selected top-k tokens to restore cross-segment interaction. Model-agnostic, training-free, plug-and-play for decoder-only LLMs.

C3 · SparseX-vLLM

A vLLM v1 0.11.0 extension that unifies segment lookup and storage for chat, RAG, and agents. It stays compatible with PagedAttention, Prefix Cache, and FlashAttention/FlashInfer via virtual blocks, frozen-block pools, and a fused copy-and-RoPE kernel.

The headline result is that SparseX recovers almost all of the quality of full recomputation at a small fraction of its TTFT. On LOCOMO with Qwen3-32B, full recompute scores 0.68 at 9.23 s; SparseX with hybrid attention scores 0.67 at 0.87 s — roughly a 10.6× TTFT reduction at 99% of the quality. On LongMemEval with Qwen3-30B-A3B, full recompute takes 15.58 s and SparseX takes 2.13 s (about 7.3×), while quality is preserved. The metric boxes below should be read against the baseline-pain numbers in Section 1.2: the gain is not merely a speed number, it is a speed number achieved without the quality collapse that naive reuse suffers.

5. SparseX-vLLM Architecture

Before the mechanism, it helps to see where SparseX lives inside a serving engine, because a recurring failure of prior reuse methods is that their algorithmic savings are eaten by data movement and incompatible execution paths. SparseX-vLLM threads its logic through vLLM's existing stages rather than replacing them: request preprocessing at the entrypoint, a two-way lookup in the KV Cache Manager, a unified scheduler output, a RoPE-realignment step in the Worker, and attention-metadata construction in the GPU Model Runner. The original PagedAttention path and FlashAttention/FlashInfer backends remain untouched at the interface level.

Figure 7 (from paper): SparseX-vLLM system architecture. SparseX modules are inserted into entrypoints, the KV Cache Manager, Scheduler, Worker, GPU Model Runner, and model attention layers, while vLLM's original PagedAttention and attention-backend execution path are preserved.

Architectural insight. SparseX deliberately avoids introducing user or session objects into the engine, which would change vLLM's abstraction boundary. Instead it extends only two primitives — the block hash (with an extra key for namespaces) and a virtual-block index — so that segment reuse rides on the same PagedAttention block pool, block table, and slot mapping as ordinary requests. This is why the sparse-recomputation algorithm actually yields throughput instead of being cancelled by data movement.

It is equally worth noting what SparseX leaves untouched, because the compatibility argument rests on it. The PagedAttention CUDA kernels, continuous batching, the sampling path, and the FlashAttention/FlashInfer backends all run unmodified; SparseX adds a fused copy-Delta-RoPE kernel and a sparse-mask field to the attention metadata, but does not fork the attention kernels themselves. Native Prefix Cache continues to serve the non-reuse prefix of every request in parallel with segment reuse. The result is that a deployment can enable SparseX on an existing vLLM v1 0.11.0 stack without giving up the optimizations that stack already provides.

6. Core Mechanism

The mechanism has four moving parts that build on one another. First, cached KV is realigned to its new position so it is usable at all (6.1). Second, the non-reuse queries are used to select which reused tokens to recompute (6.2). Third, an overflow rule captures the local-neighbourhood interaction that a pure top-k selection would miss (6.3). Fourth, a full-then-sparse layer schedule makes the selection stable across prompt layouts (6.4). This subsection follows a concept-then-formula order: each idea is stated in plain terms before the equation that makes it precise.

Because the equations reuse a compact notation, the table below fixes each symbol once so the derivations that follow read cleanly.

6.1 RoPE alignment of a segment cache

A Segment-Level Cache stores the multi-layer Key/Value states of a contiguous token subsequence so they can be reused at an arbitrary position later. The one obstacle to dropping a cached segment into a new sequence is positional: in models with rotary position embeddings (RoPE), each Key already carries its absolute position baked in, so a segment cached at positions starting at $p$ is wrong if the new sequence places it starting at $p'$. Moving it verbatim introduces an attention phase shift. The saving grace is a property of RoPE: the attention score between a query at position $m$ and a key at position $n$ depends only on their relative displacement.

Concretely, if $q$ and $k$ are the base (pre-RoPE) vectors, the query and key actually used at positions $m$ and $n$ are the base vectors rotated by their absolute-position matrices; the inner product of two rotated vectors then collapses to a single rotation by their difference:

RoPE $$\hat{q}_m^{\ell} = R_m\, q^{\ell}, \quad \hat{k}_n^{\ell} = R_n\, k^{\ell} \;\;\Longrightarrow\;\; \langle \hat{q}_m^{\ell}, \hat{k}_n^{\ell} \rangle = (q^{\ell})^{\top} R_{\,n-m}\, k^{\ell}$$

Because only the relative displacement matters, a cached Key can be migrated from old position $n$ to new position $n'$ by applying a single incremental rotation, directly in the cache domain, without ever recovering the unrotated base vector. Values carry no positional phase and are copied unchanged.

key migration $$\hat{k}_{n'}^{\ell} = R_{\,n'-n}\, \hat{k}_{n}^{\ell}$$

For a whole segment $S$ every token shares the same displacement, so the alignment is one batched rotation. Writing the displacement as the offset between the segment's new and old start positions, segment alignment is:

segment align $$K_{\text{new}}^{\ell}(S) = \mathrm{Align}_{\Delta}\!\big(K_{\text{old}}^{\ell}(S)\big), \qquad V_{\text{new}}^{\ell}(S) = V_{\text{old}}^{\ell}(S), \qquad \Delta = p' - p$$

The cost is one read, rotation, and write of the cached Keys, i.e. $O(|S| \cdot d_k)$. SparseX-vLLM fuses page movement, the Delta-RoPE Key rotation, and the Value copy into a single GPU kernel that aligns all requests in a scheduling batch inside one engine core, so realignment does not become the new bottleneck under high concurrency.

What alignment does and does not fix. RoPE alignment corrects the position of a reused segment, but it does not correct the prefix coupling of Section 2. The cached KV was produced under the old prefix; after alignment it is at the right position but still carries the wrong context. Restoring the missing cross-segment interaction is the job of the next three subsections.

6.2 SparseQ: selecting tokens with the receiver's own queries

The key observation is that interleaved reuse already contains the probe it needs. A reused segment's KV is cached, so the current request does not need to generate its queries or run its attention. But every non-reuse (original) segment — a new user turn, a RAG instruction, an agent's routing text — must compute its queries and attend to all available keys to update its hidden state. The queries that must run attention therefore live only on the non-reuse positions. This is the SparseQ structure, and it arises for free during the forward pass.

Figure 3 (from paper): The SparseQ structure naturally formed in segment-level KV reuse. Non-reuse segments must generate Query vectors and execute attention, while the KV tensors of reuse segments can be read from the cache.

Let the input of length $T$ contain positions partitioned into two index sets: the reused-segment positions $\mathcal{I}_{\text{reuse}}$ and the non-reuse positions $\mathcal{I}_{\text{nr}}$. SparseX uses only the second set as its query probe, mirroring MInference's idea of estimating a sparse pattern from a small set of probing queries — but replacing MInference's fixed last-Q tail with the non-reuse indices that reuse naturally provides. Concretely, the probe queries are the rows of $Q$ at the non-reuse positions:

$$Q_{\text{sq}} = Q[\mathcal{I}_{\text{nr}}] \in \mathbb{R}^{\,|\mathcal{I}_{\text{nr}}|\times d}$$

These probe queries attend to all keys of the current sequence (with the causal mask restricted to the probe rows), giving an attention matrix from non-reuse queries to every position:

(1) $$A_{\text{sq}} = \mathrm{softmax}\!\left(\frac{Q_{\text{sq}}K^{\top}}{\sqrt{d}} + M_{\text{causal}}[\mathcal{I}_{\text{nr}}, :]\right)$$

Summing each key position's incoming attention over all probe queries gives a per-token importance score, and the top-$k$ positions are chosen as the tokens to recompute:

(2)–(3) $$s_j = \sum_{i=1}^{|\mathcal{I}_{\text{nr}}|} A_{\text{sq}}[i, j], \qquad \mathcal{S}_{\text{key}} = \mathrm{TopK}\big(\{s_j\}_{j=1}^{T},\, k\big)$$

The cost of the probe is $O(|\mathcal{I}_{\text{nr}}| \cdot T \cdot d)$ for the attention and $O(T \log k)$ for the selection. When the reuse ratio is high the number of non-reuse positions is far smaller than $T$, so this is much cheaper than the $O(T^2 d)$ of full attention — and, crucially, the probe queries are ones the request must compute anyway, so SparseX adds neither an auxiliary model nor a separate dense probing stage. Selection uses a single score aggregated across all attention heads, giving one global token-importance estimate per request rather than a per-head pattern.

The complexity table makes the saving concrete. Full recomputation pays quadratic attention over the whole sequence; SparseX pays a small probe plus a sparse recompute over the selected set, and a linear alignment per reused segment. The saving grows with the reuse ratio, i.e. as the non-reuse fraction shrinks.

Why the non-reuse queries are the right probe is the heart of the method. These tokens are the newly inserted instructions, questions, and routing text; they specify how the reused content should be interpreted and what the current request is trying to do. Their attention therefore points, more directly than any fixed heuristic, at the reused tokens that affect this request's output. As a fallback, when the prompt tail is entirely reused and contains no non-reuse queries, SparseX adds the last 64 queries of the final reuse segment to the recompute set, recovering behaviour close to MInference's original last-Q probing.

6.3 Overflow: recovering local-neighbourhood interaction

Top-$k$ selection reproduces the vertical sparse pattern — a small set of globally important key tokens — but it does not reproduce the slash pattern, which captures local relative-position attention. Building a slash pattern the usual way would require the Key projection of every token, which contradicts the whole point of not projecting reused segments. SparseX resolves this with a cheap overflow approximation: for each non-reuse (SparseQ) interval, it expands outward by one block at both ends, pulling the last block of the previous reuse segment and the first block of the next reuse segment into the recomputation range.

The intuition is a division of labour: the vertical pattern supplies global key tokens, while the overflow blocks supply the local boundary interaction that is most often missing exactly at the seams between a non-reuse segment and its reused neighbours. The full recomputation set is therefore the union of the non-reuse positions, the top-$k$ selected keys, the overflow blocks, and the tail fallback:

recompute set $$\mathcal{R} = \mathcal{I}_{\text{nr}} \,\cup\, \mathcal{S}_{\text{key}} \,\cup\, \mathcal{S}_{\text{ov}} \,\cup\, \mathcal{S}_{\text{tail}}$$

Every token in $\mathcal{R}$ runs full attention in the current context; every reused token outside $\mathcal{R}$ keeps its RoPE-aligned cached KV. 6.4 Full+Sparse hybrid attention on a layer threshold

The final piece addresses when to make the selection, not just how. Methods such as CacheBlend select recompute tokens from first-layer or fixed early-layer signals, assuming early layers already reveal reliable, layout-insensitive token importance. SparseX tests this assumption directly with a layer-wise needle-in-a-haystack analysis, comparing two selection signals across two prompt layouts — the important cue placed before, versus after, the needle.

Figure 5 (from paper): Top-token distribution based on KV deviation (Qwen3-30B-A3B, NIAH). The layer at which the needle stabilizes depends strongly on whether the query cue precedes (left) or follows (right) the needle — an early-layer, fixed-layer selection is layout-sensitive.
Figure 6 (from paper): Top-token distribution based on last-query attention scores (same task). This signal forms a stable needle-localization signal within a similar layer range under both prompt layouts — motivating SparseQ, which generalizes last-Q probing to segment-level reuse.

The two figures deliver the paper's key diagnostic. KV-deviation selection (Figure 5), the signal CacheBlend-style and embedding-similarity methods rely on, identifies the needle only after a number of layers that shifts with prompt layout: when the cue precedes the needle it stabilizes early, but when the cue follows the reused segment the model needs many more layers to form a stable signal. Last-query attention scoring (Figure 6) is far more layout-stable, concentrating on the needle within a similar layer range either way. SparseQ is precisely the generalization of this stable signal to segment-level reuse: instead of one tail query, it uses non-reuse queries distributed across the prompt.

From this, SparseX schedules the selection by layer. Before a boundary layer the model runs full attention on all positions; at the boundary it performs one SparseQ selection using the KV that the full-attention layers have produced; after the boundary, later layers recompute only the selected tokens and read cached KV for the rest. The boundary is model-specific: roughly the first 15–20% of layers for small dense models such as Qwen3-8B, and closer to the first 10–15% for larger or MoE models. Conceptually, this places the selection in the second of three stages — early layers read structure, early-middle layers begin to localize the needle, and late layers refine semantics — so the choice is made once the key region has an observable contour but before full-attention cost is paid at every layer.

6.5 The prefill algorithm, end to end

Assembling the four parts gives the end-to-end SparseX prefill (Appendix A of the paper). The pseudocode below traces one request from segment parsing through the layer-boundary selection to the final mixed full/sparse pass; note that the expensive top-$k$ selection runs exactly once, at the boundary layer, and every later layer reuses that single decision.

# End-to-end SparseX segment-level prefill for one request
def sparsex_prefill(prompt, extra_key, boundary_layer):
    # 1. Split into interleaved reuse / non-reuse segments; pad to block size
    segments = parse_and_pad(prompt)              # [Orig1, Reuse1, Orig2, ...]
    I_nr     = non_reuse_positions(segments)     # the SparseQ probe indices

    # 2. Materialize reused KV: retrieve, allocate, RoPE-align (Section 6.1)
    for S in reuse_segments(segments):
        h_v   = hash(S.token_ids, extra_key)       # namespaced virtual hash
        K_old, V_old = lookup(h_v)                 # virtual block / frozen pool
        blk   = alloc_physical_block()
        blk.K = delta_rope(K_old, delta=S.new_pos - S.old_pos)  # fused kernel
        blk.V = V_old                                # values need no rotation

    # 3. Non-reuse prefix uses native vLLM Prefix Cache; misses prefill fresh
    prefix_cache_fill(non_reuse_prefix(segments))

    # 4. Early layers: full causal attention over ALL positions
    for layer in range(0, boundary_layer):
        H = full_attention(H, layer)

    # 5. Boundary layer: one SparseQ selection (Eqs 1-3, Section 6.2-6.3)
    Q_sq  = Q[I_nr]
    A_sq  = softmax(Q_sq @ K.T / sqrt(d) + M_causal[I_nr, :])
    s     = A_sq.sum(axis=0)                     # per-token importance
    S_key = topk(s, k)
    R     = I_nr | S_key | overflow(I_nr) | tail_fallback   # recompute set

    # 6. Later layers: recompute only R, read aligned cache for the rest
    for layer in range(boundary_layer, L):
        H[R]      = attention(Q[R], K, V, layer)   # sparse-KV recomputation
        H[~R]     = read_aligned_cache(layer)     # reused KV, untouched

    return emit_first_token(H)

Condensed and renamed for readability; the paper's Table 4 gives the exact operator sequence. The essential asymmetry is on the last two lines: only the recompute set $\mathcal{R}$ runs attention in the later layers, while every other reused token is served straight from its RoPE-aligned cache.

7. System Engineering in vLLM

The paper argues that a reuse algorithm only matters if it survives realistic serving constraints — paged KV management, batch scheduling, and GPU-memory watermarks. SparseX-vLLM therefore adds four storage primitives, all designed so that reused segments end up looking exactly like ordinary vLLM blocks by the time they reach the attention backend. The whole system is GPU-resident: it extends Prefix Cache to non-prefix workloads rather than adding a disk/CPU tier, though it composes with such tiers if present.

7.1 The four storage primitives

Each primitive solves one concrete engine problem; together they let one physical block pool serve Prefix Cache, a RAG knowledge base, and user/agent histories at once.

Frozen block

A cached block from knowledge-base prefill that is physically identical to a native vLLM block (same layout, block id, ref-counting) but is not auto-reclaimed when its ref count hits zero — so long-lived RAG knowledge is not evicted during low-reference intervals.

Frozen-block pool

A logical pool that records which blocks belong to the knowledge base, sharing the same physical blocks as native vLLM — no reserved memory region. When KV utilization exceeds a watermark (e.g. 90%), the least-referenced frozen blocks are dropped to protect ordinary requests.

Extra keys

A namespace tag folded into the block hash, so identical token sequences from different knowledge bases or users do not falsely match. A block is reusable only when both token IDs and the extra key agree.

Virtual block

A position-, prefix-, and context-independent index that points at an existing physical block without copying KV, so it adds no GPU memory. On a hit, SparseX allocates a real block and copies the KV in with the fused copy-Delta-RoPE kernel.

The namespace lookup is formalized as a virtual hash over a block's token sequence and its extra key, so multiple logical cache namespaces — ordinary Prefix Cache, RAG knowledge bases, and user histories — coexist inside one physical block pool without interfering:

virtual hash $$h_v = \mathrm{Hash}\big((x_i, x_{i+1}, \ldots, x_{i+b-1}),\; e\big)$$

Here $b$ is the block size and $e$ is the extra key. Ordinary prefix portions keep using vLLM's original prefix hash; only reuse segments use the virtual hash.

Why this matters for reuse benefit. The paper's Section 1.2 critique of prior work is that non-prefix reuse hits, if they cannot cooperate with Prefix Cache, force a request out of the optimized cache framework and reduce long-term hit rate. Virtual blocks and extra keys exist precisely so that a single request can hit ordinary prefix blocks and reused knowledge blocks in the same scheduling round, keeping both mechanisms live.

8. Evaluation

All experiments run on an 8-GPU NVIDIA RTX 4090 server with SparseX-vLLM built on vLLM v1 0.11.0, comparing only against open-source KV-reuse methods reproducible on vLLM; LLM-as-a-judge tasks use GPT-5.1 as the judge. Every workload is a two-stage reuse simulation: a first request builds the reusable segments into the block pool, and a second request recombines them with fresh non-reuse text, on which quality and TTFT are measured. The full-recompute baseline stands in for the Prefix-Cache blind spot — a non-prefix workload where the default cache cannot hit.

9.1 The two-stage reuse request

Every evaluation follows the same protocol, and it is the right mental model for using the system. A first request encodes the reusable content and writes its segment KV into the block pool; a second request recombines those segments with fresh non-reuse text and is the one whose quality and TTFT are measured. The extra key is what makes a segment findable across the two requests and keeps different knowledge bases or users from colliding.

Stage 1 · Cache-build request

Send the reusable text (dialogue history, RAG documents, an agent's analysis) once, tagged with an extra key. Its segment KV completes prefill inside the vLLM engine and is written to the block pool (as a frozen block for a knowledge base, or an ordinary reusable block for a chat/agent history).
↓

Stage 2 · Evaluation request

Send the real prompt, interleaving the same reusable segments (same text + same extra key) with new instructions and a question. SparseX retrieves and RoPE-aligns the segments, runs one SparseQ selection at the boundary layer, and recomputes only the selected tokens. Quality and TTFT are measured here.

9.2 Key parameters to set

Two settings dominate the quality/latency trade-off. The layer boundary controls how much full attention precedes sparse recomputation, and the top-$k$ budget controls how many reused tokens are recomputed at each later layer.

10. Relation to Decontaminated KV Selection

This section positions SparseX against our own thesis, which frames cross-agent KV reuse as a subtractive, per-token, receiver-decision-relevance decontamination problem — distinct from KVCOMM, which performs additive re-alignment of shared KV. SparseX is the closest paper we have found to naming our premise, so it deserves a precise, honest reckoning: what does it actually do, and where does it stop short of — or overlap with — what we claim as new?

10.1 Three questions from the full text

Reading the full paper rather than the abstract, three questions decide how much of our gap it closes.

(a) Importance / relevance selection?

Yes — and this is the honest overlap. SparseQ selects reused tokens by aggregated attention intensity from the non-reuse (receiver) queries: the new instructions and questions vote for which reused tokens they need. That is a per-token, receiver-conditioned relevance selection, not a fixed heuristic. It is materially close to the selection half of our contribution.

(b) Subtraction / decontamination, or only additive repair?

Only additive. SparseX has two repair operators, both additive: a RoPE rotation that adds the correct positional phase, and a fresh recomputation that replaces a selected token's KV under the new context. It never estimates a per-token contaminant and subtracts it; reused tokens outside the selected set keep their original-prefix KV untouched.

(c) Names the contamination phenomenon?

No. The paper calls it 'contextual coupling', 'representation error after a cache hit', and 'poorly controlled representation error'. The word 'contamination' does not appear, and the prefix-induced error is treated as something to route around by recomputing important tokens, not as a signal to be isolated and removed.

10.2 The one-line differentiator

SparseX and KVCOMM both repair reused KV additively — SparseX by recomputing the tokens the receiver's queries vote most important, KVCOMM by adding an anchor-pool offset correction — whereas our thesis subtracts a receiver-conditioned contaminant estimate from each reused token's KV, correcting it in place without a full recomputation and without leaving the unselected tokens contaminated.

SparseX / KVCOMM operator (additive)

  • Align: add the RoPE phase for the new position
  • Select important tokens (SparseQ) / shared tokens (KVCOMM)
  • Repair by recompute (SparseX) or add offset delta (KVCOMM)
  • Unselected reused tokens keep original-prefix KV

Our thesis operator (subtractive)

  • Estimate a per-token contaminant induced by the wrong prefix
  • Weight it by receiver-decision relevance, not just attention mass
  • Subtract it in place — no full recompute of the token
  • Every reused token is decontaminated, not only the top-k

10.3 Honest verdict: does it close or narrow our gap?

The full text does more than the abstract suggested, and that is a genuine novelty consideration we should not soften. Read only as 'segment-level sharing with sparse recompute', SparseX sounds orthogonal to us. Read in full, its SparseQ is a per-token, receiver-query-driven relevance selection over reused tokens — which is materially the selection half of what we were treating as our own contribution. On the selection axis, SparseX (together with CacheBlend and KVCOMM) narrows our gap substantially: 'select which reused tokens matter to the receiver' can no longer be claimed as novel on its own.

It does not, however, close the decontamination axis. Every repair operator in this literature is additive — recompute the important tokens (SparseX), add an offset correction (KVCOMM), patch first-layer deviations (CacheBlend). None estimates and subtracts a per-token contaminant, none treats the prefix-induced error as an isolable quantity to remove rather than a token to recompute, and none names contamination as the object of study. The unselected reused tokens are left as-is in every one of these methods. Our distinctive claim must therefore be sharpened away from selection and onto the operator: a cheap subtractive per-token decontamination that corrects every reused token in place, contrasted against recompute-the-important-ones. SparseX also hands us the strongest possible motivating citation for the premise itself — its prefix-coupling sentence in Section 2 is almost verbatim our starting point.

Novelty threat, stated plainly. SparseX does per-token, receiver-relevance token selection — so the selection component of our idea is no longer novel and should be presented as adopted prior art, not a contribution. What remains open, and what we must defend as the contribution, is the subtractive decontamination operator: correcting each reused token in place by removing an estimated contaminant, rather than recomputing a chosen subset or adding an alignment/offset delta. If a reviewer reads SparseX and KVCOMM together, our paper survives only if that operator distinction is made load-bearing and empirically decisive.

11. Strengths & Limitations

SparseX is a strong systems paper whose contribution is as much engineering as algorithm. The assessment below separates what it establishes from what it leaves open, read from the full text rather than the abstract.

Strengths

  • A genuinely general reuse abstraction: one segment-level loop covers chat, RAG, and agents, with arbitrary interleaving of reused and non-reuse text.
  • The SparseQ probe is free: it reuses queries the request must compute anyway, avoiding the auxiliary model that CacheClip-style methods need.
  • Deep engine integration: virtual blocks, frozen-block pools, extra keys, and a fused copy-Delta-RoPE kernel keep reuse compatible with PagedAttention, Prefix Cache, and FlashAttention/FlashInfer.
  • The layer-wise diagnostic (Figures 5–6) is a real contribution on its own: it shows early-layer KV deviation is layout-sensitive and motivates deferring selection past the early layers.

Limitations

  • The layer boundary is a task- and model-specific hyperparameter (10–20% of layers), tuned rather than derived; the paper offers heuristics, not an automatic setting.
  • Evaluation reports quality and TTFT but no end-to-end throughput or sustained-concurrency numbers, so the engine-level payoff is argued more than measured.
  • Correction is additive-only: unselected reused tokens keep their original-prefix KV, so residual contextual coupling on non-top-k tokens is never removed, only avoided by recomputing the important ones.
  • All experiments use RTX 4090s and the Qwen family; behaviour on other architectures, non-RoPE position schemes, and datacentre GPUs is left to future work.
Bottom line for our project. SparseX narrows our gap on token selection but not on the decontamination operator, and it never names contamination. We should cite its Section 2 prefix-coupling sentence as the premise, adopt SparseQ-style receiver-query selection as prior art rather than contribution, and stake our novelty on subtractive in-place decontamination of every reused token.

11.1 Takeaways for the survey

For a reader scanning this page as one entry in the survey, the four cards below compress what SparseX is, why it matters to our line of work, and how to use it in a citation.

What it is

A training-free, model-agnostic vLLM extension for segment-level KV reuse that supports arbitrary interleaving of reused and fresh text, using receiver queries (SparseQ) to select tokens to recompute and RoPE to realign the rest.

The premise to cite

Its Section 2 prefix-coupling sentence — 'the hidden states and KV tensors of the same text segment often differ under different prefixes and different concatenation positions' — is the locked motivating citation for our decontamination premise.

Overlap with us

Per-token, receiver-relevance token selection (SparseQ) is now prior art. The selection half of our idea is no longer novel and must be presented as adopted, not claimed.

What stays ours

The subtractive operator. SparseX (and KVCOMM) repair additively — recompute or add an offset. Subtracting a receiver-conditioned contaminant in place, for every reused token, remains unclaimed and is where our contribution must live.
