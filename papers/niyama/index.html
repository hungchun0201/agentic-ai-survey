Niyama: Breaking the Silos of LLM Inference Serving

Fine-grained QoS co-scheduling that replaces interactive/batch silos with dynamic chunking and overload-aware prioritization.

Kanishk Goel, Jayashree Mohan, Nipun Kwatra, Ravi Shreyas Anupindi, Ramachandran Ramjee · Microsoft Research India

arXiv:2503.22562ASPLOS program alias: QoServeQoS schedulingA100Sarathi/vLLM

1. Problem

Production LLM serving often separates interactive and batch traffic into infrastructure silos. That coarse split wastes capacity because it cannot express fine-grained QoS classes, and it handles traffic surges poorly: FCFS, EDF, and SRPF each fail under different low-load or overload cases.

Figure 3 from the paper: Niyama system overview.

2. Method

Niyama co-schedules workloads on shared infrastructure using three mechanisms: dynamic chunking that exploits decode-deadline slack, hybrid prioritization that interpolates between EDF and SRPF, and eager relegation that proactively moves soon-to-violate requests to a lower-priority queue during overload.

Dynamic chunkingUse slack to enlarge prefill chunks when safe.
Hybrid priorityBalance fairness and efficiency through EDF/SRPF interpolation.
Eager relegationGracefully degrade a small subset to avoid cascading SLO failures.

The evaluation uses Azure-Code, Azure-Conv, and ShareGPT token distributions on A100 hardware, with Sarathi-style chunked prefill as the implementation substrate.

4. Relation to This Repo

  • Niyama is scheduling-level evidence that the predictable structure of LLM inference can support admission and chunk-size decisions.
  • Its random-forest chunk-size predictor contrasts with the repo objective of using fit-light or fit-free closed-form latency prediction.
  • For the paper related-work section, Niyama should be categorized as QoS scheduling and chunked-prefill capacity management rather than per-step GPU latency decomposition.

5. Limitations

Niyama is built around Sarathi/vLLM-style chunked prefill and profile-trained prediction. Its results are strong for QoS scheduling, but it does not explain kernel dispatch, attention efficiency, or hardware portability at the level targeted by the current predictor.
