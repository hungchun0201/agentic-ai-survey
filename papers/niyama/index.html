Niyama: Breaking the Silos of LLM Inference Serving

A QoS-driven serving system that replaces interactive-versus-batch silos with fine-grained co-scheduling, combining dynamic chunking, a hybrid EDF/SRPF priority, and eager relegation under overload

1. Overview & Motivation

Niyama is a serving system that schedules every request in a single GPU pool against an explicit quality-of-service (QoS) contract, rather than partitioning the hardware into an interactive cluster and a batch cluster as production stacks do today. The motivation rests on a single observation: by 2025 the traffic arriving at a shared inference endpoint is no longer separable into two tidy classes, and any deployment that hard-partitions GPUs by class either strands capacity in the idle silo or violates the deadlines of the over-subscribed one. This section first establishes why the workload has changed, walks through one request-level failure of a conventional scheduler, quantifies the cost of the status quo, dismisses the obvious fix, identifies the structural obstacle, and positions Niyama against its immediate predecessors before presenting its contributions.

Banner (from paper): Niyama co-schedules every request on a single shared GPU pool under per-request QoS contracts, in contrast to the siloed deployments that split hardware into a separate interactive cluster and batch cluster. Co-scheduling lets the idle headroom of one class absorb the load of another within the same iteration.

1.1 Why Now: One Endpoint, Many Coexisting QoS Classes

Pre-2024 serving stacks were calibrated for a workload with one dominant latency objective per deployment: an interactive chat endpoint optimized for time-to-first-token, or an offline batch endpoint optimized for throughput. By 2025 a single production endpoint receives a mixture of these alongside a third class that did not previously exist at scale. A representative hour of traffic now interleaves streaming chat, where a user reads a reply token by token; large batch summarization and document-processing jobs, where only the completion time matters; and agentic workflows that issue tens to hundreds of dependent model calls under one end-to-end budget. The paper's evaluation models this directly with three coexisting QoS tiers carrying a 6-second time-to-first-token target, a 600-second completion target, and a 1800-second completion target, present in equal one-third proportions in the same arrival stream. Three latency contracts therefore coexist in one queue, and a scheduler that optimizes any single objective violates at least one of the other two on every batch.

Each tier is anchored in a concrete user-facing scenario. The interactive tier corresponds to a person who opens a chat assistant and reads the streaming answer at roughly human reading speed; the contract is a fast first token (a 6-second time-to-first-token budget) followed by a steady inter-token cadence (a 50-millisecond time-between-tokens budget) so the text does not stall mid-sentence. The second tier corresponds to a batch summarization job submitted by a back-office pipeline that must finish within ten minutes but is indifferent to when individual tokens appear. The third tier corresponds to an even more relaxed overnight processing job with a thirty-minute completion budget. The same GPU pool must honor all three at once, and their relative mix shifts hour to hour.

1.2 A Concrete Bad Scenario: A Late Interactive Prefill Under Earliest-Deadline-First

Consider an endpoint serving Llama-3-8B on a single A100, configured with the three tiers above, that admits requests in earliest-deadline-first order. A user submits an interactive chat request whose 1,730-prompt-token prefill must produce its first token within the 6-second budget. Earliest-deadline-first correctly assigns this request the most urgent deadline and would, in isolation, schedule it first. The difficulty appears when a burst of arrivals drives the system briefly above capacity: the chunked-prefill executor processes the long prompt one bounded chunk per iteration, and during those iterations earliest-deadline-first must also advance the inter-token deadlines of every interactive request already decoding. As the queue builds, the prefill chunks of the new request are repeatedly deferred behind decode steps that are themselves close to their own per-token deadlines, the 6-second budget elapses before the prompt finishes prefilling, and the request misses its first-token target. The scheduler then continues to spend iterations completing a request that has already failed its contract, capacity that could have protected a request still within budget.

1.3 The Quantified Baseline Pain

The paper supplies the status-quo numbers that justify treating mixed-QoS scheduling as a first-order problem. Earliest-deadline-first, which behaves well at moderate load, exhibits a violation rate that rises sharply once load crosses a threshold: the paper reports that its deadline-violation rate spikes to nearly 100% in the strictest QoS class once the offered load exceeds the point where the queue can no longer drain. First-come-first-served fares worse still under burst, where head-of-line blocking by a long prompt denies service to every request behind it regardless of deadline. Against this status quo, Niyama sustains zero deadline violations up to 30% higher load than Sarathi-EDF and continues to meet latency targets for over 95% of requests even at 50% above the nominal serving capacity, where the baseline schedulers fail outright. The gap between a near-100% violation rate and a sub-5% violation rate at the same offered load is the quantity Niyama is designed to close.

Figure 2 (from paper): Comparison of traditional policies for multi-SLA scheduling. The plots show latency and deadline-violation rate in the strictest QoS class as offered load increases. Each policy is a local optimum: earliest-deadline-first holds violations near zero at moderate load but then rises steeply, while shortest-remaining-prefill-first sustains throughput under load but deprioritizes long requests even when no congestion exists.

1.4 Strawman: Static Per-Class Silos

The obvious response is the one production stacks already deploy: provision a separate GPU pool for each QoS class and route each request to its pool. This is the siloed deployment that Niyama's title refers to, and it fails for a structural reason rather than an implementation one. The mix of classes is not stationary. An hour in which 80% of arrivals are batch jobs leaves the interactive pool nearly idle while the batch pool is over-subscribed, and an hour in which the mix inverts produces the opposite imbalance. Correcting this requires moving GPU capacity between pools at the timescale on which the mix changes, which is the original mixed-QoS scheduling problem restated one level up: deciding how much capacity each class should receive at each instant is exactly the decision a co-scheduler makes per iteration, except that rebalancing whole GPUs is far coarser and slower than rebalancing the contents of a single batch. The paper measures the cost of this rigidity directly: meeting the same QoS targets under siloing requires 13–32% more A100 GPUs than co-scheduling the identical traffic.

1.5 The Fundamental Obstacle: Each Policy Is a Local Optimum Under Output-Length Uncertainty

The reason no single classical policy suffices is structural. Each of first-come-first-served, shortest-job-first / shortest-remaining-prefill-first, and earliest-deadline-first is the correct policy under a different unstated assumption, and those assumptions do not hold simultaneously on the 2025 workload. First-come-first-served is fair when every request has the same value and arrivals are below capacity, but under burst it permits a long prompt to head-of-line block every request behind it. Shortest-remaining-prefill-first maximizes throughput when the objective is to clear the most requests, yet at low load it needlessly deprioritizes long requests that have ample deadline slack, and it ignores the relative importance of requests entirely. Earliest-deadline-first is optimal when capacity is sufficient to meet all deadlines, but once offered load exceeds capacity it admits requests strictly in deadline order without regard to remaining work, so a cascade of near-deadline requests are all advanced together and all miss, driving the violation rate toward 100%. Compounding this, the true output length of a request is unknown at arrival, so the scheduler cannot compute remaining decode work exactly; it must schedule under genuine uncertainty rather than merely choose a better policy. Niyama's design returns to this obstacle repeatedly: dynamic chunking acts on deadline slack that exists because of this uncertainty, the hybrid priority interpolates precisely between the two policies whose assumptions hold at opposite load regimes, and eager relegation is the explicit admission that under overload some requests must be sacrificed deliberately rather than allowed to fail in a cascade.

1.7 Contributions

Having established that a single classical policy cannot serve the mixed-QoS workload and that static siloing wastes capacity, the paper proposes a co-scheduler that combines three complementary mechanisms. The cards below summarize each contribution at the level of what it does and which obstacle it addresses; the mechanism section develops each one with its formulation.

Contribution 1: Dynamic Chunking

Opportunistically enlarges each prefill chunk by exploiting the decode-deadline slack of in-flight requests, with the maximum safe chunk size predicted by a lightweight random forest trained on Vidur simulator profiles. This recovers throughput that a fixed small chunk would leave unused.

Contribution 2: Hybrid Prioritization

Computes a request priority that interpolates linearly between earliest-deadline-first and shortest-remaining-prefill-first through a single parameter $\alpha$, so the scheduler behaves like the deadline-driven policy at low load and absorbs the throughput-driven policy as load rises.

Contribution 3: Eager Relegation

Under overload, proactively moves a small fraction of soon-to-violate requests — about 5% — into a lower-priority relegated queue so the remaining requests still meet their contracts, converting a cascading failure into a bounded, deliberate degradation.

2. Architecture and QoS Model

Niyama formalizes the latency contract of each request before any scheduling decision is made, because the three mechanisms all operate on deadlines derived from that contract. The QoS model distinguishes two request types — interactive and non-interactive — and converts each request's service-level objective into one or more absolute deadlines measured from its arrival time. The scheduler then runs on top of a chunked-prefill executor, computing a priority for every waiting and decoding request once per iteration and assembling the next batch from the highest-priority work that fits the iteration's token budget.

2.1 Two Request Types, Three Deadlines

An interactive request carries two service-level objectives: a time-to-first-token target that bounds how long the user waits before any text appears, and a time-between-tokens target that bounds the gap between successive tokens during decoding. A non-interactive request carries a single time-to-last-token target that bounds total completion time and is indifferent to intermediate token timing. Niyama converts these objectives into absolute deadlines as follows, where $t_{arrival}^{i}$ is the arrival time of request $i$ and $n$ indexes the output tokens.

(1) $$D_{first}^{i} = t_{arrival}^{i} + SLO_{TTFT}^{i}$$
(2) $$D_{n}^{i} = t_{arrival}^{i} + SLO_{TTFT}^{i} + (n-1)\cdot SLO_{TBT}^{i}$$
(3) $$D_{total}^{i} = t_{arrival}^{i} + SLO_{TTLT}^{i}$$

Equation (1) sets the first-token deadline for an interactive request, and equation (2) extends it so the deadline of the $n$-th token advances by one time-between-tokens budget per token, which is why a request whose decoding stalls accumulates urgency token by token. Equation (3) sets the single completion deadline for a non-interactive request. The same absolute-deadline representation is used by all three mechanisms, so dynamic chunking, hybrid prioritization, and eager relegation each operate on a uniform notion of how close a request is to violating its contract.

2.2 The Per-Iteration Scheduling Loop

The diagram below traces the work Niyama performs on each iteration of the chunked-prefill executor. Every box is colored by role: deadline computation in blue, the priority and admission logic in the accent color, the relegation branch in red, and the dynamic-chunk decision in orange. The loop is the same regardless of which QoS classes are present; the mechanisms differ only in how they weigh the deadlines computed in step one.

↓

Compute the decode-deadline slack of the in-flight decoding requests, then ask the random-forest predictor for the largest prefill chunk that fits within that slack without violating any decoder's next-token deadline (Section 3.1).

Pack the highest-priority decode steps and the sized prefill chunk into one iteration's token budget, run the forward pass, emit tokens, and return to step one.

Architectural insight: Niyama adds no new execution primitive to the chunked-prefill backend — it neither preempts mid-kernel nor introduces a second model copy. Every mechanism is a decision made once per iteration about which requests enter the batch and how large the prefill chunk is, which keeps the scheduler compatible with the existing Sarathi-Serve executor and bounds its per-iteration cost to a sort plus a single random-forest inference.

3. Core Mechanisms

The three mechanisms address the three faces of the fundamental obstacle from Section 1.5. Dynamic chunking recovers throughput from the deadline slack that output-length uncertainty creates; hybrid prioritization adapts the ordering policy across load regimes so the scheduler is never locked into the assumption of a single classical policy; and eager relegation converts the cascading failure of earliest-deadline-first under overload into a bounded, deliberate degradation. Each subsection states the plain idea first, gives the paper's formulation, and then discusses the subtlety that makes the mechanism non-obvious.

3.1 Dynamic Chunking and the Random-Forest Chunk-Size Predictor

Chunked-prefill executors split a long prompt into bounded chunks so that a large prefill does not stall the decode steps batched alongside it. A fixed chunk size is a compromise: a small chunk protects the inter-token cadence of decoding requests but wastes throughput when those requests have plenty of deadline slack, while a large chunk maximizes prefill throughput but can push a decoder past its next-token deadline. Dynamic chunking removes the compromise by sizing the chunk per iteration against the slack actually available. The slack of a decoding request is the time remaining until its next-token deadline minus the time the current iteration will take, and the largest safe prefill chunk is the one whose added iteration latency still fits within the smallest such slack across all in-flight decoders.

The decoding requests Q1, Q2, and Q3 each carry some headroom before their next-token deadline; the hatched orange band is the aggregate slack, and dynamic chunking grows the prefill chunk to fill it rather than emitting a small fixed chunk and leaving the band idle.

Predicting the iteration latency of a candidate chunk is the part that resists a closed-form solution, because latency depends on the chunk size, the number and lengths of the co-batched decode requests, the model, and the hardware. Niyama predicts it with a lightweight random forest trained on performance profiles collected from the Vidur LLM inference simulator, which can sweep batch compositions far faster than running them on the physical GPU. The pseudocode below — derived from the paper's description rather than copied from a released codebase, since no public implementation accompanies the paper — expresses the per-iteration chunk-sizing decision the scheduler makes in step four of the loop.

# Paper-derived pseudocode (not repo source): per-iteration dynamic chunk sizing.
def choose_chunk_size(decoders, rf_predictor, max_chunk):
    # Slack of a decoder = time to its next-token deadline, minus this iteration.
    slack = min(d.next_token_deadline - now() for d in decoders)
    # Search downward from the executor's maximum chunk for the largest chunk
    # whose predicted added iteration latency still fits inside the slack.
    for chunk in candidate_sizes(max_chunk):        # large -> small
        latency = rf_predictor.predict(chunk, decoders)  # Vidur-trained random forest
        if latency <= slack:
            return chunk
    return min_chunk()                            # fall back to the smallest safe chunk

The subtlety is that the predictor's error is asymmetric in consequence. If it under-estimates iteration latency and the scheduler selects a chunk that is in fact too large, an in-flight decoder can miss its next-token deadline; if it over-estimates, the only cost is a smaller chunk and slightly lower throughput. Niyama therefore treats the predicted latency as a constraint to respect conservatively rather than a target to maximize, and the random forest is favored over a heavier model because it must run once per iteration inside the scheduling loop, where a 200-millisecond inference would itself consume an iteration's worth of time. The paper validates the mechanism end to end through serving-capacity and violation metrics rather than reporting the predictor's standalone error, so its accuracy is established by the downstream QoS it sustains rather than by a reported mean error.

Stated formally, the chunk-sizing rule maximizes the prefill chunk subject to a deadline-safety constraint. Let $c$ be a candidate chunk size, $\hat{T}(c, B)$ the random forest's predicted iteration latency given the co-batched decode set $B$, and $s_j = D_{next}^{j} - t_{now}$ the slack of decoder $j$. The chosen chunk is the solution to the constrained maximization below, which the pseudocode implements by searching candidate sizes from large to small and returning the first that satisfies the constraint.

(6) $$c^{\star} = \max \; c \quad \text{subject to} \quad \hat{T}(c, B) \le \min_{j \in B} \, s_j$$

A concrete instance makes the trade-off tangible. Suppose three interactive requests are decoding, each carrying a 50-millisecond time-between-tokens budget, and the most urgent of them has 18 milliseconds remaining until its next-token deadline, so the binding slack is $\min_j s_j = 18$ ms. A small fixed chunk that the executor might default to could complete the iteration in 9 milliseconds, leaving 9 milliseconds of the slack unused. Dynamic chunking instead queries the predictor for the largest chunk whose predicted iteration latency stays at or below 18 milliseconds, growing the prefill so that the iteration lands just inside the budget rather than well short of it. The recovered prefill work is precisely the throughput that a fixed small chunk would have left on the table, and because the constraint is anchored to the tightest decoder, no decode request is pushed past its own deadline in the process.

3.2 Hybrid Prioritization: Interpolating EDF and SRPF

The two policies whose assumptions hold at opposite ends of the load spectrum are earliest-deadline-first, which is correct when capacity is sufficient, and shortest-remaining-prefill-first, which sustains throughput when it is not. Rather than committing to either, Niyama assigns each request a priority value that is a linear combination of a deadline term and a remaining-work term, controlled by a single parameter $\alpha$. A request with the smallest priority value is served first. The priority of an interactive request and of a non-interactive request are defined as follows, where $Prefill_{rem}^{i}$ and $Decode_{rem}^{i}$ are the remaining prefill and decode tokens of request $i$.

(4) $$P^{i} = t_{arrival}^{i} + SLO_{TTFT}^{i} + \alpha \cdot Prefill_{rem}^{i} \quad\text{(interactive)}$$
(5) $$P^{i} = t_{arrival}^{i} + SLO_{TTLT}^{i} + \alpha \cdot \left(Prefill_{rem}^{i} + Decode_{rem}^{i}\right) \quad\text{(non-interactive)}$$

When $\alpha = 0$, the priority reduces to $t_{arrival}^{i} + SLO^{i}$, which is exactly the absolute deadline, so the policy is pure earliest-deadline-first. As $\alpha$ grows, the remaining-work term increasingly dominates, and a request with less remaining work receives a smaller priority value and is served sooner, which is the shortest-remaining-prefill-first behavior. The single parameter therefore slides the scheduler continuously between the two regimes: a small $\alpha$ honors deadlines when capacity allows it, and a larger $\alpha$ favors clearing short work as the queue lengthens. The subtlety is that the benefit of hybrid prioritization is regime-dependent, which is why an ablation that measures it at a single operating point understates its value. At an optimal load the paper reports that adding hybrid prioritization on top of the other two mechanisms contributes only a small marginal improvement, because near that load earliest-deadline-first alone is close to correct. The contribution becomes significant at high load, where the remaining-work term prevents the deadline-only policy from advancing a cascade of near-deadline requests that would all miss. The interpolation is also the reason a single static $\alpha$ is workable across the trace: because the term it scales is remaining work, its influence automatically grows as the queue fills with work and shrinks as the queue drains, without retuning per load level.

The sensitivity sweep shows that the deadline term ($\alpha = 0$) suffices at moderate load, while a non-zero remaining-work weight reduces violations as load rises, confirming that the benefit of the interpolation is concentrated in the high-load regime.

3.3 Eager Relegation Under Overload

When offered load exceeds capacity, some deadlines cannot be met no matter how the batch is ordered, and the failure mode of earliest-deadline-first is that it spreads the inevitable misses across the whole queue: it keeps advancing near-deadline requests until a large block of them all miss together. Eager relegation makes the sacrifice deliberate and small instead. If a request has already violated its first-token or completion deadline, or will violate it in the current iteration, Niyama moves it into a lower-priority relegated queue, where it is served only with capacity left over after the main queue is satisfied. Removing a request that is already lost frees the capacity it would have consumed for requests that are still within budget, which is the difference between sacrificing one request and losing the block of requests queued behind it.

The relegation decision also incorporates request importance through application hints. In a multi-tenant deployment, a free-tier request and a paid-tier request may carry the same deadline but not the same value, so Niyama preferentially relegates the lower-priority request first when a sacrifice must be made. The pseudocode below — again paper-derived rather than repo source — captures the relegation test applied to each request in step three of the per-iteration loop.

# Paper-derived pseudocode (not repo source): eager relegation test, run per request.
def relegate_if_doomed(req, main_queue, relegated_queue):
    deadline = req.current_deadline()          # D_first, D_n, or D_total per QoS class
    if now() > deadline or req.will_violate_this_iter(deadline):
        relegated_queue.add(req, tier=req.app_hint)  # free-tier relegated before paid-tier
        main_queue.remove(req)
    # Relegated requests are served only with capacity left after the main queue.

The subtlety is the word eager. A reactive scheme would relegate a request only after it has already failed, by which point the capacity spent advancing it toward its now-missed deadline is already gone. Relegating proactively, the moment a violation becomes certain for the current iteration, reclaims that capacity before it is wasted, and the paper reports that relegating just 5% of requests is enough to maintain the median request's QoS even under very high overload. The mechanism is deliberately conservative in how much it relegates, because relegating too aggressively would degrade requests that the remaining slack could still have served; the 5% figure reflects the small fraction that genuinely cannot be saved at the measured overload.

Eager relegation also composes with the hybrid priority rather than overriding it. The priority computed in step two determines the order in which the main queue is served, while relegation in step three removes from that queue only the requests whose violation is already certain, so the two mechanisms operate on disjoint sets: the priority governs requests that can still be saved, and relegation governs those that cannot. This separation is what allows the relegated queue to remain non-empty without harming the main queue, because a relegated request consumes capacity only when the main queue has been fully served for the iteration. In the multi-tenant case the application hint refines the order of relegation within the doomed set, so when two requests are equally certain to miss, the lower-value one is set aside first and the higher-value one retains the residual capacity. The combined effect across the four-hour transient trace is that no important task is missed at all, and the residual 8.75% of misses fall on the least-valuable requests, which is the bounded, deliberate degradation the mechanism is designed to produce.

4. Performance Results

Niyama is evaluated on a hardware testbed of NVIDIA A100 80GB GPUs, serving Llama-3-8B on a single A100 and Qwen-7B with tensor parallelism across two A100s, against three production-derived workloads with Poisson arrivals over the trace's prompt and decode token distributions. The evaluation reports effective serving capacity and goodput, defined as the number of requests served per second while meeting their p99 latency targets, with at most 1% of requests permitted to violate their deadlines. The headline result is that Niyama increases serving capacity by 32% compared to current siloed deployments while maintaining QoS guarantees.

4.3 Behavior Under Overload

The overload study is where the difference between a local-optimum policy and Niyama's adaptive scheduler is largest. Under extreme overload at 50% above the nominal serving capacity, Niyama continues to meet latency targets for over 95% of requests, whereas the baseline schedulers fail outright. In a transient test driving load dynamically between 2 and 6 QPS over four hours, Niyama misses deadlines for no important task and for only 8.75% of all requests, while the baselines collapse. These results follow directly from eager relegation, which prevents the cascading miss, and from the hybrid priority, whose remaining-work term dominates precisely in this regime.

5. Limitations and Scope

The assessment below is drawn from the paper's own scope statements and from the structure of its mechanisms; no public implementation accompanies the paper, so every entry reflects the reported design rather than independent reproduction. The strengths column captures what the evidence in the paper supports, and the limitations column captures the assumptions on which the reported gains depend.

Strengths

  • ✓ A single scheduler adapts across load regimes through one parameter, rather than committing to a policy that is only locally optimal.
  • ✓ Co-scheduling reclaims the capacity that siloing strands, reducing A100 GPU demand by 13–32% at the same QoS.
  • ✓ Eager relegation converts the cascading overload failure of earliest-deadline-first into a bounded degradation of about 5% of requests.
  • ✓ The scheduler adds no new execution primitive, remaining compatible with the existing chunked-prefill backend and bounding per-iteration cost.

Limitations

  • △ Non-interactive decode length is not known at arrival; it is approximated from per-application history, over-approximated by two standard deviations to set the deadline term.
  • △ Eager relegation assumes a roughly 5% fraction of requests can be safely degraded, which holds at the measured overload but is a tolerance the operator must accept.
  • ✗ The implementation is coupled to the Sarathi-Serve / vLLM chunked-prefill execution model and is not demonstrated on other execution backends.
  • ✗ Evaluation is limited to A100 GPUs and Llama-3-8B / Qwen-7B-class models; behavior on larger models or newer hardware is not reported.

6. Reproduction Sketch (Paper Configuration)

The following sketch records the experimental configuration as the paper reports it, so a reader can reconstruct the evaluation environment even though no public implementation is released. It is presented as a paper-only specification, not as a tested runnable recipe; the parameters are those the paper states for its hardware testbed, its models, and its workloads.

6.1 Hardware and Models

The testbed uses NVIDIA A100 80GB GPUs. Llama-3-8B is served on a single A100, and Qwen-7B is served with tensor parallelism across two A100s; the capacity study extends to a shared cluster. The configuration below summarizes the reported setup.

# Paper-reported configuration (specification only; no public code release).
hardware:
  gpu: NVIDIA A100 80GB
  llama_3_8b:  1x A100                 # single GPU
  qwen_7b:     2x A100  (tensor_parallel=2)
  capacity_study: shared cluster (up to ~76 GPUs)
backend:
  executor: chunked-prefill (Sarathi-Serve / vLLM lineage)
predictor:
  model: random_forest                 # lightweight, runs once per iteration
  trained_on: Vidur LLM inference simulator profiles

The choice of a random forest for the chunk-size predictor is tied to this hardware setup: the predictor runs inside the per-iteration scheduling loop, so its inference must complete in well under one iteration's time, which rules out the heavier models that a length-prediction task might otherwise invite. Training on Vidur profiles rather than on physical-GPU traces is what makes sweeping the batch-composition space tractable.

6.2 QoS Tiers and Workloads

The reported evaluation divides arrivals equally among three QoS tiers and drives them with Poisson arrivals over the prompt and decode distributions of three production traces. The specification below lists the tier targets and the workloads used to populate them.

# Paper-reported QoS tiers (Table 2) and workloads (Table 1).
qos_tiers:                               # each = 33.33% of traffic
  Q1: { type: interactive,     SLO_TTFT: 6s,   SLO_TBT: 50ms }
  Q2: { type: non_interactive, SLO_TTLT: 600s }
  Q3: { type: non_interactive, SLO_TTLT: 1800s }
arrivals: poisson                        # over trace prompt/decode token distributions
workloads:
  sharegpt:    { prompt_p50: 1730, decode_p50: 415 }
  azure_conv:  { prompt_p50: 928,  decode_p50: 41 }
  azure_code:  { prompt_p50: 1930, decode_p50: 8 }
goodput_metric:                          # effective serving capacity
  served_per_sec_meeting_p99: true
  max_deadline_violation: 1%

The goodput metric is the quantity all the headline numbers are measured against: a request counts toward goodput only if it meets its p99 latency target, and a run is considered to meet QoS if at most 1% of requests violate their deadlines. Holding this metric fixed is what makes the cross-workload comparison meaningful, because Azure-Code, Azure-Conv, and ShareGPT impose different prefill-versus-decode balances on the same scheduler. For the non-interactive tiers, the decode length needed to set the deadline term is not known at arrival and is over-approximated from per-application history by two standard deviations, which is the conservative estimate the scheduler uses when it cannot observe the true output length.
