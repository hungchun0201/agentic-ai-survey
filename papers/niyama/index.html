QoS-aware capacity scheduling for shared LLM fleets

Niyama: QoS-Driven LLM Inference Serving

A deadline-aware Sarathi-Serve branch that co-schedules interactive and batch requests instead of siloing them.

Authors Kanishk Goel, Jayashree Mohan, Nipun Kwatra, Ravi Shreyas Anupindi, Ramachandran Ramjee
Affiliation Microsoft Research India
Venue and version ASPLOS 2026, arXiv 2503.22562v1
Page scope Deadline-aware admission, dynamic chunk sizing, and Sarathi-Serve implementation branch

Core Question

Niyama treats QoS as scheduler state. The serving problem is not only how many tokens per second a GPU can produce, but whether different request classes meet their deadlines on a shared fleet.

The scheduler combines deadline-aware priority, dynamic prefill chunking, and KV-cache admission so urgent work can progress without permanently starving background work.

Motivation Ladder

The design is a QoS-control layer, not a faster kernel. Its capacity improvement comes from admitting work with awareness of deadlines, predicted chunk cost, and KV-cache space.

The Sarathi-Serve branch exposes the relevant pieces in deadline scheduling, sequence tier fields, chunk-size prediction, and deadline-aware block-space management.

1

Why now

LLM providers increasingly serve interactive users, background jobs, and product tiers on shared GPU fleets. Coarse siloing makes capacity planning simple, but it wastes slack when one class is underloaded and another class is saturated.

The motivation is deadline-aware capacity, not average throughput alone. Niyama treats each request's QoS target as part of the scheduling state.

2

Concrete bad scenario

During a burst, interactive requests and batch requests compete for the same model. FCFS can let long prefill work delay short interactive deadlines, while pure EDF can chase urgent work and harm throughput stability.

The bad case shows why overload cannot be handled by one global queue rule. A request with little slack and a request with generous slack should not receive identical prefill treatment.

3

Baseline pain

Sarathi-Serve chunking improves batching, but a fixed chunk size cannot satisfy all QoS classes. The paper reports that smaller chunks can protect latency while reducing throughput, and larger chunks can increase deadline risk.

The baseline pain motivates dynamic chunking rather than a fixed chunk size. Chunking has to reflect both predicted cost and remaining deadline slack.

4

Strawman

A simple rate limiter or strict priority queue can protect premium traffic. That leaves idle opportunities unused and can let lower-priority jobs starve even when serving them would not harm urgent deadlines.

A pure deadline order is not enough because GPU work is admitted in chunks. The scheduler must decide how much prefill to run, not only which request comes first.

5

Fundamental obstacle

The scheduler must decide both which request to serve and how large a prefill chunk to admit. Those choices interact with decode slack, remaining prefill length, predicted output length, GPU memory budget, and per-tier deadlines.

The hard part is coupling prediction, admission, and KV-cache space management. Missing any piece can either violate deadlines or leave capacity unused.

6

Position against nearby systems

Niyama builds on Sarathi-Serve rather than replacing the model executor. Its contribution is QoS-aware scheduling: dynamic chunking, hybrid prioritization, eager relegation, and selective prefill admission.

This position makes Niyama a QoS-control layer for serving rather than a faster kernel. Its contribution is deciding when and how much work should enter the GPU.

Claim Boundaries

The claim is not lower latency for every request. It is higher goodput under tiered deadlines by admitting work only when slack and memory permit it.

The Sarathi-Serve branch validates the scheduler mechanisms, but it also exposes experiment-specific choices such as randomized tier assignment.

System Map

The system map runs from request tier and slack to chunk-size prediction and block-space allocation. It is a scheduler-control problem rather than a kernel-optimization problem.

Dynamic chunking is the hinge: the scheduler decides not only who runs next, but how much prefill work can safely run before a deadline is endangered.

Design Equation

The equation captures Niyama’s decision shape: rank candidates by priority, then admit the largest prefill chunk whose predicted cost fits the remaining slack.

The prediction term is critical. Wrong chunk-cost estimates can turn deadline-aware scheduling into either missed deadlines or unused GPU capacity.

This summarizes the hybrid priority and dynamic chunk sizing logic: priority chooses the candidate, while the chunk rule admits only work that fits remaining slack.

Mechanism Deep Dive

Niyama combines priority, prediction, and admission. It chooses which request runs and how large a prefill chunk can be without consuming too much deadline slack.

The design is not a faster kernel. It is a control layer that attempts to keep high-priority deadlines while still filling unused capacity with lower-priority work.

Deadline metadata

The source branch defines tier deadlines of 6, 600, and 1800 seconds and assigns each request a tier. For TTLT-style tiers, TTFT deadline is reduced by predicted decode time.

Hybrid prioritization

The sequence comparator combines arrival plus deadline with a remaining-token term, and the scheduler can emulate FCFS, EDF, SRPF, or the deadline policy.

Dynamic chunking

The scheduler uses a stratified linear latency model over total tokens, prefill tokens, decode tokens, decode context, and prefill context. It then searches token budgets to fit within slack.

Eager relegation

If remaining prefill service time is predicted to exceed a request’s deadline, the implementation increments a drop marker and pushes the request back behind viable work.

Interaction Among Pieces

Niyama’s pieces interact through slack. Hybrid priority chooses the next candidate, dynamic chunking sizes the work, and block-space management decides whether the request can be admitted.

Eager relegation is the failure-control path. When predicted service time exceeds the deadline budget, the scheduler avoids spending scarce GPU time on work that is already unlikely to count as goodput.

Implementation Trace

The Sarathi-Serve branch implements the scheduling path. Deadline scheduling, sequence tier state, chunk-size prediction, and deadline-aware block management all appear as concrete code paths.

The branch also reveals experimental simplifications. Tier assignment in `Sequence` is randomized for experiments, which is different from a production admission-control interface.

  • `sarathi/core/scheduler/deadline_scheduler.py` contains the main scheduling loop, dynamic prefill sizing, and eager relegation condition.
  • `sarathi/core/datatypes/sequence.py` defines tier deadlines, hybrid priority comparison, and TBT deadline calculation.
  • `chunk_size_predictor/predictor.py` trains stratified linear models over batch token and context features.
  • `fig7_tiny.sh`, `fig10_11_tiny.sh`, and related scripts encode the experiment sweeps for FCFS, EDF, SRPF, and deadline scheduling.

Prototype Boundary

The implementation therefore supports the mechanism but not every deployment assumption. A production system would need real tier assignment, admission policy, and monitoring integration.

Prediction quality is a central boundary. If chunk-cost prediction is wrong, the scheduler can either miss deadlines or leave throughput unused.

Evaluation Discipline

Niyama’s evaluation should be judged by goodput under deadlines, not raw throughput alone. Deadline violations are part of the objective, not a secondary metric.

The transient-overload experiments are especially important because they test the scheduler’s refusal to spend prefill time on requests that cannot still meet their deadline.

Limitations and Failure Modes

The main limitation is deployment realism. The paper’s scheduler needs accurate QoS classes, predicted prefill costs, and enough request diversity to exploit slack.

The second limitation is interaction with memory pressure. Deadline-aware choices still depend on KV-cache availability and block-space management.

Prototype branch

The public code is a specialized Sarathi-Serve branch. Its README states that Sarathi-Serve is a research prototype and not feature-complete with vLLM.

Predictor dependence

Dynamic chunking depends on latency prediction quality. The source contains hard-coded fitted coefficients in the scheduler plus a separate training script.

Policy assumptions

The public branch randomly assigns tiers in `Sequence`, which is suitable for experiments but different from a production admission-control interface.

Takeaways

The main lesson is that capacity is not a single number under QoS. The same GPU can be either overloaded or underused depending on how deadlines and chunks are scheduled.

The second lesson is that chunk size is a QoS decision. It controls both how quickly urgent work progresses and how much batching efficiency remains.

  • QoS-aware serving needs both ordering and chunk-size control.
  • Relegating work that cannot meet a deadline can improve system-wide deadline health.
  • The Sarathi-Serve branch implements the scheduler path, so the paper is not only a conceptual policy.

Bottom Line

Niyama’s contribution is to make QoS explicit in admission and chunk sizing. It converts slack into shared capacity instead of enforcing hard silos.

Its operational risk is prediction and tier accuracy. Bad chunk-cost estimates or artificial tier assignment can make the scheduler’s decisions look better than they would in production.

Best use case

Shared serving fleets where interactive deadlines and background throughput must coexist.

Main risk

Prediction error or unrealistic tier assignment can distort the scheduler’s deadline decisions.
