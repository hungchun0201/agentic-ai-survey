PAT: Prefix-Aware Attention for LLM Decoding

A pack-forward-merge decode-attention design that packs queries by shared prefix, runs a resource-efficient multi-tile CUTLASS kernel selected per prefix group, and merges partial results with online softmax to eliminate redundant KV-cache reads

Jinjun Yi, Zhixin Zhao, Yitao Hu, Ke Yan, Weiwei Sun, Hao Wang, Laiping Zhao, Yuhao Zhang, Wenxin Li, Keqiu Li

Tianjin University · Stevens Institute of Technology

1. Overview & Motivation

During LLM decoding, attention is the component that reads the key-value (KV) cache from GPU global memory once per generated token, and that read is bounded by memory bandwidth rather than by arithmetic throughput. PAT observes that the requests in a modern serving batch increasingly share large hierarchical prefixes — a system prompt, a tool catalogue, a chat template, or a retrieved document set — and that conventional decode-attention kernels load each shared prefix from global memory once for every query that uses it. PAT restructures decode attention into three stages, pack, forward, and merge, so that a shared prefix is read once for the whole group of queries that depend on it, while the kernel that performs the read is chosen to fit the on-chip resources available for that particular group.

Figure 1 (from paper): Latency breakdown of Llama-3-8B and Qwen3-8B decoding across context length on A100 under vLLM v0.9.0 at batch size 64. As context length grows, the attention component grows to dominate per-step latency, reaching up to roughly 68% of the decode step, while linear projections and other operators stay comparatively flat.

1.1 Why Now: Shared Prefixes Have Become the Common Case

The decode-attention bottleneck that PAT addresses is a consequence of how 2025 inference traffic is composed, not a property of attention in the abstract. Three shifts coincide. First, the requests in a single serving batch now routinely overlap in their leading tokens: agentic pipelines replay a fixed tool catalogue and a planning template on every step, retrieval-augmented generation prepends the same retrieved passages to many concurrent questions, and chat deployments share a long system prompt across every conversation. Second, prefix caching has become a standard runtime feature in vLLM, SGLang, and similar systems, so the KV cache for these shared tokens already resides in global memory and is explicitly reused; the remaining cost is no longer recomputation but the repeated reading of that cache. Third, decode is memory-bound, so the dominant term in per-token latency is the volume of KV bytes moved from global memory to the streaming multiprocessors. The paper's own latency breakdown shows the attention component growing to about 68% of the decode step as context length increases, which makes the reading of shared prefix KV the single largest contributor to decode latency in prefix-heavy workloads.

1.2 A Concrete Bad Scenario: A Tool-Agent Batch on A100

Consider a tool-agent deployment of Llama-3-8B served by vLLM on a single A100-80GB, decoding a batch of 64 concurrent requests that each begin with the same 2,000-token system prompt and tool catalogue, then branch into per-request suffixes of a few hundred tokens. The shared prefix has been resolved once during prefill and its KV cache resides in global memory under the prefix-cache table. On each decode step a query-centric kernel such as FlashAttention assigns one query to one cooperative thread array (CTA) and streams the full prefix KV for that query from global memory. Because 64 queries share the identical 2,000-token prefix, the kernel reads that same prefix KV 64 times per step rather than once. On the paper's measured traces this redundancy amounts to FlashAttention moving 4.3 to 8.7 times more KV-cache bytes from global memory than the theoretical minimum that a single shared read would require. Since the step is memory-bound, the wasted bandwidth translates almost directly into wasted decode latency, and it grows with both batch size and prefix length — exactly the regime that prefix-heavy agentic traffic occupies.

1.3 The Quantified Baseline Pain

Before any of PAT's improvements are introduced, the status quo can be stated in concrete numbers. On the toolagent and conversation traces, FlashAttention reads 4.3 to 8.7 times the theoretically minimal KV-cache volume per decode step, because each shared prefix is re-read once per dependent query rather than once per group. This redundant traffic is the direct cause of the attention component reaching about 68% of decode-step latency in the breakdown of Figure 1; the kernel spends most of its time moving bytes it has already moved for a sibling query in the same batch. The waste is not a constant tax but scales with the product of batch size and shared-prefix length, so it is most severe precisely in the high-batch, long-prefix conditions that agentic and RAG serving create. A reader should take from these numbers that the inefficiency being fixed is bandwidth spent re-reading identical KV, and that its magnitude is multiplicative in the two quantities a prefix-heavy workload maximizes.

Figure 5a (from paper): Average KV-cache bytes loaded from global memory per decode step on the toolagent and conversation traces, comparing FlashAttention (FA), PAT, and the theoretical optimum. FlashAttention moves 4.3 to 8.7 times the optimal volume because each shared prefix is re-read per dependent query; PAT approaches the optimum by reading each shared prefix once per group.

1.4 Strawman: A Single Shared Pass Over the Prefix

The obvious response to redundant prefix reads is to read each shared prefix exactly once and reuse it for every dependent query, which is the strategy of RelayAttention. RelayAttention performs a single pass over one shared prefix common to the whole batch, computes the partial attention contribution of that prefix, and then delegates the per-request suffix attention to a standard FlashAttention kernel. This works when the batch has exactly one global prefix, but it does not match the structure of real agentic and conversational traffic, which is hierarchical: a batch typically contains several distinct system prompts, each of which fans out into several tool or template branches, which in turn fan out into many per-request suffixes. RelayAttention recognizes only a single level of sharing, so on a conversation trace with a three-level prefix tree it captures the savings of the top level and re-reads everything below it, and a fixed single-prefix pass cannot express the uneven, multi-level grouping that the workload actually exhibits. The design space therefore reduces to handling sharing at arbitrary tree depth, not at one global level.

1.5 The Fundamental Obstacle: Query-Centric vs KV-Centric, on Uneven Groups

Once sharing must be handled at arbitrary tree depth, a structural tension appears between two ways of assigning work to CTAs, and neither resolves it alone. A query-centric kernel assigns one query per CTA; it is simple and load-balanced across queries, but it re-reads each shared prefix once per query and therefore carries the redundant-bandwidth cost described above. A KV-centric kernel assigns one shared prefix segment per CTA and lets all dependent queries attend to it in a single read, which removes the redundant traffic, but it makes the per-CTA workload depend on how many queries share that segment and on how long the segment is. When prefix groups are uneven — six queries on one branch, one query on another, suffixes of widely differing length — a single fixed tile shape forces a choice with no good answer: a tile sized for the large group pads on-chip memory with unused entries for the small groups, an inefficiency the paper labels memory waste, while CTAs holding short KV segments finish early and sit idle as the SM waits for CTAs holding long segments, an inefficiency the paper labels the execution bubble. Eliminating redundant reads with a KV-centric layout therefore introduces a resource-utilization problem that a fixed tiling cannot solve, and the partial results produced by separate prefix-segment CTAs must additionally be recombined correctly. PAT refers back to this tension when it selects a kernel per group rather than a single kernel for the batch, and when it merges partial results with online softmax.

PAT differs from these works along three axes that none of them combined. The result is a memory-bound decode-attention kernel whose KV traffic approaches the theoretical minimum while keeping the streaming multiprocessors busy.

1.7 Contributions and Headline Results

Having established why redundant prefix reads dominate memory-bound decode and why neither a query-centric kernel nor a fixed KV-centric tiling resolves the tension, the paper's contributions can now be stated as the response to that pain. They are organized around the three stages of the execution pattern and the runtime integration that makes the kernel usable inside vLLM.

Contribution 1: Prefix-Aware Query Packing

A pack scheduler that builds a tree-structured block table over the batch and groups queries sharing a KV prefix into a CTA, governed by a profit model that packs a node only when its shared length exceeds a block-granularity threshold of 16 tokens.

Contribution 2: Resource-Efficient Multi-Tile Kernel

A CUTLASS-based decode kernel whose tile shape $(m,n)$ is selected per prefix group under shared-memory, bandwidth-saturation, and tile-size constraints, so that each group runs on a configuration matched to its query count and KV length.

Contribution 3: Multi-Stream Forward and Online-Softmax Merge

Concurrent forwarding of differently-shaped per-group kernels across CUDA streams, with long-KV CTAs split for balance, followed by a lightweight merge kernel that recombines partial results using online-softmax rescaling.

Contribution 4: Drop-In vLLM Backend

A plugin that exposes PAT as a vLLM attention backend, enabled by setting the environment variable VLLM_ATTENTION_BACKEND to PREFIX_ATTN, requiring no changes to model code.

2. Architecture: The Pack-Forward-Merge Pipeline

PAT replaces a single monolithic decode-attention kernel with a three-stage pipeline that runs once per decode step. The pack stage analyzes the batch's prefix structure and decides which queries should share a KV read; the forward stage runs the per-group kernels that perform those shared reads on configurations sized to each group; and the merge stage recombines the partial attention outputs into the per-query result. The stages are sequenced so that grouping decisions made in software determine the kernel shapes launched on the GPU, and the numerical correctness of the recombination is preserved by carrying the running softmax statistics through to the merge.

Stage 1 · Pack

Group queries by shared prefix

Build a tree-structured block table over the batch; a profit model decides which tree nodes are profitable to pack into a shared CTA. Output is a PackedBox describing the CTAs, their KV segments, and the query-to-CTA map.

Stage 2 · Forward

Run per-group multi-tile kernels

For each group, pick a tile shape that satisfies the on-chip resource constraints, launch the matching CUTLASS kernel, run different shapes concurrently on separate CUDA streams, and split long-KV CTAs for balance.

Stage 3 · Merge

Recombine with online softmax

A lightweight kernel reduces each query's partial results — running max, log-sum-exp accumulator, and weighted value sum — into the final attention output using the standard online-softmax rescaling.

3. Core Mechanisms

The three stages of the pipeline rest on four mechanisms: a packing decision governed by a profit model, a per-group selection of the kernel tile shape, a forwarding strategy that uses multiple CUDA streams and splits long KV segments, and a merge that preserves the softmax normalization across partial results. Each mechanism is described below with the relevant formulas and, where helpful, condensed code from the public implementation.

3.1 Prefix-Aware Query Packing

Packing is the decision of which queries should be served by a single CTA so that their common prefix is read from global memory only once. The scheduler represents the batch as a prefix tree: each node holds a run of KV blocks shared by all the queries beneath it, and each leaf corresponds to a request's private suffix. Packing a node means assigning all queries below it to one CTA that reads the node's KV once; not packing it means the queries read that KV separately. Whether packing helps depends on how much KV is shared and how many queries share it, because grouping introduces an intermediate cost: each CTA must write out a partial result that the merge stage later reads back.

The profit model formalizes this trade-off. For a node $u$ shared by $s_u$ queries over a KV length $l_u$ with head dimension $d$, the ratio of the global-memory traffic saved by sharing to the intermediate read/write traffic introduced is governed by the following condition, which the paper reduces to a simple length threshold.

(1) $$r = \frac{(s_u - 1)\, l_u\, d}{8\, s_u\, d} \;\geq\; \frac{l_u}{16}$$

The left-hand side is the saved-to-overhead ratio: the numerator counts the prefix reads removed by sharing across the $s_u$ queries, and the denominator counts the intermediate partial-result traffic. The reduction to $l_u / 16$ shows that packing is profitable whenever the shared KV is at least 16 tokens long, because sharing is performed at the granularity of KV blocks. This threshold is why short shared runs are left unpacked: below it, the partial-result write-and-read costs more than the saved prefix read. The scheduler applies the condition at every tree node and emits a packing that respects it.

In the public implementation, the packing decision is produced by pack_prefix_blocks in prefix_attn/block_scheduler.py, which walks a sorted SeqGroup and emits a PackedBox. The condensed signature and docstring below show the shape of the output the scheduler hands to the kernel: the mapping from CTAs to queries, the per-CTA KV blocks, and the split bookkeeping that the forward and merge stages consume.

def pack_prefix_blocks(seq_group: SeqGroup, block_size: int, k: int = 64) -> PackedBox:
    # identify multi-level prefix blocks & pack queries + KV into CTAs
    # sharing a common prefix. k = max number of sequences per CTA.
    #
    # example seq_group (block_size = b), 6 sequences:
    #   [A B C  D E F  N O P]   [A B C  D E F  Q]

    #   [A B C  H I J  V W X Y] [A B C  K L M  Z]
    #
    # example output (10 CTAs):

    #   block_table      = [[A,B,C],[D,E,F],[H,I,J],[K,L,M], ...]
    #   num_seqs_per_CTA = [6,2,3,1,1,1,1,1,1,1]   # group sizes (uneven)
    #   CTA_rank         = [0,1,1,1,2,2,2,2,2,2]   # tree depth of each CTA
    #   kv_in_CTA        = [3b,3b,3b,3b,3b,b,3b,b,4b,b]  # KV length per CTA
    assert seq_group.is_sorted, "SeqGroup must be sorted"
    assert k <= 64, "max sequences per CTA must be <= 64"
    # ... main packing loop groups sequences by current block id,
    #     applies the profit condition, and fills the PackedBox ...

The worked example in the docstring makes the central difficulty concrete: the shared root [A,B,C] is read once for all six sequences, but the resulting groups are deliberately uneven, with num_seqs_per_CTA ranging from six down to one and kv_in_CTA ranging from one block to four. This unevenness is not a defect of the packing; it is the faithful structure of a hierarchical prefix tree, and it is exactly the input that the forward stage must run efficiently. The CTA_rank field records each CTA's tree depth so that the merge stage knows how the partial results of a query stack across levels.

3.2 Resource-Efficient Multi-Tile Kernel and Per-Group Selection

A decode-attention CTA computes two matrix-vector products: the query attends to the keys to produce scores, and the normalized scores weight the values. The kernel processes this in tiles of $m$ queries by $n$ KV entries, prefetching the next KV tile asynchronously while computing on the current one. The tile shape $(m,n)$ determines how much on-chip memory each CTA consumes and how many CTAs can run concurrently per SM, so a tile that is well-matched to one group is wasteful for another. Rather than apply a single fixed tile to the whole batch, PAT selects the tile shape per prefix group, subject to three constraints.

Figure 3 (from paper): (a) The two general matrix-vector multiplications (GEMV) that make up decode attention: query-by-keys producing scores, and scores-by-values producing the output. (b) The tiling execution pipeline, in which the next KV tile is prefetched asynchronously while the current tile is being computed, overlapping memory movement with computation.

The first constraint is the on-chip storage budget. A tile must hold $m$ queries, $n$ KV entries, and the $m$ partial outputs in shared memory, so for head dimension $h$ and element sizes $b$ and $b'$ the shape must satisfy the shared-memory bound below, where $S_{smem}$ is the per-CTA shared-memory capacity.

(2) $$m\, h\, b \;+\; n\, h\, b \;+\; m\, h\, b' \;\leq\; S_{smem}$$

The second constraint sets a lower bound on $n$ so that there is enough in-flight KV data to saturate memory bandwidth. With inherent memory latency $L$, bandwidth $B$, $S$ streaming multiprocessors, $C$ concurrent CTAs per SM, head dimension $h$, and element size $b$, the KV tile must be at least as large as the bandwidth-delay product divided across the available concurrency.

(3) $$n \;\geq\; \left\lceil \frac{L \times B}{S \times C \times h \times b} \right\rceil$$

The third constraint is imposed by the CUTLASS building blocks PAT is written on: tile dimensions must be powers of two no smaller than 16, so $m, n \in \{2^k : 2^k \geq 16\}$. Together the three conditions carve out a small discrete set of feasible $(m,n)$ shapes, and PAT picks, for each group, the feasible shape whose query dimension is closest to the group's query count and whose KV dimension covers the group's KV length without excessive padding. 3.3 Multi-Stream Forwarding and Long-KV Splitting

Selecting a tile shape per group produces a set of kernels with different shapes that must run on the same GPU within one decode step, and the way they are launched determines whether the streaming multiprocessors stay busy. Two issues remain after the per-group shape is fixed: kernels of different shapes launched serially leave gaps when a small group's kernel cannot fill the device on its own, and a CTA assigned a very long KV segment runs much longer than its siblings, leaving SMs idle in the tail of the step — the execution bubble identified in the motivation. PAT addresses the first issue by forwarding kernels of different $(m,n)$ configurations concurrently on separate CUDA streams, so that a small kernel and a large kernel can co-reside on the device, and the second issue by splitting any CTA whose KV length exceeds the batch's mean KV length along the KV axis into several shorter CTAs that finish closer together.

Figure 9 (from paper): Execution pipeline of four CTAs under different concurrency. (a) High concurrency with dynamic KV lengths yields low tail efficiency and a large execution bubble; (b-d) lower concurrency, obtained through a larger KV tile and long-KV splitting, shortens per-CTA latency and reduces the bubble across the shown execution orders.

Long-KV splitting trades a small amount of redundant intermediate state for a large reduction in tail latency. When a CTA is split along the KV axis, each fragment computes attention over its own slice of the KV segment and produces its own partial result; these partials are then combined in the merge stage in the same way that partials from different prefix nodes are combined. Splitting therefore does not require any new merge machinery — it reuses the online-softmax reduction described next — which is what makes it a low-cost way to flatten the per-step tail.

3.4 Online-Softmax Merge

Because a single query's attention is now computed in pieces — one partial result per prefix-tree node it passes through, and one per KV split — the pieces must be combined into the exact result a single full pass would have produced. The difficulty is that softmax is a global normalization: a query's output is a weighted average of values in which the weights depend on the maximum score seen across all KV positions, and that maximum is not known until every piece has been processed. Online softmax solves this by carrying three running statistics per query — the running maximum score, a running normalizer (the sum of exponentials shifted by that maximum), and a running weighted sum of values — and rescaling them whenever a new maximum appears, so that pieces can be combined incrementally without ever materializing the full score vector.

Concretely, when a new partial result with local maximum $m^{(j)}$, local normalizer $\ell^{(j)}$, and local value sum $o^{(j)}$ is merged into the running accumulator $(m, \ell, o)$, the merge first computes the combined maximum and then rescales both contributions to that common reference before adding them.

(4) $$m_{new} = \max\!\left(m,\, m^{(j)}\right)$$
(5) $$\ell_{new} = e^{\,m - m_{new}}\,\ell \;+\; e^{\,m^{(j)} - m_{new}}\,\ell^{(j)}$$
(6) $$o_{new} = e^{\,m - m_{new}}\,o \;+\; e^{\,m^{(j)} - m_{new}}\,o^{(j)}$$

After every partial result has been folded in, the query's final attention output is the accumulated value sum normalized by the accumulated normalizer, $o / \ell$. The two scaling factors $e^{m - m_{new}}$ and $e^{m^{(j)} - m_{new}}$ are the heart of the procedure: they retroactively correct contributions that were exponentiated against a stale maximum, which is what makes the order in which pieces arrive irrelevant to the result. This order-independence is the property PAT relies on to combine partials from uneven prefix groups and from long-KV splits in a single reduction, and it is why splitting a long CTA introduces no numerical error — only additional partials for the same merge to absorb. The paper adopts the standard FlashAttention formulation of this reduction and applies it across the tree-structured partials that packing produces.

Why correctness is preserved: The merge produces a result that is numerically equivalent to a single dense pass over the full KV for each query. Packing, per-group tiling, multi-stream forwarding, and long-KV splitting are all performance transformations that change only how the KV is read and the order in which partials are produced; the online-softmax reduction guarantees that the recombined output is independent of that order. PAT therefore changes the cost of decode attention, not its value.

The kernel experiments sweep twenty synthetic decode-batch configurations under four attention-head settings — 32/32, 16/8, 32/8, and 64/8 query/KV heads, which span multi-head and grouped-query attention — and report normalized kernel performance against FlashAttention, FlashInfer, FastTree, and RelayAttention. 4.2 End-to-End Serving Performance

The end-to-end experiments serve Llama3-8B and Qwen3-8B under two real traces — a toolagent trace with a 59% prefix-cache hit rate and a conversation trace with a three-level prefix structure — and sweep the request rate. Across these settings PAT reduces time-per-output-token by 17.2 to 68.1% against RelayAttention++, by 17.0 to 89.5% against FlashAttention, and by 32.2 to 93.1% against FlashInfer, with corresponding P99 time-per-output-token reductions of up to 93.4%. 4.3 Ablation: Where the Gains Come From

The ablation isolates the contribution of each mechanism by comparing PAT against variants that remove one piece at a time — a compute-model cost function (PAT-compute), a naive packing without the profit model (PAT-naive), a fixed single tile (PAT-fixed), and a serial single-stream launch (PAT-serial). The attention-latency panel shows that no single mechanism accounts for the full gain; the memory-traffic panel confirms that prefix-aware packing is what drives the global-memory read volume down toward the optimum, while the tiling and multi-stream pieces convert that saved bandwidth into latency by keeping the SMs busy.

Figure 12a (from paper): Average attention latency of PAT against ablation variants that each remove one mechanism. Each removed piece raises latency, and no single variant recovers the full PAT result.
Figure 12b (from paper): Global-memory read and write volume for the same variants. Prefix-aware packing is the dominant contributor to the reduction in global-memory reads; the small additional write volume is the intermediate partial-result traffic that the profit model bounds.

The scheduler's own overhead is small relative to the per-step preprocessing that the serving system performs regardless, so the packing decision does not erode the kernel gains it enables. The paper measures the pack-scheduler cost against the system's preprocess latency on both traces and finds it to be a minor fraction of the per-step host work.

Figure 14 (from paper): Overhead of the pack scheduler compared against the serving system's preprocess latency on the toolagent and conversation traces. The scheduler adds a minor fraction to the host-side per-step work the system already performs.
Caveat on the range of gains: The wide reported ranges — for instance TPOT reductions from 17.0% to 93.1% — reflect that PAT's benefit is a function of how much the workload actually shares. The improvement scales with the prefix-cache hit rate and with the quality of the prefix-group packing; on a workload with little shared prefix, the redundant reads PAT removes are themselves small, and the gain narrows toward the low end of each range. The high end is reached on long, widely-shared prefixes, and the low end on short or unshared ones. The numbers should therefore be read as a function of workload structure, not as a single expected speedup.

5. Claims vs Implementation

The public repository at github.com/flashserve/PAT contains a CUTLASS-based kernel under csrc/, a Python scheduling package under prefix_attn/, and a vLLM integration plugin under plugin/, together with the benchmark scripts used in the paper. 5.1 Strengths & Limitations

The repository is organized for artifact evaluation and carries the ACM Available, Functional, and Reproduced badges, which makes the kernel and scheduler claims directly checkable; the practical limitations are mostly about hardware scope and the workload-dependence of the headline numbers.

Strengths

  • Clean stage separation — scheduler in Python, kernel in CUTLASS C++, integration in a vLLM plugin
  • Drop-in adoption: a single environment variable selects the backend, with no model-code changes
  • Numerically exact — the online-softmax merge reproduces a dense pass, so no accuracy is traded for speed
  • Artifact-evaluated with bundled real traces and one-command benchmark scripts

Limitations

  • Kernels are instantiated for SM80 (A100) and validated on H100; other architectures need new compiled variants
  • Gains depend on prefix-cache hit rate and packing quality; low-sharing workloads see the low end of each range
  • Scope is decode attention only — prefill scheduling, request admission, and multi-node routing are out of scope
  • Full end-to-end reproduction needs over 60 GPU-hours and a large Docker image with model weights

6. How to Reproduce

The repository is packaged for ACM artifact evaluation, with a prebuilt Docker image that bundles the model weights and the benchmark traces. The steps below follow the repository's own artifact-evaluation instructions: prepare the image, run a basic functional test, then run the kernel and end-to-end benchmarks that reproduce Figures 10 and 11.

6.1 Prepare the Image and Container

Clone the repository, pull the prebuilt image, and start a container with GPU access and a large shared-memory segment, which the multi-stream kernels require. The image is built against the SM80 (Ampere) target the kernel is compiled for, and the shared-memory segment has to be large enough to hold the partial attention results that the forward streams exchange before the merge step.

# Clone the repo and pull the prebuilt artifact image (~50 GB, includes weights)
git clone https://github.com/flashserve/PAT.git
docker pull flashserve/pat:ae

# Start the container with all GPUs and a 64 GB shared-memory segment
docker run -it --gpus all -v ${PWD}/PAT:/workspace/PAT -w /workspace \
    --shm-size=64g flashserve/pat:ae /bin/bash

Once inside the container, a single functional test confirms that the compiled kernel loads and produces correct output before any timing run is attempted. The test exercises the pack-forward-merge path on a small batch and compares its result against the reference attention, so a pass certifies that the kernel is correctly installed before any benchmark consumes GPU hours.

# Basic correctness test; expect: [INFO] successfully pass the test!
cd /workspace/PAT/test
python test.py

A passing test means the SM80 kernel is correctly installed; if it fails, the most common cause is a driver or CUDA mismatch with the image, which the hardware requirements below are meant to prevent.

6.2 Run the Kernel and End-to-End Benchmarks

The kernel benchmark reproduces the synthetic-workload comparison of Figure 10 and takes about 1.5 hours; the end-to-end benchmark reproduces Figure 11 and is provided in a partial form for quick verification and a full form for the complete result.

# Kernel performance (Section 8.3, Figure 10); ~1.5 hours -> kernel_perf.json
cd /workspace/PAT/benchmark
bash ./run_kernel_bench.sh

# End-to-end (Section 8.4, Figure 11). Quick partial run: ~8-10 GPU-hours
bash ./run_e2e_bench_part.sh
# Full reproduction (over 60 GPU-hours):
# bash ./run_e2e_bench_full.sh

Results are written to kernel_perf.json and e2e_perf.jsonl. The plotting scripts then turn those logs into the comparison figures, with eval_kernel_perf.py producing the kernel plot and eval_e2e_from_jsonl.py producing the end-to-end P99 plot.

# Plot kernel performance (Figure 10)
cd /workspace/PAT/plot
python eval_kernel_perf.py --log-file ../benchmark/kernel_perf.json

# Parse end-to-end serving results (Figure 11, QPS=7&9 partial run)
python eval_e2e_from_jsonl.py --log-file ../benchmark/e2e_perf.jsonl

To enable PAT inside a live vLLM server rather than the benchmark harness, the backend is selected through a single environment variable, after which the serving path uses the prefix-aware kernel transparently.

# Enable PAT as the vLLM attention backend
export VLLM_ATTENTION_BACKEND="PREFIX_ATTN"

With the variable set, vLLM routes decode attention through the plugin registered in plugin/vllm/attention/backends/prefix_attn.py; no further model or serving-config change is required for the prefix-aware path to take effect.

Hardware Requirements: The artifact requires an x86-64 Linux host with at least 64 GB RAM, 200 GB of free disk space, and an NVIDIA A100 GPU with 80 GB of memory, running NVIDIA driver >= 550 and CUDA >= 12.4. The kernels are compiled for SM80; H100 (SM90) is additionally validated for the kernel experiments. The full end-to-end suite exceeds 60 GPU-hours, so the repository provides a partial-run script (QPS 7 and 9) for quick verification; multiple GPUs are detected automatically and used to parallelize the runs.

7. Independent Kernel Reproduction

Beyond reading the paper, this page is paired with a separate hands-on reproduction that rebuilt PAT from source and re-ran its decode-attention kernel benchmark across six GPUs spanning four hardware generations. The full report is hosted on this site and linked below; this section states what the reproduction measured and how its numbers relate to the paper's central claim.

Full report: PAT Kernel Reproduction — Prefix-Aware Attention across six GPUs →

The artifact ships no prebuilt wheel, so it was compiled from source, and the kernel-latency sweep covered twenty prefix-tree shapes crossed with four attention-head configurations. Every measured run was checked against the vLLM-FlashAttention backend to within a 1e-2 maximum-absolute tolerance, so the comparison reports speed only among kernels that produce the same output. The five cards below were exercised: A100-40GB, A100-80GB, L40S, H100, and H200, which together span the Ampere, Ada, Hopper, and Blackwell generations.

7.1 What the reproduction confirms

On the paper's reference hardware, the A100-80GB, PAT reaches a geometric-mean speedup of 2.058 times over FlashInfer and 2.993 times over vLLM-FlashAttention across the prefix-tree sweep, and it is the fastest decode-attention kernel on every architecture tested. The result therefore reproduces the paper's central claim rather than merely echoing it, and the numerical check confirms that the speed comes without changing the attention output beyond a 1e-2 tolerance.

7.2 Reading the result

The size of the gain tracks how much shared-prefix structure exists in the batch. PAT builds a radix tree over the batch's block tables and computes each shared prefix once per cooperative thread array rather than once per request, so the benefit is largest when many requests share long prefixes and narrows as prefixes become short or unique. That the advantage holds from Ampere through Blackwell indicates it is structural — a consequence of removing redundant KV reads — rather than an artifact tuned to a single GPU, which is the same conclusion the paper draws from its own measurements.
