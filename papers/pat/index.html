Prefix sharing as an attention-kernel problem

PAT: Prefix-Aware Attention for LLM Decoding

A CUTLASS/vLLM attention backend that avoids reloading shared prefix KV blocks across requests.

Authors Jinjun Yi, Zhixin Zhao, Yitao Hu, Ke Yan, Weiwei Sun, Hao Wang, Laiping Zhao, Yuhao Zhang, Wenxin Li, Keqiu Li
Affiliation Tianjin University and collaborators
Venue and version ASPLOS 2026, arXiv 2511.22333v3, DOI 10.1145/3779212.3790200
Page scope Prefix tree scheduling, multi-tile attention, and vLLM backend integration

Core Question

PAT pushes prefix reuse below the cache manager and into the attention kernel. Storing shared KV blocks saves memory capacity, but decode attention can still reload the same prefix for every request.

The paper’s question is therefore about HBM traffic, not only cache hits. It asks whether a prefix tree can be packed into Tensor Core-friendly work without changing the exact attention result.

Motivation Ladder

PAT is a conditional acceleration: it is strongest when application prompts create common roots and suffix divergence. Independent prompts reduce the opportunity for prefix-tree reuse.

The implementation boundary is narrower than all decode attention. The vLLM plugin checks attention features and KV formats, and unsupported cases leave the specialized path.

1

Why now

Modern serving batches are increasingly shaped by system prompts, tool templates, and retrieval outputs that create hierarchical common prefixes. Prefix caching stores these blocks once, but common attention kernels still reload the same KV data independently for each query.

Modern shared prompts turn prefix reuse into a kernel problem, not only a cache-capacity problem. PAT targets the remaining KV traffic after prefix blocks are already cached.

2

Concrete bad scenario

Many requests share a long instruction prefix and diverge only near the suffix. A query-centric kernel launches per request, so HBM traffic scales with batch size even when most prefix blocks are identical.

The failure case shows why cache hit rate alone is not enough. Cached KV blocks can still be reread many times if the attention backend remains query-centric.

3

Baseline pain

FlashAttention and FlashInfer are efficient for general decode attention, but they do not exploit prefix identity across requests. RelayAttention and tree-based approaches reduce some reuse gaps, yet the paper shows resource mismatch when CTA shapes are fixed.

The paper uses this pain to motivate prefix-aware tiling. A general fast attention kernel can still move avoidable KV bytes when many requests share ancestors in the prefix tree.

4

Strawman

One can group requests by prefix and process the shared prefix once. That is insufficient because the kernel must still map variable numbers of queries and variable KV lengths onto Tensor Core-friendly CTAs without wasting shared memory and registers.

Grouping by prefix is only the first step. The grouped work must also fit Tensor Core-friendly CTAs without wasting shared memory, registers, or merge bandwidth.

5

Fundamental obstacle

The obstacle is a three-way coupling among prefix tree structure, KV-cache block layout, and GPU tile shape. A good schedule must decide which prefix nodes become CTAs, which tile type each CTA uses, and how split outputs are merged with stable softmax math.

The obstacle forces the scheduler, radix-tree representation, and softmax merge path to be designed together. A mismatch in any one part loses the intended reuse.

6

Position against nearby systems

PAT is narrower than a full serving system and deeper than a scheduling-only prefix cache. It replaces the attention backend with prefix-aware packing, a multi-tile kernel, and vLLM integration that can be activated through `VLLM_ATTENTION_BACKEND`.

This boundary explains PAT's scope: it is an attention-backend replacement that converts application prompt regularity into lower HBM traffic.

Claim Boundaries

PAT’s claim is conditional on prefix structure. The evaluation therefore has to pair latency numbers with measured shared-prefix ratios in the active batch.

The public backend also has explicit feature checks. Unsupported attention modes or KV formats do not exercise the prefix-aware CUDA path.

System Map

The path begins with a prefix tree over cached KV blocks. Nodes with shared ancestors are packed into grouped work so the kernel can load the common prefix once.

The backend then chooses tile shapes and carries softmax state across splits. This is why scheduler metadata and CUDA kernel layout are inseparable in PAT.

Build prefix tree Represent shared KV blocks across the batch as hierarchical prefix nodes.
Pack CTAs Group query rows and KV block ranges so each CTA covers shared work once.
Select tile shape Choose M, N, and warp count according to query multiplicity and KV length.
Run PAT kernel Load paged KV blocks, compute attention fragments, and store partial outputs.
Merge split outputs Use online softmax metadata to combine partial results without numerical drift.

Mechanism Deep Dive

PAT has four moving pieces: prefix-tree construction, block scheduling, multi-tile forward attention, and split-output merge. Removing any one of them turns prefix awareness into either a layout trick or an unsafe approximation.

The design succeeds only if the scheduler and kernel agree on the same tree. Python prepares grouped work; C++/CUDA consumes that metadata without falling back to per-request KV reads.

Prefix packing

PAT identifies common block prefixes and turns them into CTA work units with `q_table`, `block_table`, split ranks, and KV length metadata. The code has both Python and C++ prefix-tree paths.

Multi-tile kernel

The CUTLASS/CUTE kernel accepts tile parameters for query rows, KV columns, and warps. This avoids forcing all prefix groups into one large or one small CTA shape.

Softmax-safe merging

When a sequence is split across multiple CTAs, PAT stores accumulated outputs and log-sum-exp values, then gathers them with a numerically stable merge kernel.

vLLM backend integration

The plugin adds `PREFIX_ATTN` as a vLLM attention backend and calls `prefix_attn_with_kvcache` in decode mode. The README states that enabling the backend only needs an environment variable after installation.

Interaction Among Pieces

PAT’s mechanism only works if the prefix tree, block scheduler, tile selector, and merge kernel agree on the same grouping. Prefix awareness in Python is not enough unless the CUDA path consumes exactly that grouping.

The hard boundary is the softmax merge. Once prefix work is split across tiles, PAT must preserve exact attention semantics while still avoiding repeated KV reads.

Implementation Trace

The implementation is split across Python packing code and CUDA kernels. `prefix_attn/block_scheduler.py` prepares work; `csrc/prefix_tree.h` and `csrc/pat_fwd_kernel.h` define the tree and forward path.

The vLLM backend is the operational hinge. `plugin/vllm/attention/backends/prefix_attn.py` receives decode metadata and routes supported cases into `prefix_attn_with_kvcache`.

  • `prefix_attn/block_scheduler.py` implements prefix block packing and a tile distributor over query and KV dimensions.
  • `csrc/prefix_tree.h` builds a radix tree and packs prefix nodes into grouped `KernelInfo` tensors.
  • `csrc/pat_fwd_kernel.h` contains the CUTLASS/CUTE forward kernel and the gather kernel for split outputs.
  • `plugin/vllm/attention/backends/prefix_attn.py` wires decode metadata into `prefix_attn_with_kvcache` under the `PREFIX_ATTN` backend.

Prototype Boundary

The public implementation does not imply universal backend coverage. It is a specialized attention path with feature checks, build requirements, and assumptions about KV-cache format.

Unsupported attention modes matter because they decide whether traffic reaches the prefix-aware kernel at all. Block-sparse attention, sliding windows, ALiBi, or unsupported KV types can invalidate the path.

Evaluation Reading

The evaluation separates three questions: whether KV bytes fall, whether kernel latency falls, and whether vLLM TPOT/tail latency falls. PAT needs all three to support its systems claim.

The ablations are central rather than decorative. Fixed tile, compute-only, and naive merge variants show that prefix grouping alone does not explain the result.

Evaluation Discipline

PAT’s evaluation is credible only where prefix sharing is measured, not assumed. The trace-level shared-prefix ratio should be read before the kernel speedup.

The ablations are the guardrail: fixed tile, compute-only, and naive merge variants identify which part of the prefix-aware path actually carries the result.

Limitations and Failure Modes

PAT is limited by prompt regularity. It is a strong fit for tool, retrieval, and system-prompt-heavy workloads; it is weaker when a batch has little shared prefix structure.

The build and backend constraints are also real. CUTLASS/CUDA compilation and vLLM feature checks make PAT a specialized systems component rather than a transparent library switch.

Prefix-dependent gain

PAT needs shared prefixes in the active batch. If requests are independent or prefix cache hits are rare, the backend has less reusable KV traffic to remove.

Backend constraints

The vLLM integration checks attention features and rejects unsupported cases such as block-sparse attention, ALiBi slopes, sliding windows, and non FP16/BF16 KV cache types.

Build cost

The README lists CUDA, CUTLASS, vLLM source build, and GPU requirements; this is a specialized kernel implementation rather than a drop-in pure Python package.

Takeaways

The main lesson is that prefix caching should be measured in bandwidth as well as capacity. A cache hit that is reread many times still leaves performance unused.

The second lesson is that tree structure must match GPU tile structure. PAT works when the prefix tree can be converted into efficient CTAs and exact softmax merges.

  • Prefix caching saves memory capacity; PAT turns the same structure into memory bandwidth savings.
  • The design is strongest when application prompts create repeated hierarchical prefixes.
  • The public repository includes a real vLLM backend and a custom kernel, not only a simulator.

Bottom Line

PAT’s contribution is to convert application prompt regularity into lower attention bandwidth. Prefix caching stores shared KV; PAT tries to avoid rereading it.

The design is strongest for assistant, RAG, and tool workloads with repeated prompt skeletons. Its weakest regime is independent prompts or unsupported attention features.

Best use case

Batches with long shared system prompts, retrieval templates, or tool instructions that diverge near the suffix.

Main risk

Low prefix sharing or unsupported attention features leave little work for PAT to reuse.
