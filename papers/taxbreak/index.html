TaxBreak: Unmasking the Hidden Costs of LLM Inference

A trace-driven decomposition of host-visible orchestration overhead into framework, library, and launch-path components, with a host-vs-device boundedness index

arXiv:2603.12465 Preprint 2026 H100 · H200 Dense & MoE Prefill + Decode PyTorch 2.10 · nsys

Prabhu Vellaisamy, Shreesh Tripathi, Vignesh Natarajan, Surya Santhan Thenarasu, Shawn Blanton, John P. Shen

NeuroAI Computer Architecture Lab (NCAL) · Electrical and Computer Engineering Department · Carnegie Mellon University

1. Problem: A Tax Bill Without an Itemized Receipt

Modern LLM inference deployments are entering a regime in which the GPU is no longer the only — or even the primary — bottleneck. Latency-sensitive serving paths, agentic workflows that interleave reasoning with tool calls, and Mixture-of-Experts (MoE) architectures that dispatch dozens of small kernels per token together push more and more work back onto the host. Operators who try to reduce inference latency are asked to optimize a stack with five abstraction layers — application runtime, ML framework, CUDA library, CUDA launch path, and the GPU itself — yet the diagnostic tools that ship with this stack only report aggregate numbers. The result is that engineers know they are paying a host-side “tax”, but they cannot read the line items, and so cannot target the layer that would actually return the most latency per engineering hour.

1.1 Why Now: 2025 LLM Serving No Longer Looks Like 2022 CNN Inference

The execution profile of a 2025 LLM-serving deployment differs from the workloads on which prior overhead-attribution work was calibrated. Three shifts matter together. First, the dominant model class on inference servers is no longer the dense encoder-only network that fit cleanly into compute-bound regimes; production deployments now mix dense decoder-only models (LLaMA-3, GPT-4 class) with mixture-of-experts architectures such as DeepSeek-V3, which activates only 37B of 671B parameters per token but dispatches many small dependency-chained kernels in the process. Second, the serving stack itself has grown an additional layer: high-level runtimes such as vLLM and Orca now own batching and KV-cache state, sit on top of PyTorch 2.x with TorchDynamo / TorchInductor, and may or may not call vendor libraries like cuBLAS, cuBLASLt, and cuDNN — so the cost of a single “forward step” now traverses three software layers before the first CUDA call. Third, Hopper-generation hardware (H100, H200) has improved on-device throughput so dramatically that, in eager mode at small batch sizes, the GPU now finishes its share before the host has finished preparing the next one.

1.2 A Concrete Bad Scenario: A Single Decode Step for OLMoE on H200

Consider an interactive deployment of OLMoE-1B/7B on an H200 GPU paired with a 32-core Intel Xeon Gold 6538Y+ CPU, configured with batch size 1, sequence length 512, and a 10-token decode horizon. An operator opens a standard GPU profiler and sees that the kernel-by-kernel timeline reports approximately 9,305 kernel launches per output token; the average GPU utilization, however, is only 15.5%. A coarse framework-tax study would report this as “host-bound”, and a launch-path study (TKLQT) would point to the cudaLaunchKernel API as the dominant cost. Both attributions are partly true and operationally insufficient. The operator who acts on either answer alone may invest engineering effort in a kernel-fusion pass that collapses launches, only to discover that the framework dispatch path above the launch already contributes 5.32 ms of fixed overhead per per-step orchestration window, of which the Python-side ATen overhead is itself larger than the launch-path floor. Without a per-layer attribution, the operator cannot tell whether to recompile the model under torch.compile, swap an attention kernel for FlashAttention-2, replace cuBLAS-mediated GEMMs with framework-native ones, or simply switch CPUs.

1.3 The Quantified Baseline Pain

The paper supplies the missing numbers that justify treating this attribution gap as a first-order problem. At the measured decode configuration (batch size 4, sequence length 2048, ten output tokens), MoE models such as OLMoE-1B/7B and Qwen1.5-MoE-A2.7B dispatch 8 to 11 times more GPU kernels per output token than dense models of comparable active parameter count. OLMoE-1B/7B reaches a steady-state GPU utilization of 15.5% under this configuration, against 58.9% for a dense Llama-3.2-1B model with similar active parameter count. End-to-end decode latency for OLMoE-1B/7B is 11.5 times that of Llama-3.2-1B at batch size 1, sequence length 512 — and, importantly, this latency gap is nearly invariant to context length, varying only from 2081 ms at sequence length 512 to 2164 ms at sequence length 4096. A workload whose latency does not respond to context length is one in which the launching layer, not the computational kernels, dominates wall-clock time, and the existing diagnostic stack does not name which launching layer.

1.4 Strawman: Just Trust the Existing Profilers

A reasonable first response is that the existing tooling is sufficient: NVIDIA Nsight Systems exposes per-kernel timestamps, the PyTorch Profiler exposes per-operator timing, and the framework-tax studies have already enumerated where overhead lives. The difficulty is that none of these tools produces a decomposition that is mutually exclusive and collectively exhaustive at the per-kernel granularity. The framework-tax line of work measures the gap between an end-to-end latency and the sum of GPU-active times, and reports the residual as a single aggregate number; it cannot tell the operator whether the dominant contributor inside that residual is Python-side ATen translation, the cuBLAS heuristic-selection path, or the irreducible cudaLaunchKernel floor. The kernel-launch / queue-tax line of work (TKLQT) measures the interval from cudaLaunchKernel issuance to GPU execution and is therefore precise about queueing, but it folds the entire pre-launch stack — Python dispatch, ATen, vendor library setup — into “not measured”. An operator who sees a small TKLQT and a large end-to-end residual is left with no remaining hypothesis space to choose from.

1.5 The Fundamental Obstacle: Eager Dispatch is Single-Threaded

The reason the existing single-layer views are insufficient is structural, not a matter of additional engineering effort on the same instrumentation. In eager-mode PyTorch — which remains the default execution mode for any workload with dynamic shapes, dynamic control flow, or aggressive autotune behavior, and therefore for most production LLM serving — the dispatch path is single-threaded. Each forward step issues kernels serially through one CPU thread, so the host-side per-kernel cost composes additively with kernel count rather than being absorbed by additional CPU cores. The implication is direct: shrinking total host-side cost requires either lowering the per-kernel dispatch cost (faster single-thread execution, ahead-of-time compilation) or reducing kernel count (kernel fusion, CUDA Graphs), and the choice between those two strategies depends entirely on which sub-layer contributes the most. Without an itemized attribution, an operator who throws more CPU cores at the problem is buying capacity that the single-threaded dispatcher cannot use; an operator who chooses CUDA Graphs without first measuring the framework-side cost may discover that the captured graph still pays the same Python-side overhead at instantiation. The dispatch architecture forces the diagnosis to be done correctly, layer by layer, before any remediation is selected.

Empirical characterization of $T_{sys}^{floor}$ (null-kernel launch floor) and family-by-family $\Delta KT_{fw}$ residuals, validated across Hopper platforms.

Contribution 3: HDBI Diagnostic

The Host-Device Balance Index complements the layer-resolved attribution by summarizing host-vs-device boundedness as a single ratio in $(0,1)$.

Empirical evidence across dense and MoE workloads in both prefill and decode showing that aggregate metrics by themselves obscure the dominant optimization target.

A controlled H100-vs-H200 comparison establishing that faster CPU single-thread performance reduces end-to-end LLM-inference latency by 11–14%, even when paired with a slower-clocked GPU.

Key insight: Coarse host-bound vs device-bound diagnosis is a one-bit answer; modern LLM serving needs a layer-resolved attribution because the optimization that fixes a framework-bound regime (torch.compile, CUDA Graphs) is entirely different from the one that fixes a library-bound regime (replacing cuBLAS-mediated GEMMs with framework-native kernels) or a launch-floor-bound regime (kernel fusion). TaxBreak gives the operator the information needed to pick the right optimization on the first attempt.

2. TaxBreak at a Glance

TaxBreak is a measurement methodology, not a runtime system. It consumes timestamped traces produced by NVIDIA Nsight Systems and the PyTorch Profiler, attributes every host-side microsecond between the application call and the GPU kernel start to exactly one of three components, and emits both a per-kernel decomposition table and a workload-level boundedness ratio. The methodology is designed for eager-mode PyTorch but applies unchanged to compiled paths whenever the dispatcher still issues kernels one at a time.

2.1 The Five-Layer Execution Stack

The layered structure of the modern PyTorch-CUDA execution stack is the substrate that the methodology operates on. Each layer corresponds to a distinct source of host-side time, and the gap between consecutive layers is precisely the quantity that TaxBreak attributes.

2.2 What Each Component Captures

The three host-side components are designed so that, for any single kernel invocation, exactly one component carries each microsecond of host-side latency. The dispatcher path naturally decomposes into these layers, but framework-native kernels — those generated directly by the ATen layer without a vendor library front-end — must skip the library component, and the methodology models that skip explicitly through an indicator variable.

$\Delta FT$ — Framework Translation

Python-side ATen dispatch overhead $T_{Py}$ plus the irreducible ATen-to-C++ dispatch baseline $T_{dispatch\_base}$. Captures everything the framework does before any CUDA-library call.

$\Delta CT$ — CUDA Library Translation

Vendor library front-end excess above the framework-native dispatch baseline, $\max(0, T_{dispatch} - T_{dispatch\_base})$. Gated to zero for non-library kernels by the indicator $\mathbb{1}_{lib} \in \{0,1\}$.

$\Delta KT$ — Kernel Launch Floor

Hardware floor $T_{sys}^{floor}$ from null-kernel profiling — the irreducible cost of issuing any CUDA kernel through cudaLaunchKernel on a given GPU/driver pair.

Key insight: $\Delta KT$ is reported as the hardware floor $T_{sys}^{floor}$ rather than the raw launch interval, because the raw interval $T_{launch}^{raw} = T_{sys}^{floor} + \Delta KT_{fw}$ already contains a framework-enqueue residual $\Delta KT_{fw}$ that $\Delta FT$ and $\Delta CT$ have separately accounted for. This avoids double counting and is the structural reason the decomposition is mutually exclusive.

3. Methodology — A Mutually Exclusive Per-Kernel Decomposition

The methodology rests on three formal equations. The first decomposes the host-side latency of a single kernel invocation into the three components introduced above. The second sums that decomposition across all kernels in a model run to obtain the workload-level orchestration cost. The third defines the Host-Device Balance Index that complements the layer-resolved attribution. Together they convert a stream of NVTX-annotated, replay-recovered timestamps into a diagnostic that can be read at either resolution depending on the operator's question.

3.1 Per-Kernel Decomposition (Equation 1)

For each kernel invocation, the per-kernel host-side latency $T_{Host}$ is the sum of three mutually exclusive components, with the CUDA-library component gated by the indicator $\mathbb{1}_{lib}$ that is one for library-mediated kernels and zero for framework-native ones.

(1) $$T_{Host} \;=\; \underbrace{T_{Py} + T_{dispatch\_base}}_{\Delta FT} \;+\; \mathbb{1}_{lib} \cdot \underbrace{\max(0,\; T_{dispatch} - T_{dispatch\_base})}_{\Delta CT} \;+\; \underbrace{T_{sys}^{floor}}_{\Delta KT}$$

3.2 Workload-Level Aggregation (Equation 2)

The orchestration overhead of a full model run is the sum of the per-kernel decomposition over all $N$ kernel invocations in the trace, retaining the gating indicator on the library term so that framework-native kernels contribute only $\Delta FT$ and $\Delta KT$.

(2) $$T_{Orchestration} \;=\; \sum_{i=1}^{N} \Big( \Delta FT^{(i)} \;+\; \mathbb{1}_{lib}^{(i)} \cdot \Delta CT^{(i)} \;+\; \Delta KT^{(i)} \Big)$$

3.3 Library-Mediated vs Framework-Native Kernels

The indicator $\mathbb{1}_{lib}$ is set per-kernel by tracing the dispatch chain in the captured profile. A kernel whose dispatch path passes through ATen, then a vendor-library front-end such as cuBLAS or cuDNN, and finally cudaLaunchKernel receives $\mathbb{1}_{lib} = 1$ and pays a non-zero $\Delta CT$. A kernel that is generated directly by the ATen layer or by a hand-written elementwise or data-movement op — for instance aten::mul, aten::native_layer_norm, cudaMemcpyAsync, or cudaMemset — receives $\mathbb{1}_{lib} = 0$ and pays no library cost.

To make the indicator concrete, consider the two representative kernels below — a library-mediated linear projection and a framework-native layer-norm, taken from the same forward step. The first chain (a) traces the path of nn.Linear, the workhorse of every transformer block. The Python-side dispatcher hands the call to ATen, which selects the matrix-multiplication implementation aten::addmm; ATen then consults the cuBLAS front-end to pick a tile size and create a descriptor, and only after that descriptor is built does control reach cudaLaunchKernel. The kernel that finally runs on the GPU is one of cuBLAS's SM90 xmma GEMM variants. Because the cuBLAS front-end performs real, measurable work between aten::addmm and cudaLaunchKernel, this kernel inherits the indicator value $\mathbb{1}_{lib} = 1$ and is charged a non-zero $\Delta CT$ — the library translation cost.

The structural consequence of this gating is that $\Delta CT$ is mathematically forced to zero for the framework-native class and remains the only cost channel where a vendor-library replacement (cuBLASLt swap, hand-rolled GEMM, lower-overhead descriptor cache) can yield a positive return. If an operator observes that $\Delta CT$ is the dominant residual on a workload, the candidate optimizations narrow to the column (a) path; if $\Delta CT$ is already gated to zero across the trace, replacement of vendor-library front-ends is provably not the right intervention and the operator should re-target $\Delta FT$ or $\Delta KT$.

3.4 Why the Decomposition is Mutually Exclusive

The mutual exclusivity is enforced by two design choices. First, the framework component $\Delta FT$ is defined to include only the Python-to-ATen translation $T_{Py}$ and the irreducible ATen-to-C++ dispatch baseline $T_{dispatch\_base}$ — the latter is measured as the median dispatch cost across framework-native kernels (those with $\mathbb{1}_{lib} = 0$), so it captures the dispatcher cost in the absence of any vendor-library contribution. Second, the library component $\Delta CT$ is defined as the excess above that baseline rather than the total library-front-end time, so it captures only the vendor-library-specific cost. The launch component $\Delta KT$ is reported as the hardware floor $T_{sys}^{floor}$, isolated by null-kernel profiling, rather than the raw launch interval. The raw interval contains a framework-enqueue residual $\Delta KT_{fw} = \max(0, T_{launch} - T_{sys}^{floor})$ that is reported separately for diagnostic insight but is not used in Equation 2, because that residual reflects framework enqueue overhead already captured by $\Delta FT$ and $\Delta CT$.

4. Host-Device Balance Index (HDBI)

The per-kernel decomposition explains where host time is spent; it does not by itself tell the operator whether the host is in fact the bottleneck. For that summary judgement, the paper introduces a second metric. The Host-Device Balance Index is the ratio of device-active time to the sum of device-active and host-orchestration time, and it lives in the open interval between zero and one.

(3) $$\mathrm{HDBI} \;=\; \frac{T_{DeviceActive}}{T_{DeviceActive} + T_{Orchestration}} \;\in\; (0,1)$$

4.1 Reading the Index

A workload with $\mathrm{HDBI} \to 0$ is host-bound: the GPU spends most of the wall-clock window waiting for the host. A workload with $\mathrm{HDBI} \to 1$ is device-bound: the host has finished its share before the GPU does. The two extremes call for different optimization layers: a host-bound workload benefits from compilation, kernel fusion, or a faster single-threaded CPU; a device-bound workload requires kernel-level optimization such as FlashAttention-2 or a faster GPU. The diagnostic interpretation is therefore that HDBI selects which axis to invest engineering effort in, and the per-kernel decomposition then selects which sub-layer within that axis to target.

4.2 HDBI vs Coarse Utilization

HDBI is intentionally distinct from the GPU utilization figure that vendor profilers report. GPU utilization measures device-active time against wall-clock latency and therefore folds host-side stalls into the denominator. HDBI explicitly separates host-orchestration time as its own quantity, so a workload with 60% GPU utilization can resolve to either a moderately host-bound regime if $T_{Orchestration}$ is the gap, or a kernel-fragmentation regime if $T_{DeviceActive}$ is split across many small kernels. The two cases call for entirely different remediation, and HDBI together with the per-kernel decomposition is what allows the operator to tell them apart.

5. Two-Phase Measurement Pipeline

The decomposition equations rely on quantities that cannot be read directly from any single profiler. To populate the equations, TaxBreak runs a two-phase measurement pipeline. Phase 1 captures Python-visible framework overhead from a full-model trace and builds a kernel database keyed by canonical kernel name, grid/block configuration, ATen metadata, and invocation frequency. Phase 2 measures $T_{sys}^{floor}$ with a null-kernel nsys run, then replays each unique kernel in isolation to measure its dispatch translation, launch-floor cost, and the per-family residuals without queue interference.

5.1 Phase 1: Full-Model Trace

Each measurement run starts with $W = 50$ warm-up iterations to stabilize the dynamic system floor, followed by $R = 150$ measured iterations under PyTorch Profiler. The profiler captures timestamped Python and Torch operators, ATen operators, CUDA runtime calls, and GPU kernels, all linked by correlation identifiers. From the last profiled iteration the pipeline extracts the kernel launch sequence and computes the framework translation per invocation as the gap between the Python-side dispatch boundary and the ATen C++ boundary.

(4) $$\Delta FT^{(i)} \;=\; T_{Py}^{(i)} \;+\; T_{dispatch\_base}, \qquad T_{Py}^{(i)} = t_{aten\_op}^{(i)} - t_{torch\_op}^{(i)}$$

5.2 Phase 2: Isolation Replay

Phase 2 first measures the null-kernel floor $T_{sys}^{floor}$, defined as the mean raw launch interval of an empty C++ __global__ null kernel profiled under the same protocol. Then, for each kernel-database entry, the pipeline replays the original ATen operation in isolation under nsys. Kernels sharing identical ATen metadata, target kernel name, and launch configuration are deduplicated via a global cache and partitioned so that only uncached entries are profiled. Each replay is bounded by an NVTX range and serialized with torch.cuda.synchronize() to prevent GPU-queue overlap, so that the recorded launch path reflects the dispatch chain of one kernel rather than the residual queueing of a steady-state run.

5.3 NVTX-Annotated Per-Kernel Window

Each per-kernel replay window is bracketed by an NVTX range push and pop, with three timestamps captured: $t_{nvtx}$ at the open of the range, $t_{api}$ at the host-side dispatch boundary (cudaLaunchKernel issuance), and $t_{kernel}$ at the GPU-side kernel execution start. The host dispatch interval is then $t_{api} - t_{nvtx}$, and the launch gap is $t_{kernel} - t_{api}$. These three timestamps are sufficient to populate the dispatch baseline, the library translation residual, and the launch-floor estimate for every kernel family.

nvtx.range_push("aten_dispatch")   # t_nvtx (1)
execute_operation(op_name, inputs)  # t_api (2)
nvtx.range_pop()                    # t_kernel (3)
torch.cuda.synchronize()            # kernel complete

Each named call in the sketch establishes one timestamp. The opening range push records $t_{nvtx}$ before any dispatcher work begins, so its delta against $t_{api}$ later isolates the Python and ATen dispatcher portion of the path. The execute-operation call drives one full host-side dispatch, ending at $t_{api}$ when the dispatcher reaches cudaLaunchKernel; the gap from $t_{api}$ to $t_{kernel}$ captures the launch-floor interval that null-kernel calibration uses as $T_{sys}^{floor}$. Closing the NVTX range and then synchronizing the CUDA stream serialize the replay so that the next kernel's measurement is not contaminated by overlap. Synchronization is necessary precisely because the replay is per-kernel: without it, the host would continue issuing dispatches while the GPU is still draining the previous one, which would conflate launch overhead with queue overlap and corrupt the per-family residual estimate.

(5)–(6) $$T_{dispatch}^{(j)} \;=\; t_{api}^{(j)} - t_{nvtx}^{(j)} \qquad T_{launch}^{(j)} \;=\; t_{kernel}^{(j)} - t_{api}^{(j)}$$

5.4 Dispatch Baseline and Per-Family Residuals

The dispatch baseline $T_{dispatch\_base}$ is the median of $T_{dispatch}^{(k)}$ across all kernels with $\mathbb{1}_{lib} = 0$, exposing the irreducible ATen-to-C++ cost in the absence of any vendor-library front-end. With that baseline fixed, the library translation residual for any library-mediated kernel is the positive part of the gap between its measured dispatch and the baseline. The framework-attributable launch residual $\Delta KT_{fw}$ is reported as the positive part of the gap between the raw launch interval $T_{launch}$ and the null-kernel floor $T_{sys}^{floor}$; this residual is informative but is not summed into Equation 2, because $\Delta FT$ already covers the framework enqueue path that produces it.

(7) $$T_{dispatch\_base} \;=\; \mathrm{median}\Big(\{ T_{dispatch}^{(k)} : \mathbb{1}_{lib}^{(k)} = 0 \}\Big)$$
(8) $$\Delta CT \;=\; \max\big(0,\; T_{dispatch} - T_{dispatch\_base}\big)$$

5.5 Kernel Matching Discipline

A replay may dispatch a variant kernel that differs from the original trace owing to vendor-library autotuning. After narrowing replay candidates to the target neighborhood, the methodology resolves the final kernel via the following name-based fallback hierarchy, where $\bar n$ denotes the cleaned canonical kernel name: exact match if the replay name equals the trace name; substring match if the replay name is a substring of the trace name, or the trace name is a substring of the replay name; otherwise the most-frequent replay name is used. This three-tier match keeps the replayed kernel comparable to the captured trace even when cuBLAS picks a slightly different sm90_xmma variant on re-entry.

(9) $$\mathrm{match}(k) \;=\; \begin{cases} \mathrm{exact}, & \bar n_{\mathrm{replay}} = \bar n_{\mathrm{trace}} \\ \mathrm{substring}, & \bar n_{\mathrm{replay}} \subseteq \bar n_{\mathrm{trace}} \;\vee\; \bar n_{\mathrm{trace}} \subseteq \bar n_{\mathrm{replay}} \\ \mathrm{most\text{-}frequent}, & \mathrm{otherwise} \end{cases}$$

6. Experimental Infrastructure

The experimental setup is designed to make the cross-platform CPU comparison a controlled study rather than a confounded benchmark. Both platforms share Hopper-generation GPUs and a fixed per-GPU host-side allocation, so any latency difference attributable to host orchestration must arise from the CPU rather than from differences in operating-system scheduling headroom.

7. Results — Where the Tax Actually Lives

The end-to-end measurements show two distinct trajectories. Dense models start host-bound at small batches but cross over into compute- or memory-bound as workload grows; MoE models do not cross over within the measured range and remain host-bound across both prefill and decode. The per-kernel decomposition explains why: MoE kernel fragmentation produces an order-of-magnitude more launches per output token, and the resulting host-side cost amortizes only weakly across batch size or context length.

7.1 End-to-End Prefill and Decode Latency

Dense prefill scales primarily with sequence length because attention work grows with prompt length: for Llama-3.2-1B on H100, latency rises from 22 ms at SL=512 to 586 ms at SL=8192 (26.6× growth), while Llama-3.2-3B reaches 827 ms at SL=8192. Batching amortizes fixed overhead effectively in this regime: at SL=512, increasing batch size from 1 to 16 raises Llama-3.2-1B prefill latency by only 3.6× (22 ms to 79 ms). Dense decode behaves differently. At (BS=1, SL=512), generating 10 decode tokens requires 188 ms versus 22 ms for prefill over the same context. As sequence length grows, the decode bottleneck shifts toward KV-cache memory traffic, reaching 756 ms at SL=8192.

MoE prefills and decodes differ qualitatively because routing introduces many short, dependency-chained kernels. On H100 at (BS=1, SL=512), OLMoE-1B/7B prefill takes 260.5 ms, 11.7× slower than Llama-3.2-1B despite similar activated parameter count, and dispatches 13,741 kernels versus 850 for the dense model. Qwen1.5-MoE-A2.7B is even more fragmented at the same point, with 22,558 kernel launches. In decode, host bottleneck becomes dominant: OLMoE-1B/7B reaches 2157 ms at (BS=1, SL=512) — 11.5× slower than dense Llama-3.2-1B — and remains nearly flat across context length, varying only from 2081 ms at SL=512 to 2164 ms at SL=4096. This weak context sensitivity reflects a dispatch-dominated regime: at (BS=4, SL=2048, $m=10$), OLMoE-1B/7B dispatches 9,305 kernels per token; with a per-kernel floor of about 4.7 µs, launch-path cost alone contributes about 44 ms per token before framework dispatch is added.

7.3 Null-Kernel Floor and Per-Family Residuals

8. CPU Single-Thread Performance Is a First-Order Parameter

The paper's most counter-intuitive measurement is that the CPU, paired with an otherwise slower GPU, can deliver an end-to-end speedup. The H100 platform pairs an Intel Xeon 8480C (Sapphire Rapids, base 2.0 GHz / turbo 3.8 GHz) with a 1980 MHz GPU; the H200 platform pairs an Intel Xeon Gold 6538Y+ (Emerald Rapids, base 2.2 GHz / turbo 4.0 GHz) with a 1785 MHz GPU. The H200 GPU runs at a 9.9% lower clock than the H100, so any end-to-end speedup observed on the H200 platform cannot be attributed to GPU compute and must come from the faster host CPU.

8.1 Orchestration Tracks CPU Single-Thread Speed

$T_{Orchestration}$ is 10–29% lower on H200 across the measured workloads, even though the GPU is unchanged at the same model and context. Because the GPU is the same and the H200 GPU clock is lower, this reduction is attributable to the faster host-side dispatch on Emerald Rapids: the per-kernel framework-translation cost is lower, and a single-threaded dispatcher amortizes that improvement across every one of the thousands of kernels per token. $T_{DeviceActive}$ remains comparable on H200, ruling out GPU memory bandwidth as the source of the improvement. The relationship between the two components reverses at higher load: at (BS=4, SL=2048) Llama-3.2-1B prefill is strongly device-bound (HDBI=0.93), so a 13% drop in $T_{Orchestration}$ yields only a 5% end-to-end gain. Qwen1.5-MoE-A2.7B at the same point remains host-bound (HDBI=0.24), and the same 13% drop in $T_{Orchestration}$ still produces an 8% latency gain.

8.2 Decode Amplifies the CPU Effect

For Llama-3.2-1B, decode reduces $T_{Orchestration}$ by 29% on H200 and 14% in prefill, because decode issues approximately 10× more kernel launches per output token (8,437 versus 850). The per-dispatch saving compounds much more strongly under decode, where each token traverses the same single-threaded dispatcher. The cross-platform conclusion is therefore direct: for host-bound LLM inference, and especially for MoE decode, CPU single-thread performance is a first-order design parameter, on a par with GPU choice. An operator who deploys a Hopper-class GPU but pairs it with an older CPU is leaving 11–14% of end-to-end latency on the table.

9. Case Studies — TaxBreak in Action

Two case studies show how the layered decomposition gives an answer that aggregate metrics could not. The first compares TaxBreak's HDBI against the prior TKLQT metric on a single workload to show that boundedness ratios alone can disagree about where optimization should be invested. The second uses TaxBreak to attribute the speedup obtained by replacing eager attention with FlashAttention-2, demonstrating that a measured FlashAttention-2 gain at long sequences is primarily a device-side reduction rather than a host-overhead one.

9.1 GPT-2 on H200: HDBI vs TKLQT

GPT-2 124M on H200 at (SL=512) is the calibration workload most directly comparable to prior TKLQT studies. TaxBreak shows that HDBI rises monotonically with batch size, from 0.25 at BS=1 to 0.74 at BS=16, placing the host-to-device crossover between BS=4 and BS=8. The source of this transition is informative: $T_{Orchestration}$ stays nearly flat across batch sizes ranging from 5.04 ms at BS=1 to 5.52 ms at BS=16. This batch-size invariance is consistent with a serial dispatch path — larger batches increase GPU work without materially changing host submission behavior. Normalizing by kernel count (376 to 394 across batch sizes) yields a per-kernel cost of approximately 13.7 µs that is effectively constant within ±2.3%, confirming that $T_{Orchestration}$ scales linearly with $N$ at a fixed per-dispatch overhead.

The contrast with TKLQT is instructive. Both metrics capture the same regime shift, but TKLQT rises much more sharply at larger batch sizes because it includes queue delay once the GPU becomes occupied. HDBI remains interpretable across both regimes because it reflects the balance between $T_{DeviceActive}$ and $T_{Orchestration}$ rather than the exposed launch path alone. For GPT-2 on H200, TaxBreak further shows that the crossover is driven by increasing device work while host orchestration remains nearly flat and is dominated by $T_{dispatch\_base}$, with no hidden vendor-library contribution. This zero-$\Delta CT$ result reflects GPT-2's matrix-multiply kernels being emitted as framework-native nvJit GEMM rather than cuBLAS/cuDNN: $\mathbb{1}_{lib} = 0$ and $\Delta CT$ is gated to zero.

9.2 Eager vs FlashAttention-2 for Llama-3.2-1B on H200

The second case study contrasts eager execution against FlashAttention-2 (FA2) for Llama-3.2-1B on H200 to test whether a measured kernel-level optimization yields a host-side or device-side win. At the smaller configuration (BS=1, SL=512), FA2 reduces end-to-end latency from 19.5 ms to 18.1 ms (7.2%) and lowers $T_{Orchestration}$ from 9.8 ms to 9.1 ms (7.1%); HDBI decreases from 0.38 to 0.33 because $T_{DeviceActive}$ falls faster than host orchestration. At the larger configuration (BS=8, SL=2048) the gain is much larger: FA2 reduces end-to-end latency from 303.9 ms to 95.5 ms (68.6%) and reduces $T_{Orchestration}$ from 11.7 ms to 8.9 ms (24%).

GPU utilization remains effectively saturated in both modes (97.9% eager vs 96.5% FA2), so the primary benefit at long context is not improved occupancy but a large reduction in device-side work per token: FA2's tiled, online-softmax kernel avoids materializing the full $N \times N$ attention matrix to HBM, substantially reducing memory traffic by eliminating intermediate read-back round trips. The HDBI decrease from 0.96 to 0.90 reflects FA2 cutting $T_{DeviceActive}$ faster than host orchestration, enlarging the host-visible share despite both absolute values improving. FA2 also exemplifies the kernel-fusion prescription that TaxBreak makes diagnostic: by collapsing the multi-kernel attention sequence into a single fused kernel, FA2 reduces dispatch count from 850 to 791 (−7%) at (BS=1, SL=512) and from 903 to 731 (−19%) at (BS=8, SL=2048). The corresponding $N \cdot T_{sys}^{floor}$ term drops by 0.3 ms and 0.8 ms respectively, consistent with the eliminated launches multiplied by the per-kernel floor.

9.3 What These Two Cases Together Demonstrate

The GPT-2 case shows that the boundedness ratio alone can be misleading: at large batches GPT-2 looks “device-bound” by either HDBI or TKLQT, but TaxBreak shows that host orchestration is essentially fixed and the transition is purely a device-work effect, leaving no host-side optimization headroom. The FA2 case shows the opposite: at long context FA2 produces a 68.6% end-to-end gain, but only 24% of that is on the host side; an operator who reads only $T_{Orchestration}$ would underestimate the optimization's effect, and an operator who reads only end-to-end latency would attribute the entire gain to FA2 when in fact 7% of the launches were eliminated as a side effect. The layered decomposition is the only artefact that gives the operator both numbers simultaneously.

10. Related Work and Positioning

TaxBreak sits at the intersection of three research lines: AI-tax / framework-tax studies, kernel-launch and queue characterization, and device-side GPU profiling for LLMs. The contribution claim is that no prior work combines per-layer host-side attribution with coverage of both prefill and decode on dense and MoE LLMs running on Hopper hardware. The positioning is summarized in the comparison table from Section 1.6 above; this section expands on the immediate prior works that share methodology or motivation.

10.1 AI Tax / Framework Tax

The AI Tax line of work (Richins et al.) documents that pipeline and infrastructure costs can dominate real deployments and provides a framework for measuring those costs in server-class workloads — but the workloads are FaceNet / R-CNN class, the evaluation is edge-data-center-oriented, and the cross-stack attribution is pipeline-level rather than per-layer. The Framework Tax line (Geoffrey et al.) is the closest precedent on methodology: it isolates the host-vs-GPU gap as a residual quantity, motivates the framework-bound vs compute-bound classification, and supplies the conceptual vocabulary that TaxBreak refines. Its limitation is the same as its strength: it treats the entire pre-GPU stack as one aggregate residual.

10.2 Kernel Launch and Queue Tax (TKLQT)

The Kernel-Tax / TKLQT line (Park et al.) sharpens the measurement to the cudaLaunchKernel-to-GPU-execution interval and provides per-kernel CUDA queue tax measurements on PCIe-attached A100/H100 and tightly-coupled GH200 systems. TKLQT is a precise, well-instrumented metric for the launch and queue layer, and TaxBreak uses TKLQT as a calibration point in the GPT-2 case study. The complementarity is clear: TKLQT measures the launch-path layer of the stack with high resolution, while TaxBreak measures the framework-translation and library-translation layers that sit above it. An operator who is told TKLQT alone cannot distinguish a workload bottlenecked by Python-side ATen overhead from one bottlenecked by cuBLAS heuristic selection.

10.3 LLM-Serving Optimizations as Application Context

The optimizations that TaxBreak prescribes — kernel fusion, AOT compilation, CUDA Graphs, faster CPU pairing — connect to a body of LLM-serving work that has matured rapidly. Sarathi-Serve, DistServe, vLLM, and Orca all redesign the serving runtime to amortize host-side cost across many concurrent requests, but each of them sits above the framework layer that TaxBreak measures and therefore cannot localize the layer-resolved bottleneck within a single forward step. The TaxBreak diagnostic is intended to inform the choice between such serving-layer optimizations and the lower-level remediation that targets the actual sub-layer carrying the cost.

11. Limitations and Takeaways

TaxBreak is a measurement methodology; it does not, in itself, remove a microsecond of overhead. Its value lies in giving the operator a layer-resolved attribution of host-side time so that the next optimization is selected against evidence rather than against the aggregate residual. The methodology has well-defined limitations, and the operator-facing takeaways follow from those limitations as much as from the positive results.

11.1 Stated Limitations

The limitations below circumscribe the regimes in which TaxBreak's attribution can be trusted. They fall into four classes: vendor coverage of the tracing surface, fidelity of the kernel-replay assumption, the diagnostic-only status of HDBI, and the scope of the single-GPU evaluation.

  • Vendor scope is currently NVIDIA-only because the methodology depends on CUDA tracing interfaces; porting to AMD ROCm or Intel oneAPI would require an equivalent tracing surface that exposes per-kernel host-side timestamps with comparable resolution.
  • Replay fidelity drops for highly dynamic, autotuned, or synchronization-heavy kernels whose isolation behavior diverges from in-step execution; the three-tier name match introduced in §5.5 mitigates the drift but does not eliminate it.
  • HDBI is a diagnostic work ratio rather than an optimization objective, and is meaningful only when read alongside absolute latency and the per-layer TaxBreak decomposition; treating HDBI as a target to maximize in isolation would invert the methodology's intent.
  • The evaluation is single-GPU, so multi-GPU and distributed inference settings — which introduce inter-GPU communication, collective scheduling, and NCCL or NVLink overhead — sit outside the model TaxBreak has been calibrated against.

11.2 Operator-Facing Takeaways

The takeaways below translate TaxBreak's decomposition into operator decisions. Each one names a diagnostic signature in the decomposition and the remediation that the signature implies — first for stack-bound configurations, then for launch-bound and driver-bound configurations, and finally for the procurement decision that the host-bound MoE regime reframes.

  • When HDBI is low and $\Delta FT + \Delta CT$ dominates, the bottleneck sits in the software stack — Python dispatch or library front-end overhead — and the right remediation is compilation (torch.compile) or library-path replacement.
  • When HDBI is low and $N \cdot T_{sys}^{floor}$ dominates, the cost scales with launch count, so kernel fusion or CUDA Graphs will yield the largest reduction.
  • When the per-kernel framework-launch residual $\Delta KT_{fw}$ is significant, the driver/runtime path is the bottleneck; CUDA Graphs or persistent kernels help amortize the cost.
  • For host-bound MoE decode the procurement balance shifts: a faster single-thread CPU returns 11–14% of end-to-end latency even when paired with a slower GPU, so the methodology supports re-allocating budget from accelerator generation to host-side single-thread performance in that regime.

Final reading: TaxBreak's core claim is not that any single bottleneck — framework dispatch, library front-end, or launch floor — universally dominates LLM inference.
