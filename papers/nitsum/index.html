Nitsum

Serving Tiered LLM Requests with Adaptive Tensor Parallelism — promoting TP from a deployment knob to a sub-second runtime control surface.

arXiv:2605.05467 May 2026 cs.DC Tiered SLO Dynamic TP PD Disaggregation

Vikranth Srivatsa, Zijian He, Pu Guo, Dongming Li, Yiying Zhang

University of California San Diego · GenseeAI Inc.

1. Why now: production traffic stopped being single-tier

Until roughly 2023, the LLM serving literature could legitimately treat a deployment as having one SLO at a time. A chat product optimized TTFT; a batch-summarization service optimized throughput; the two were operated on separate clusters with separate budgets, so each scheduler had only one objective to honor at any moment. Production traffic in 2025-2026 has broken this assumption. The same model checkpoint and the same GPU pool now serve a workload mix that contains, simultaneously, interactive code-completion requests that require a TTFT below 300 ms, longer interactive conversations with a TTFT budget closer to 500 ms, agent-style background calls that are willing to wait several seconds for the first token, and bulk summarization or evaluation jobs whose deadline is measured in minutes.

Two infrastructure pressures are responsible for this consolidation. The first is unit economics: a Hopper-class GPU rents at multi-dollar per hour, and provisioning a separate cluster for each SLO tier leaves expensive accelerators idle whenever that tier's traffic dips. Operators are therefore pooling traffic across tiers, accepting the scheduling complexity in exchange for utilization. The second is model homogenization: a single model family of a given size is now reused across all of these use cases, so the only differentiator at the serving layer is the SLO the request was admitted under, not the model weights it touches.

The paper grounds this shift in the ServeGen workload, which mirrors the Alibaba production trace. Within a ten-minute window on an eight-GPU H100 cluster running Llama-3.1-8B, the conversation and coding mixes oscillate substantially in both arrival rate and prompt-length distribution. The configuration of GPUs that maximizes goodput at minute three is not the configuration that maximizes goodput at minute seven, even though the SLO targets and the model checkpoint have not changed.

Figure 1 (from paper): ServeGen conversation and coding workloads on 8 H100 GPUs serving Llama-3.1-8B over a ten-minute window. Top: the per-second request arrival pattern for each tier. Middle: the configuration (request group | prefill / decode stage | TP level) that maximizes goodput at each instant — note that the optimal mapping changes multiple times within the window. The figure motivates treating execution configuration as a runtime control, not a deployment constant.

2. A concrete failure: what a static config does on this workload

To make the cost of a static execution configuration concrete, consider a single ten-minute slice of the ServeGen trace served on four A100 GPUs by Llama-3.1-8B. The mix consists of a strict tier requiring 500 ms TTFT and 15 ms TPOT, and a loose tier requiring 500 ms TTFT and 30 ms TPOT. Suppose the operator commits to a single execution configuration for the entire slice. Three obvious choices exist: run all four GPUs at tensor-parallel degree 1 with prefill and decode co-located, run all four GPUs at TP=2, or split the cluster so that prefill runs at TP=1 on two GPUs and decode runs at TP=2 on the other two.

The paper's measurement (Figure 3) shows that none of these three static choices dominates for more than a fraction of the window. When arrivals are heavy and prompts are short, TP=1 with co-located stages packs the largest decode batches and wins. When arrivals are heavy and prompts are long, the prefill-decode split reduces head-of-line blocking on long prefills and wins. When arrivals are light, the higher TP degree wins on TTFT because tensor shards become small enough that compute, not communication, is the binding constraint. An oracle that may switch among these three configurations every second outperforms every fixed choice; the paper measures the gap at 23-29% additional goodput, and the gap is the part of capacity that any static deployment leaves on the table.

A second observation in the same figure is more severe. When incoming load rises above roughly 40 requests per second, the goodput of every static configuration collapses to a small fraction of arrivals, because each configuration has at least one tier whose service time exceeds the SLO under that load. A scheduler that controls only when requests run cannot recover this lost capacity — by the time a request has been queued, dispatched, and given to a backend that is fundamentally too slow for its tier, the deadline has already been missed.

3. The fundamental obstacle: when-to-run is not enough

The reason a request-level scheduler cannot close the gap shown in the previous section is structural, not algorithmic. Every existing SLO-aware serving system — Llumnix, Chiron, QLM, SCOOT, and to a large extent DistServe and SplitWise — operates on a control surface that decides which request runs on which backend, in which order, and with what batch composition. The backend's per-request service time, however, is fixed by the execution configuration that was chosen when the backend was launched: the tensor-parallel degree, the prefill-decode partition, the compiled CUDA graphs, the kernel selections. A scheduler whose action space is restricted to picking among backends with already-determined service times can rearrange the order in which deadlines are missed; it cannot make a request whose required service time is 12 ms run on a backend whose service time is 18 ms.

A second structural issue is that the optimal execution configuration for a given workload mix is itself non-stationary. The paper's measurement of tensor parallelism on a 14B model on A100 and a 70B model on H100 and B200 (Figure 2) shows that raising TP from 1 to 2 to 4 to 8 reduces TTFT monotonically for every input length, but its effect on per-GPU decode throughput is non-monotonic in batch size. At batch size 1, raising TP to 4 produces roughly a 3x throughput advantage because the smaller per-GPU tensor shards fit in L2 cache and reduce HBM traffic; as batch size grows, communication cost dominates and the advantage shrinks, eventually flipping. There is therefore no single TP degree that is best across the realistic range of decode batch sizes — and the realistic range itself changes as the workload mix and load intensity drift over time.

Figure 2a: Prefill TTFT versus input length for the 14B model on A100 across TP = 1, 2, 4, 8. Higher TP reduces TTFT monotonically.
Figure 2b: Per-GPU decode throughput (normalized) versus batch size on A100. The TP that maximizes decode throughput depends on batch size, so no single TP degree dominates over the workload's realistic batch-size range.

The combination of these two observations is what makes the problem genuinely require an execution-level control. The optimal service time for each tier depends on a moment-by-moment property of the workload (which TP / partition the backend should expose), and the service time of every backend has been baked in at deployment. Any solution that does not adjust execution configuration at second-scale must therefore either over-provision (run multiple separate clusters, accepting low utilization) or accept that whichever tier is unlucky in this minute will miss its SLO.

4. Strawman: the obvious fixes and why each one fails

A reader at this point may ask why an operator would not simply split the cluster into per-tier slices, or, conversely, why the operator would not simply implement classical TP reconfiguration as a runtime control. The paper considers both and shows each to fail for a different structural reason, which clears the design space for the actual contribution.

4.1 Strawman A: partition the cluster by tier

Allocate two GPUs to the strict tier and two to the loose tier, each running the static TP that is best for that tier in isolation. This restores per-tier optimization and eliminates interference. The structural problem is that the optimal partition is workload-dependent: when 80% of arrivals in a minute are loose-tier requests, the two strict-tier GPUs sit idle while the loose-tier partition is over-subscribed; when the mix inverts, the opposite occurs. Rebalancing capacity between the partitions every second to chase the workload is, by inspection, the same scheduling problem in a different costume — except that it now also pays the cost of cold-loading model weights every time it shifts a GPU from one tier to the other.

4.2 Strawman B: classical TP reconfiguration as runtime control

The dual strawman accepts that TP must change at runtime and implements it the obvious way: when the policy decides to switch from TP=2 to TP=4, redistribute the weights across GPUs, repartition the running requests' KV-cache heads, and resume. The paper measures this naive approach end-to-end on Qwen-14B and reports approximately 30 seconds per TP change for the weight redistribution alone, even with the weights already cached on each GPU's local SSD. A second variant stores one weight copy per TP level on each GPU to avoid the redistribution; this consumes 56% of the GPU memory budget on a 13B Llama model and leaves correspondingly less HBM for KV cache. A third variant migrates running KV using cudaMemcpyAsync over the PagedAttention page table; because each page is a separate small allocation, each requires its own async copy, and the resulting overhead measures in hundreds of milliseconds for the working sets the system actually has to move.

The ablation study confirms the magnitude of this obstacle. When the paper inserts a runtime TP-switching policy into vanilla SGLang and implements both the weight reload and the KV migration the obvious way, end-to-end goodput collapses to zero on the experimental workload because every switch stalls service for longer than the SLO permits. The conclusion is that runtime TP control is not merely an interesting algorithmic question; it is a question whose answer depends entirely on whether the switching mechanisms can be made fast enough that the control loop is worth running at all.

The point is that the prior works are not wrong; they each optimize an action surface that is necessary but, by itself, insufficient for the 2025-2026 tiered-SLO setting.

6. The central insight: tensor parallelism as a control surface

The paper's framing is that the tensor-parallel degree is not, in fact, a deployment constant; it is a knob that — under appropriate engineering — can be turned on the same time scale as a batching decision. Once TP is admitted to the action space, the scheduler gains two qualitatively new abilities. It can satisfy the strict tier by raising TP so that prefill and small-batch decode complete fast enough to meet TTFT and tail TPOT. It can simultaneously satisfy the loose tier by lowering TP on a different subset of GPUs so that decode runs in large batches and saturates the cluster's throughput.

The non-obvious part of this claim is the L2 cache effect at small decode batches. Conventional intuition treats higher TP as a pure TTFT win paid for in inter-GPU communication and thus a decode-throughput loss. The paper's measurement on A100 (Figure 2c-d) shows that this intuition is wrong below a workload-dependent batch-size threshold: as TP rises, each GPU's tensor shard shrinks, the active working set fits in L2, and the resulting HBM-traffic reduction dominates the NVLink communication cost. The effect is large — roughly 3x throughput advantage at batch size 1 — and it disappears as batch size grows. The scheduler therefore prefers high TP when the cluster is lightly loaded (small batches) and low TP when it is heavily loaded (large batches), exactly the opposite of what a deployment-time choice would commit to.

Figure 2c: L2 cache hit rate versus decode batch size for the 14B model on A100 across TP = 1, 2, 4, 8. Higher TP shrinks the per-GPU shard until it fits in L2, sharply raising the hit rate at small batches.
Figure 2d: Inter-GPU communication cost versus decode batch size on A100. Communication grows with TP, but at small batches the L2-cache gain still dominates; the crossover defines the batch-size threshold below which the scheduler should prefer higher TP.
Why this insight is load-bearing. If the optimal TP were monotonic in batch size, a moderately sophisticated static deployment could approximate it well. The non-monotonicity, combined with the workload's drift in arrival rate and prompt-length distribution, is what forces the optimal TP to change within minutes and what therefore forces the scheduler to be allowed to change it within minutes.

7. What Nitsum contributes

With the motivation now established, the system's contributions can be stated in their proper order. Each is necessary; removing any one is shown in the ablation to collapse end-to-end goodput.

C1. TP as runtime control

Reframes tensor parallelism from a deployment constant to a runtime variable, then characterizes its effect on TTFT, decode throughput, L2 cache hit rate, and inter-GPU communication across 14B and 70B models on A100, H100, and B200, establishing that no single TP degree dominates across the realistic workload range.

C2. Zero-overhead TP weight switching

Each GPU holds a single full weight copy and exposes TP-specific shards via a small kernel-side selector. Warm processes for every candidate TP level are pre-launched and pre-compiled (CUDA graphs, torch.compile); switching activates a warm process and hibernates the rest, eliminating the ~30 s redistribution cost.

C3. Aggregated, pipelined KV migration

A custom kernel coalesces fragmented PagedAttention regions into a contiguous staging buffer while the previous stage's bytes are still in flight on the network, overlapping the two phases. Measured speedup is 245-376x versus cudaMemcpyAsync, bringing 0.5-5 GB KV migrations from 0.88-9.25 s down to 3.6-24.8 ms — fast enough to live inside a 1 s control window.

C4. Goodput-aware joint policy

A reconfiguration policy that jointly selects per-tier TP level and prefill/decode GPU split each control window using offline-profiled per-stage throughput, paired with an SLO-aware request scheduler that tracks per-GPU SLO-compliant available bandwidth, classifies arriving requests as feasible or best-effort, and isolates background traffic into a designated pool.

8. System architecture

Nitsum is built atop SGLang and adds a thin control plane that runs out-of-band from the request path. The control plane comprises three components arranged as a 1 Hz outer loop and a continuously running inner loop. The outer loop, called the cluster reconfiguration policy, takes recent arrival statistics and the offline performance profile as inputs and emits a configuration vector — one (TP-prefill, TP-decode, GPU-count-prefill, GPU-count-decode) tuple per request tier. The inner loop, the SLO-aware request scheduler, dispatches arriving requests into the configuration chosen by the outer loop. The TP-switching mechanism and KV-migration kernel sit inside the data plane: they are invoked when the outer loop's decision differs from the prior one.

Figure 4 (from paper): Nitsum architecture. The control plane runs a 1 Hz reconfiguration policy whose decisions are realized by warm-process activation (TP weight switching) and a coalesced pipelined KV migration. The request scheduler is the inner loop, dispatching arriving requests against the bandwidth budget exposed by the current configuration.

A single design choice unifies the four contributions: every action the control plane takes must complete within the 1 s control window, otherwise the policy is reacting to a stale picture of the workload. The 1 s budget is what sets the engineering requirement on the weight-switching and KV-migration mechanisms; conversely, it is the existence of those fast mechanisms that justifies running the policy at 1 Hz rather than at the autoscaling-typical timescale of minutes.

9. Mechanism 1: TP-aware weight reuse

The first mechanism eliminates weight-transfer cost across TP transitions. The starting observation is that, regardless of TP degree, the sharded weight that a GPU needs to hold for a particular layer is a contiguous slice of the unsharded weight tensor. When TP=2, GPU-0 needs the first half of each weight matrix along the sharded axis; when TP=4 on the same node, GPU-0 needs the first quarter; when TP=1, GPU-0 needs the entire matrix. The system therefore stores the full unsharded weight once per GPU and selects the appropriate slice at execution time via a thin kernel-side selector. No bytes move between GPUs at a TP switch, because each GPU already holds every slice it will ever need.

The remaining cost is the runtime infrastructure: each TP level requires its own process, its own NCCL communicator, its own CUDA graphs, and its own torch.compile cache. Building this infrastructure on the critical path of a TP switch would cost hundreds of milliseconds. The system therefore pre-launches a process per candidate TP level at deployment, runs them through a warm-up step that captures CUDA graphs and torch.compile cache entries, and leaves them resident but idle. A TP switch is reduced to a single operation: signal the warm process for the new TP level to take over, and signal the previous one to hibernate. The active process at any given moment is the one whose TP level the policy has selected.

Figure 5 (from paper): Three approaches to dynamic TP. Strawman 1 redistributes weights across GPUs at every switch (~30 s for 14B). Strawman 2 stores a per-TP weight copy and reloads on demand (consumes 56% of GPU memory). Nitsum keeps one full copy per GPU plus a warm pre-compiled process per TP level; switching is process activation, not weight movement.

The memory overhead of this scheme is bounded by one full weight copy per GPU rather than one per TP level. For Llama-3.1-8B on an 80 GB A100, the full weight is approximately 16 GB; the remaining 64 GB are available for KV cache and activations. The strawman of storing one per-TP copy of the same model would push the weight footprint past 45 GB and leave only 35 GB for KV — a regression that ablation confirms collapses goodput on the loose tier, whose decode-side memory demand is high.

The asymmetry is what makes warm-process pre-launch the choice that actually composes with KV-cache demand at production scale.

10. Mechanism 2: aggregated and pipelined KV migration

The second mechanism addresses what is left over after weights have been removed from the critical path: the KV cache of in-flight requests, which must be repartitioned every time the TP level changes. The structural difficulty is that PagedAttention represents each request's KV as a list of small fixed-size pages scattered across HBM, and on a TP transition the heads on each page need to be redistributed across a different number of GPUs. A naive port of this operation onto cudaMemcpyAsync issues one async copy per page, and the per-call launch overhead — not the bytes themselves — dominates the elapsed time.

The system replaces this with a single custom kernel per source-destination pair that performs three steps simultaneously: it walks the page table on the GPU, gathers the relevant heads from the source pages into a contiguous staging buffer, and hands that buffer to NCCL for transmission. While the kernel is filling stage k of the staging buffer, NCCL is sending stage k-1 on the wire, and the destination kernel is scattering the just-arrived bytes from stage k-2 into the destination page table. The pipeline has three stages, all double-buffered, and the dominant cost is whichever stage is slowest — bandwidth for moderate-to-large KV migrations, kernel launch only for tiny ones.

Figure 6 (from paper): KV head repartitioning across a TP=1 to TP=2 to TP=4 transition on a four-GPU node with 8 KV heads. Each head's bytes follow a deterministic source-to-destination mapping that the custom kernel walks once per page table.
Figure 7 (from paper): Migration latency (log scale) versus KV payload size, for fully fragmented and contiguous layouts, across cudaMemcpyAsync, a contiguous-aware baseline, and Nitsum's coalesced pipelined kernel. Nitsum tracks the contiguous baseline regardless of fragmentation; cudaMemcpyAsync lags by 245-376x at the working sizes the system actually moves.

The reported numbers are 3.6-24.8 ms for migrations of 0.5-5 GB of KV (4,096-40,960 tokens of fp16 Llama-3.1-8B), against 0.88-9.25 s for cudaMemcpyAsync on the same payloads. The headline 245-376x speedup is the ratio of those two ranges at matching payloads. The system can therefore migrate the KV of every in-flight request on a 4-GPU node within roughly 10 ms, which is well below the per-token decode budget of even the strict tier.

11. Scheduling: goodput-aware allocation and SLO-aware dispatch

With the mechanism cost reduced to roughly 10 ms per switch, the system can afford to ask the policy questions every second. The policy itself is structured as a two-level decision: an outer cluster-reconfiguration step that picks a per-tier (TP-level, prefill/decode split) configuration, and an inner scheduling step that places each arriving request into the configuration the outer step chose.

11.1 Goodput efficiency and the assignment rule

Let a candidate configuration for tier $t$ be a pair $(\text{TP}_i, \text{TP}_j)$ — the TP degree for prefill and decode respectively — together with $P$ prefill GPUs and $D$ decode GPUs. The offline profile gives $\text{THP}_t^{\text{TP}_i}$, the maximum prefill throughput in requests per second that one GPU at TP $i$ can deliver for tier $t$'s prompt-length distribution while honoring the tier's TTFT, and the analogous $\text{THP}_t^{\text{TP}_j}$ for decode and TPOT. The system balances the two stages so neither becomes the bottleneck, and defines goodput efficiency as goodput delivered per GPU consumed:

(1) $$\text{GE}_t^{(\text{TP}_i,\text{TP}_j)} \;=\; \frac{\min\!\bigl(\,P \cdot \text{THP}_t^{\text{TP}_i},\; \text{rps}_t\,\bigr)}{P \cdot \text{TP}_i \;+\; D \cdot \text{TP}_j}$$

The numerator is the goodput the configuration actually delivers — capped by either the prefill stage's serving rate or the tier's arrival rate $\text{rps}_t$, whichever is smaller. The denominator is the GPU cost of running both stages at their chosen TP degrees. A greedy allocator that simply picked the configuration maximizing $\text{GE}_t$ would starve any tier whose efficiency happens to be lower in this window, so the system weights each tier's score by the fraction of demand it has so far failed to serve:

(2) $$\text{WGE}_t^{(\text{TP}_i,\text{TP}_j)} \;=\; \text{GE}_t^{(\text{TP}_i,\text{TP}_j)} \cdot \frac{\text{rps}_t}{\text{served\_rps}_t}$$

The allocator iterates over tiers in descending order of $\text{WGE}_t$, awarding each tier the configuration that maximizes its weighted goodput efficiency on the GPUs that have not yet been assigned. Because $\text{TP}_i, \text{TP}_j \in \{1, 2, 4, 8\}$ and the number of GPUs per node is bounded, the candidate space is small (on the order of a few hundred per tier per cluster size), and the allocator returns in roughly 2.5 ms for 128 GPUs and four tiers.

11.2 SLO-aware dispatch

The inner-loop scheduler is split between a global dispatcher (one per cluster) and a local scheduler (one per GPU). The global dispatcher maintains, for each prefill GPU, the SLO-compliant available serving bandwidth — the maximum throughput the GPU can produce in its current configuration minus the throughput it has already committed to feasible requests. An arriving request is marked feasible if adding it to a prefill GPU of its tier would not exceed that GPU's bandwidth; feasible requests are routed to the least-loaded such GPU. Requests that fail this test are spilled into a best-effort pool routed to any prefill GPU; background-tier requests bypass both checks and go directly to a designated background pool.

The local scheduler at each GPU maintains three queues — feasible SLO requests, best-effort spill, and background — and assembles each forward batch by drawing from the queues in that order, subject to the per-tier throughput bound derived from the profile. When a request completes, the local scheduler notifies the global dispatcher so that the available-bandwidth counter is restored. The combination keeps feasible requests in their preferred backend, makes opportunistic use of residual capacity for best-effort, and prevents background traffic from displacing either.

Figure 8 (from paper): The two-level scheduler. The global dispatcher tracks per-GPU SLO-compliant available bandwidth and classifies arrivals into feasible, best-effort, or background. The local scheduler on each GPU consumes its three queues in priority order, bounded by the profile's per-tier throughput cap.

12. End-to-end results

The end-to-end evaluation runs Llama-3.1-8B on 4 and 8 A100s and Qwen-14B on 4 and 8 H100s, against Azure production traces and ServeGen, with the per-configuration SLOs reproduced from the paper's Table 1. The five comparison points are Llumnix, Chiron, SGLang with prefill-decode disaggregation, vanilla SGLang, and Split — the last being a strict-vs-loose cluster partition where each side runs the static TP that is best for its tier in isolation. The headline result is that goodput remains monotonically increasing with offered RPS only for Nitsum; every baseline collapses once the offered load exceeds the bandwidth its static configuration can deliver SLO-compliantly.

13. Ablation: which contributions are load-bearing

The ablation runs Qwen-14B on 8 H100s at 70 RPS and incrementally adds components starting from vanilla SGLang. The point of the experiment is not to show that each component helps a little; it is to show that two components are individually nullifying — adding them in isolation drops goodput to zero — and become positive only when the rest of the system is also present.

The two zero-goodput rows are the part of the ablation that carries the paper's argument. Prefill/decode disaggregation is widely regarded as a near-universal serving win, and yet without dynamic reconfiguration it is actively harmful here, because the split has to be chosen at deployment and cannot track the workload. Likewise, dynamic TP is widely regarded as too expensive to consider at runtime, and the naive implementation confirms that suspicion — but with weight reuse and pipelined KV migration in place, the same dynamic-TP capability is responsible for the last 1.4x of end-to-end gain. The conclusion the paper draws is that the fast mechanisms are not an optimization on top of the policy; they are the precondition that makes the policy worth running.

14. Sensitivity and operating range

Two sensitivity experiments calibrate the regime in which the system is worth running. The first sweeps an SLO-scale factor that uniformly tightens or relaxes the targets in Table 1. The system's advantage over the best static baseline is largest at the moderate end of the range — the regime that matches production traces — and shrinks as SLOs relax, because once the targets are loose enough that the prefill stage's worst-case latency already fits inside the TTFT bound, dynamic TP has nothing left to optimize. At the strict end of the range, the absolute goodput of every system falls because the cluster is too small to honor the targets at the offered load, but the relative ordering is preserved.

The second sensitivity experiment extends the workload to three SLO tiers — interactive, deadline, and a new relaxed tier — running concurrently on the same ServeGen-derived stream. Split, the static-partition baseline, holds up reasonably well at high load because its boundaries happen to match the steady-state mix, but wastes capacity in any window whose mix departs from steady state. Nitsum dominates across the entire load range because it can re-balance among the three tiers each second.

A separate microbenchmark on the scheduler implementation itself reports 16,100 requests per second of dispatch throughput in a single-process Rust service and a 2.49 ms average reconfiguration-planning time for 128 GPUs and four tiers. Because the candidate space is bounded by the cardinality of TP levels and the number of GPUs per node, this planning time does not grow appreciably with cluster size.

15. Limitations and what remains open

Workload-dependent benefit

The system's lift is largest when the workload's optimal configuration drifts within minutes — multi-tier traffic mixes, ServeGen, Azure-like traces. On a stationary workload that the operator can already characterize at deployment, dynamic TP has little to offer and the memory overhead of the warm processes is uncompensated.

Memory overhead

Each GPU holds one full unsharded weight copy plus a warm process per candidate TP level. The weight footprint is bounded but the warm-process resident set adds a few hundred megabytes per level. The system trades this memory for the elimination of weight-redistribution and process-startup time on every switch.

Forecast dependence

The reconfiguration policy uses a recent-arrival estimate of rps per tier as input. Workloads whose arrival rate is bursty on time scales shorter than the 1 s window can cause the policy to react to a still-developing burst; the paper reports robustness across a 0.5-2 s window range but the limit is fundamental — a sub-second control loop cannot react to sub-millisecond bursts.

Scope of the control surface

The action space considered is the tensor-parallel degree and the prefill/decode GPU split. The paper notes that the same approach in principle extends to pipeline parallelism, MPS, and other execution knobs, but does not yet implement those; whether they can be made fast enough to participate in a sub-second control loop is an open engineering question.

Open-source status. The paper states the implementation will be released, but no code URL was attached to the v1 submission. Anyone wishing to reproduce the headline numbers will need either the eventual release or a reimplementation of the warm-process pre-launch, the kernel-side TP slice selector, and the coalesced pipelined KV migration on top of SGLang.
