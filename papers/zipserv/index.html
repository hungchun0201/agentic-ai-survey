Lossless BF16 compression fused with GEMM

ZipServ: Hardware-Aware Lossless Compression for LLM Inference

A BF16 lossless compression format and fused ZipGEMM kernel for memory-bound inference.

Authors Ruibo Fan, Xiangrui Yu, Xinglin Pan, Zeyu Li, Weile Luo, Qiang Wang, Wei Wang, Xiaowen Chu
Affiliation HKUST(GZ), HIT(SZ), HKUST
Venue and version ASPLOS 2026, arXiv 2603.17435v1, DOI 10.1145/3779212.3790250
Page scope Triple-bitmap encoding, fused decompression/GEMM, and GDDR-oriented inference speedups

Core Question

ZipServ targets a narrow but important bottleneck: BF16 weight traffic on memory-bandwidth-limited inference GPUs. It keeps model values exact while reducing how many bytes must be moved.

The key is not compression alone. The compression format must feed Tensor Core GEMM without materializing a full decompressed BF16 matrix in global memory.

Motivation Ladder

The main comparison is against generic compression and separate decompression. ZipServ’s advantage comes from keeping the compressed representation live until the compute tile consumes it.

The implementation is a specialized C++/CUDA kernel path optimized for GDDR memory GPUs. That scope is important: the README itself warns that gains can differ on HBM datacenter GPUs.

1

Why now

LLM inference is often limited by moving weights from memory to compute units, especially on GDDR-based inference GPUs. Quantization can reduce traffic, but it changes values and can hurt accuracy on some workloads.

The motivation narrows the target to lossless weight-traffic reduction on GPUs where memory movement can dominate inference time.

2

Concrete bad scenario

A deployment wants lower memory traffic without changing model outputs. Existing lossless codecs compress the weights, but decompression emits a temporary full BF16 matrix that is then read again by GEMM, so the bandwidth benefit is reduced.

This failure case explains why decompression must be fused with GEMM. A codec that creates a temporary BF16 matrix removes the bandwidth benefit it was meant to provide.

3

Baseline pain

General entropy coding creates variable-length bitstreams that are unfriendly to SIMT execution. Decoupled decompression and GEMM also create extra global-memory traffic, which the paper measures as a large overhead relative to core inference compute.

The baseline pain makes entropy coding the wrong shape for this workload. ZipServ needs fixed, parallel-friendly metadata that can feed Tensor Core tiles.

4

Strawman

One can decompress weights to global memory before GEMM and keep using cuBLAS. That keeps the math path simple, but it loses the main reason for compression because decompressed BF16 data travels through memory again.

The strawman preserves correctness but not locality. ZipServ keeps the compressed representation live until the compute tile consumes the values.

5

Fundamental obstacle

A useful format must be parallel-decodable, tile-aligned, and cheap enough to fuse into Tensor Core GEMM. ZipServ’s answer is to encode frequent exponent values with three bitmaps and to keep sign and mantissa in compact buffers.

This obstacle leads directly to the triple-bitmap layout: common exponents become compact metadata, while sign and mantissa remain accessible to fused decode logic.

6

Position against nearby systems

ZipServ is not a lossy quantizer and not only a storage compressor. It is a hardware-aware format plus kernels that choose fused or decoupled execution depending on the inference stage.

This positioning separates ZipServ from quantization and generic compression. Its value depends on preserving exact BF16 values while reducing memory traffic.

Claim Boundaries

The claim is limited to lossless BF16 weight traffic reduction. It should not be read as a general compression layer for arbitrary numeric formats.

The README’s GDDR scope is not incidental. The result depends on memory-bandwidth pressure being large enough for fused reconstruction to pay off.

System Map

The pipeline has an offline stage and an online stage. Offline compression builds the triple-bitmap representation; online ZipGEMM reconstructs values close to Tensor Core consumption.

This map is the core of the paper: remove global-memory traffic without changing BF16 values and without inserting a separate decompression kernel.

Analyze BF16 Find frequent exponent values across model weight matrices.
Encode tiles Store top exponent classes in three bitmaps and rare values as full BF16.
Load compressed Move bitmaps, sign-mantissa bytes, and fallback values into shared memory.
Decode in kernel Use popcount and bit operations to reconstruct BF16 fragments in registers.
Feed Tensor Cores Multiply decompressed fragments immediately without materializing a full matrix.

Mechanism Deep Dive

ZipServ has three coupled pieces: Tensor-Core-aware encoding, register-level reconstruction, and fused GEMM consumption. The format is useful only because those pieces are designed together.

The design point is locality. Values are reconstructed close to Tensor Core use, avoiding a decompressed BF16 matrix in global memory.

TCA-TBE format

Each 8 by 8 tile uses three 64-bit bitmaps to encode up to seven frequent exponent classes, while uncommon values are stored in a full BF16 buffer. This makes decode control flow regular enough for GPU execution.

Register reconstruction

The kernel reconstructs BF16 values from sign-mantissa bytes and exponent code bits using bit operations and popcount offsets. Values are reconstructed close to Tensor Core consumption.

Fused ZipGEMM

The main API selects a tiling configuration based on N and uses fast or safe kernels depending on alignment. When Split-K is used, a reduction kernel combines partial results.

Stage-aware execution

The paper separates compute-bound prefill from memory-bound decode. ZipServ uses decoupled decompression where compute dominates and fused ZipGEMM where memory traffic dominates.

Interaction Among Pieces

ZipServ’s mechanism is a format-kernel co-design. The bitmap layout would be only a storage trick without a GEMM path that reconstructs fragments close to Tensor Core use.

The interaction to watch is locality: the design saves bandwidth only when compressed bytes stay compressed until the kernel is ready to consume the BF16 value.

Implementation Trace

The code path is kernel-centric. `TilingConfig.h` fixes tile assumptions, `L_API.cu` exposes compressed GEMM entry points, and `L_Kernel.cuh` reconstructs fragments in CUDA code.

The benchmark files matter because this is not a scheduler paper. The claim lives or dies on whether the compressed kernel outperforms dense or separately decompressed execution.

  • `csrc/TilingConfig.h` fixes MMA and tile constants for BF16 triple-bitmap GEMM.
  • `build/L_API.cuh` exposes `BF16TripleBitmap_MM_API`, `BF16TripleBitmap_Decompress_API`, and compression initialization entry points.
  • `csrc/L_Kernel.cuh` reconstructs BF16 fragments from three bitmaps, sign-mantissa bytes, and full-value buffers inside CUDA kernels.
  • `kernel_benchmark/test_mm.cu` measures compression statistics, cuBLAS baselines, and BF16 triple-bitmap matrix multiplication.

Prototype Boundary

The implementation is specialized for BF16 and GDDR-oriented GPUs. It should not be read as a universal compression layer for arbitrary model formats.

HBM datacenter GPUs are a natural boundary. If memory bandwidth is less constraining or exponent distributions differ, the speedup can shrink.

Evaluation Discipline

ZipServ’s evaluation must be read in two layers: compression ratio first, then whether the fused GEMM path avoids enough memory traffic to beat dense execution.

Hardware class is part of the claim. Results on GDDR inference GPUs should not be automatically transferred to HBM datacenter GPUs without measuring the bandwidth regime.

Limitations and Failure Modes

The main limitation is format specificity. The triple-bitmap structure is tied to BF16 exponent behavior and Tensor Core tile access.

The second limitation is integration depth. A fast kernel benchmark is not the same as a complete serving-stack replacement.

GPU class dependence

The README explicitly says ZipServ is optimized for GDDR memory GPUs such as RTX 4090, L40S, RTX 5090, and RTX 6000 Pro.

BF16-specific design

The format exploits BF16 exponent distribution and Tensor Core tile shapes. Other numeric formats would need separate analysis and likely a different encoding.

Prototype scope

The GitHub code is a research prototype with C++/CUDA kernels and benchmarks; production serving integration is more limited than a full framework patch.

Takeaways

The main lesson is that lossless compression must be compute-path aware. Separating decompression from GEMM recreates the traffic the codec was meant to remove.

The second lesson is hardware specificity. The same compressed format can be excellent on one GPU memory regime and ordinary on another.

  • Lossless compression can accelerate inference only when decompression is designed with the compute kernel.
  • The main systems point is removing the intermediate decompressed matrix from global memory.
  • The design is best interpreted as hardware-aware BF16 serving, not as a general-purpose codec.

Bottom Line

ZipServ’s contribution is a lossless format designed around the GEMM execution path, not a generic codec.

Its risk is hardware and format specificity: BF16 exponent statistics and GDDR bandwidth pressure are part of the reason the result works.

Best use case

BF16 inference on memory-bandwidth-limited GDDR GPUs where weight traffic dominates.

Main risk

Other numeric formats or HBM-heavy server GPUs may not match the exponent distribution and bandwidth regime.
