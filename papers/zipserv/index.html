ZipServ: Hardware-Aware Lossless Compression for LLM Inference

A fixed-length Tensor-Core-aware compression format and a fused decompression-GEMM kernel that shrink BF16 weight traffic without ever materializing a decompressed matrix in global memory

arXiv:2603.17435 ASPLOS 2026 Lossless Compression Tensor Core GEMM Memory-bound Inference BF16 · GDDR/HBM

Ruibo Fan, Xiangrui Yu, Xinglin Pan, Zeyu Li, Weile Luo, Qiang Wang, Wei Wang, Xiaowen Chu

HKUST (Guangzhou) · Harbin Institute of Technology, Shenzhen · HKUST

1. Why Lossless Weight Compression Is Hard on a GPU

Large language model inference spends much of its time moving weights, not multiplying them. During autoregressive decoding the model reads its entire weight matrix to produce a small batch of tokens, so on a bandwidth-limited accelerator the decode step is bounded by how many bytes leave DRAM rather than by arithmetic. ZipServ asks whether those bytes can be reduced losslessly — preserving every BF16 value exactly — and still feed a Tensor Core matrix multiply without the decompression itself becoming the new bottleneck.

Figure 1 (from paper): ZipServ is positioned between lossy quantization, which reduces traffic by changing values and risking accuracy, and conventional lossless codecs, which keep values exact but pay for a separate decompression pass. ZipServ keeps the values bit-exact and fuses reconstruction into the matrix multiply.

1.1 Why now: weights, not FLOPs, set the decode clock

The weights of a modern model dwarf the activations that pass through them. A LLaMA3.1-8B checkpoint occupies 14.96 GB in BF16, and LLaMA3.1-70B occupies 131.56 GB; during decoding the engine must stream the whole of that tensor from DRAM for each small batch of tokens it generates. On inference-class GPUs built around GDDR memory — the RTX 4090, L40S, and RTX 5090 lines — sustained bandwidth ranges from roughly 0.86 to 1.8 TB/s, well below the multiple-terabyte figures of HBM datacenter parts, so the time to read the weights, not the time to multiply them, governs the decode latency. This is the regime in which reducing weight bytes translates directly into faster tokens.

Quantization is the usual response, but it changes the stored values and can degrade quality on sensitive workloads, so a deployment that must preserve model outputs exactly cannot use it. Lossless compression keeps every value intact, which is why the question ZipServ poses — how to cut weight traffic without touching a single bit of the model — has become practically relevant only as bandwidth, rather than compute, became the binding constraint.

1.2 A concrete failure: the decompression pass eats the saving

Consider a latency-sensitive chat assistant serving LLaMA3.1-8B on an L40S, a GDDR6 card whose sustained bandwidth is about 864 GB/s, with a per-token decode budget of roughly 50 ms so that the stream keeps pace with a reading user. At a small decode batch of N = 16 tokens the step is weight-bound: the 15 GB weight tensor must be streamed from DRAM, and at 864 GB/s that movement alone costs on the order of 17 ms, already about a third of the per-token budget before any useful arithmetic. A general-purpose lossless codec such as DietGPU can shrink the stored weights, but its decoder writes a full BF16 matrix back into global memory, and the matrix multiply then reads that matrix again. The roughly 15 GB saved on the compressed load is therefore re-incurred as a decompressed-matrix write followed by a GEMM read, so the bandwidth the codec was meant to save reappears one stage later. The assistant ends up moving as many bytes as before, plus the cost of running the decoder, and its token budget is no easier to meet.

1.3 Baseline pain: variable-length codes fight the GPU

The damage is not only the extra memory pass. Classical entropy coders emit variable-length bitstreams, and on a SIMT machine the threads of a warp must then decode codewords of different lengths, which serializes lane progress and forces a bitstream-parsing step before any value is known. The combination is why decoupled GPU codecs are slow in exactly the place ZipServ cares about: the paper reports ZipServ decompresses about 2.14 times faster than DietGPU, which is another way of saying that the established lossless baseline spends more than twice as long on decode work alone, before the saved bytes can be used. A format that must be parsed sequentially and then written back to memory is the wrong shape for feeding a Tensor Core.

1.4 The obvious fix and why it fails

The obvious fix is to decompress the weights into global memory ahead of the GEMM and then call the highly tuned cuBLAS kernel unchanged. The arithmetic path stays simple and correct, but the design loses the only property that motivated compression in the first place: the decompressed BF16 data travels through DRAM a second time, so the bandwidth saving evaporates exactly as in the failure above. The lesson is that a lossless codec helps inference only if the compressed bytes remain compressed until the moment the compute tile is ready to consume them, which means the reconstruction has to happen inside the GEMM rather than before it.

1.5 The fundamental obstacle

A weight format that can be reconstructed inside a Tensor Core matrix multiply must satisfy three constraints at once. It must be parallel-decodable, so that every thread of a warp computes the position of its own data without parsing a shared bitstream; it must be tile-aligned, so that a unit of compressed data corresponds exactly to a Tensor Core MMA tile; and its reconstruction must be cheap enough — a handful of register operations — to run in the shadow of the memory load it replaces. Variable-length entropy codes violate the first constraint, and decoupled codecs violate the third. The design space therefore reduces to a fixed-length, tile-addressable representation whose decode is branch-free, which is precisely the gap the Tensor-Core-Aware Triple Bitmap Encoding is built to fill.

2. What ZipServ Contributes

With the obstacle established, ZipServ contributes a co-designed format and kernel rather than a standalone codec. The three contributions below correspond to the three constraints of the previous subsection, and the headline numbers follow only once the fused path is in place.

A fixed-length, tile-aligned format

Tensor-Core-Aware Triple Bitmap Encoding (TCA-TBE) stores the common exponent classes of an 8-by-8 tile in three 64-bit bitmaps, with sign and mantissa packed into one byte per element and rare values escaped into a side buffer. Every tile carries the same fixed metadata, so the decoder addresses its data arithmetically rather than by parsing a stream.

A fused decompression-GEMM kernel

ZipGEMM loads the compressed buffers, reconstructs BF16 fragments directly into Tensor Core registers using bit operations and popcount offsets, and multiplies them without ever writing a decompressed matrix to global memory. The reconstruction is branch-free, so a warp decodes its lanes in lockstep.

Stage-aware integration

Because prefill is compute-bound while decode is memory-bound, ZipServ uses decoupled decompression where compute dominates and the fused ZipGEMM path where memory traffic dominates, so the compression machinery is applied only where it helps rather than slowing the compute-bound stage.

3. Architecture: One Offline Stage, One Fused Online Path

ZipServ separates the work into an offline compression stage and an online execution stage, and the whole design rests on never letting a decompressed matrix exist in global memory between them. Offline, the model weights are analyzed and rewritten into the triple-bitmap representation once; online, the ZipGEMM kernel loads the compressed buffers and reconstructs each fragment in registers at the moment the Tensor Core consumes it.

Figure 6 (from paper): The system splits into offline compression, stage-aware execution, and the fused ZipGEMM kernel. The offline pass builds the bitmap buffers once; the online path selects decoupled decompression for the compute-bound prefill stage and the fused path for the memory-bound decode stage.

3.1 The tile-cost equation

The quantity ZipServ tries to reduce is the time to process one weight tile, which decomposes into the cost of loading the compressed buffers, the cost of reconstructing the BF16 fragment, and the cost of the Tensor Core multiply. Writing it out makes clear what the design removes: there is no term for storing a decompressed matrix.

$$T_{\text{ZipGEMM}} = T_{\text{load}}(B_{\text{exp}}, S_{\text{mant}}, F_{\text{bf16}}) + T_{\text{reconstruct}}(e, s, m) + T_{\text{mma}}(\text{tile})$$

The load term reads the three exponent bitmaps, the packed sign-mantissa bytes, and the full-BF16 escape buffer; the reconstruct term is the branch-free register arithmetic of the next section; the MMA term is the unchanged Tensor Core multiply. The useful comparison against the dense baseline is therefore not the compressed size alone but whether the load plus the reconstruction together cost less than reading full-width BF16 weights on the target GPU.

Architectural insight: The architecture is a single decision repeated at tile granularity: reconstruct close to use. Everything else — the bitmap layout, the offset tables, the stage-aware split — exists to make that one decision cheap and branch-free on a Tensor Core.

4. Mechanism Deep Dive

ZipServ has three coupled pieces: Tensor-Core-aware encoding, register-level reconstruction, and fused GEMM consumption. The format is useful only because those pieces are designed together.

The design point is locality. Values are reconstructed close to Tensor Core use, avoiding a decompressed BF16 matrix in global memory.

TCA-TBE format

Each 8 by 8 tile uses three 64-bit bitmaps to encode up to seven frequent exponent classes, while uncommon values are stored in a full BF16 buffer. This makes decode control flow regular enough for GPU execution.

Register reconstruction

The kernel reconstructs BF16 values from sign-mantissa bytes and exponent code bits using bit operations and popcount offsets. As a consequence, values are reconstructed close to Tensor Core consumption rather than staged in global memory.

Fused ZipGEMM

The main API selects a tiling configuration based on N and uses fast or safe kernels depending on alignment. When Split-K is used, a reduction kernel combines partial results.

Stage-aware execution

The paper separates compute-bound prefill from memory-bound decode. ZipServ uses decoupled decompression where compute dominates and fused ZipGEMM where memory traffic dominates.

Figure 2 (from paper): BF16 weight exponents cluster into a narrow band. This skew is the empirical premise of the format: a window of seven consecutive exponent values captures most elements, so each can be recorded as a small offset rather than a full eight-bit field.

4.1 TCA-TBE: the encoding, exactly

The format rests on one empirical fact and one design choice. The empirical fact is that BF16 weight exponents cluster into a narrow band (Figure 2). The design choice is to select a window of seven consecutive exponent values and treat every weight whose exponent falls inside that window as high-frequency. Because the seven values are consecutive, an element's exponent can be recorded as a small offset into the window rather than as a full eight-bit field, and decoding becomes an addition rather than a table lookup.

Each 8 by 8 tile holds 64 elements and carries three 64-bit bitmaps. Reading bit p of bitmap1, bitmap2, and bitmap3 together yields a three-bit code in the range 0 to 7 for element p. A code of 1 to 7 marks a high-frequency element and names the offset of its exponent within the window; a code of 0 is an escape, meaning the element's exponent lies outside the window. This is the sense in which the encoding is a triple bitmap: three bit-planes jointly carry one three-bit class index per element, laid out so that a bit position is exactly an element position inside the Tensor-Core tile.

A high-frequency element then stores only its sign bit and seven-bit mantissa, packed into a single byte; its exponent is implied by the code and is never written. An escape element stores its full sixteen-bit BF16 value in a separate buffer. The host-side encoder in csrc/L_API.cu performs exactly this per tile:

// one 8x8 tile; element index pos = 0..63; window = exponents [start_exp+1 .. start_exp+7]
exp = (bf16 >> 7) & 0xFF
if start_exp < exp && exp <= start_exp + 7:      // high-frequency
    code = exp - start_exp                          // 1..7
    bitmap1 |= ( code        & 1) << pos
    bitmap2 |= ((code >> 1) & 1) << pos
    bitmap3 |= ((code >> 2) & 1) << pos
    sign_mantissa[h++] = (sign << 7) | mantissa    // 1 byte; exponent dropped
else:                                               // escape, code = 0
    full_bf16[f++] = bf16                            // 2 bytes, verbatim

The subtle point is that the escape path is represented by the absence of bitmap bits rather than by a fourth bitmap or a variable-length code. That single choice keeps every tile addressable with fixed-size metadata: the three bitmaps are always present at 24 bytes per tile, and only the uncommon values spill into a side buffer, so the decoder can compute where each tile's data lives without parsing a bitstream.

4.2 The decoding, exactly

Because the window is consecutive, the kernel never consults a lookup table. It gathers the three bits at position p into a code and, when the code is non-zero, rebuilds the exponent by adding the code to start_exp; the sign and mantissa come from the next packed byte. The entire reconstruction is a few shifts, a mask, and one addition per element, with no data-dependent branch, so a warp decodes its 32 lanes in lockstep and incurs no control-flow divergence. This is the reconstruction in csrc/L_Kernel.cuh:

// reconstruct element pos, branch-free
code = ((bitmap3 >> pos) & 1) << 2
     | ((bitmap2 >> pos) & 1) << 1
     | ((bitmap1 >> pos) & 1)
exponent_bits = (start_exp + code) << 7           // addition, not a table lookup
bf16 = (sign << 15) | exponent_bits | mantissa     // high-frequency element
// code == 0  ->  take the next value verbatim from full_bf16[]

The only exceptional case is the zero code: when it appears, the thread must advance through the full-value buffer in step with the encoder's offset tables rather than read a sign-mantissa byte. The branch-free fast path is therefore safe precisely because the per-tile offset tables tell each thread block where its packed sign-mantissa bytes and its escape values begin, so reconstruction reduces to the following bit assembly.

$$\text{value} \;=\; (\text{sign} \ll 15)\;\big|\;\big((\texttt{start\_exp} + \text{code}) \ll 7\big)\;\big|\;\text{mantissa}$$

Reading the assembly back to the format: the sign bit returns to the top of the BF16 word, the reconstructed exponent occupies the eight exponent bits, and the seven mantissa bits fill the bottom. The whole sequence is the same handful of integer operations on every lane, which is what makes it cheap enough to hide inside the memory load it accompanies.

4.3 Where the compression ratio comes from

The arithmetic that bounds the whole approach is short. A high-frequency element costs one byte of sign and mantissa plus three bitmap bits, eleven bits in total, against the sixteen bits of a raw BF16 value; an escape element costs nineteen bits, slightly more than raw. If a fraction f of a matrix's elements are high-frequency, the compressed size per element is 11f + 19(1 minus f) bits, so the ratio is:

$$r \;=\; \frac{16}{\,19 - 8f\,}, \qquad f \to 1 \;\Rightarrow\; r \to \frac{16}{11} \approx 1.45\times$$

The ceiling is therefore about 1.45 times, reached only when essentially every exponent falls in the seven-value window, and the format expands data once f drops below one half. This single relation explains both the modest model-size reduction the paper reports and, as the reproduction section shows, why the kernel speedup cannot exceed a similar factor on bandwidth-bound hardware. The three tile granularities the encoder maintains (8 by 8, 16 by 64, and 64 by 64) with their per-level offset tables let a thread block locate where its own 64 by 64 region begins in the packed byte streams, which is what makes the compressed representation addressable at Tensor-Core-tile granularity.

4.4 Interaction among the pieces

ZipServ's mechanism is a format-kernel co-design. The bitmap layout would be only a storage trick without a GEMM path that reconstructs fragments close to Tensor Core use.

The interaction to watch is locality: the design saves bandwidth only when compressed bytes stay compressed until the kernel is ready to consume the BF16 value.

Figure 10 (from paper): Decompression is fused with the GEMM: reconstructed BF16 fragments are consumed inside the matrix multiply rather than written back to global memory, which is the systems hinge that turns the bitmap layout into a bandwidth saving.

The evaluation must be read in two layers: first whether the format compresses, and then whether the fused GEMM path avoids enough memory traffic to beat dense execution. 5.1 Evaluation discipline

The hardware class is part of the claim rather than a deployment footnote. Results on GDDR inference GPUs should not be transferred automatically to HBM datacenter parts without measuring the bandwidth regime, because the size of the saving depends on how memory-bound the GEMM is on the specific device. The reproduction section that follows makes this dependence quantitative across five GPUs.

6.1 Prototype boundary

The implementation is specialized for BF16 and GDDR-oriented GPUs and should not be read as a universal compression layer for arbitrary model formats. HBM datacenter GPUs are a natural boundary: where memory bandwidth is less constraining or where the exponent distribution differs from the assumed skew, the speedup shrinks, a behaviour the reproduction section measures directly.

7. Independent Reproduction on Five GPUs

To test how far the claims travel across hardware, we forked the repository and ran its own kernel benchmark (kernel_benchmark/test_mm) on five GPUs that span the two memory technologies the paper distinguishes: two GDDR cards (L40S, RTX 5090) and three HBM datacenter cards (A100-40GB, H100, H200). Each GPU was compiled for its native architecture and swept over six Llama-2 7B and 13B weight-GEMM shapes and six token counts, with N ranging from 16 to 512, giving thirty-six configurations per GPU. Every configuration compares ZipGEMM against cuBLAS with and without Tensor Cores under a cold-L2 protocol that re-reads the weight from DRAM on every iteration, which is the setting most favorable to compression.

The measurements confirm the paper's central claim along the axis it cares about and qualify it along another. Decompression is numerically faithful on every GPU: ZipGEMM matches cuBLAS Tensor-Core bit-for-bit in twelve to thirty of the thirty-six configurations, and where it differs the gap is the same floating-point reduction-order difference that separates cuBLAS's own Tensor-Core and pedantic paths. The speedup over the deployment-relevant cuBLAS Tensor-Core baseline, however, is governed almost entirely by memory bandwidth, and it orders the five GPUs cleanly by memory technology.

7.1 Why the typical speedup is bounded

The ordering is not a quirk of any one shape; it follows from a roofline argument. For a weight-dominated GEMM with a cold cache, the arithmetic intensity is approximately the token count N, because each weight byte read participates in N multiply-accumulates. When N is small the operation is memory-bound, and the time is set by how many weight bytes must move.

$$\text{AI} \approx N \;\text{FLOP/byte}, \qquad \text{speedup} \;=\; r \cdot \frac{B^{\text{eff}}_{\text{ZipServ}}}{B^{\text{eff}}_{\text{cuBLAS-TC}}} \;\le\; r \;\lesssim\; 1.45\times$$

A lossless codec that shrinks the weight to one over r can therefore run at most r times faster, and only inside the memory-bound region. With r near 1.42 to 1.45 from the analysis above, the structural ceiling is about 1.45 times, never 2.21. The realized speedup is this ceiling scaled by how well ZipGEMM sustains bandwidth relative to cuBLAS Tensor-Core, and the fused decode usually sustains less. On the RTX 5090 at N equal to 16, ZipGEMM moved roughly thirty percent fewer bytes yet sustained only about 250 GB/s against cuBLAS Tensor-Core's 745 GB/s, so the decode pipeline, not the byte count, was the binding constraint. On the HBM cards the memory-bound region itself is narrow because bandwidth is abundant, which is why their speedups collapse toward 0.2 times.

Speedup is highest for tall weight matrices at small N (the most memory-bound case) and decays as N grows toward the compute-bound regime.

7.2 Reconciling with the paper's headline

The paper reports average kernel speedups of 1.31 times on RTX 4090 and 1.36 times on L40S, with a maximum of 2.21 times; this reproduction finds an L40S geomean of 0.87 times with a best configuration of 1.45 times. The two pictures are consistent once the framing is made explicit. The headline 2.21 times is a per-shape maximum on configurations where cuBLAS Tensor-Core happens to tile poorly, whereas a geomean over a broad shape and token sweep sits near parity; the structural ceiling set by a lossless ratio near 1.42 means no typical shape can reach a factor of two. The paper's positive averages were measured on GDDR cards, exactly the regime where this reproduction also finds ZipGEMM most competitive, and the collapse on the HBM cards is the quantitative form of the README's own caution about datacenter GPUs.

Measurement boundary: The compression ratio here comes from the benchmark's synthetic weight generator, whose exponents are deliberately concentrated in the seven-value window, so 1.42 times should be read as roughly best case for the encoding rather than a real-checkpoint figure. The latency and numerical results are valid kernel measurements regardless of that generator.

8. Limitations and Failure Modes

The main limitation is format specificity: the triple-bitmap structure is tied to the BF16 exponent distribution and to Tensor Core tile access, so it is not a drop-in layer for arbitrary numeric formats. The second limitation is integration depth, because a fast kernel benchmark is not the same as a complete serving-stack replacement, and the end-to-end gain depends on how often the compressed GEMM path is on the critical layer.

GPU class dependence

The README states that ZipServ is optimized for GDDR memory GPUs such as the RTX 4090, L40S, RTX 5090, and RTX 6000 Pro, and the five-GPU reproduction shows the benefit collapses toward parity on HBM datacenter parts.

BF16-specific design

The format depends on the BF16 exponent distribution and Tensor Core tile shapes. Other numeric formats would need a separate analysis and most likely a different encoding, because the consecutive-exponent window assumes the BF16 skew.

Prototype scope

The published code is a research prototype of C++/CUDA kernels and benchmarks, so production serving integration is more limited than a full framework patch and leaves request scheduling and KV-cache handling untouched.

8.1 Takeaways

The lessons generalize beyond this particular format. Lossless compression accelerates inference only when decompression is designed together with the compute kernel; separating the two recreates exactly the traffic the codec was meant to remove. Hardware specificity is the second lesson, since the same compressed format can be strong on one GPU memory regime and ordinary on another.

  • Lossless compression can accelerate inference only when decompression is designed with the compute kernel.
  • The main systems point is removing the intermediate decompressed matrix from global memory.
  • The design is best interpreted as hardware-aware BF16 serving, not as a general-purpose codec.

9. Bottom Line

ZipServ's contribution is a lossless format designed around the GEMM execution path rather than a generic codec, and its risk is the same specificity that makes it work: BF16 exponent statistics and GDDR bandwidth pressure are both part of the reason the result holds. The five-GPU reproduction supports the paper where it is careful — bit-exact decompression and a real benefit on bandwidth-limited GDDR cards — and qualifies the headline by locating the structural ceiling near 1.45 times.

Best use case

BF16 inference on memory-bandwidth-limited GDDR GPUs where weight traffic dominates the decode step and exact model outputs are required.

Main risk

Other numeric formats or HBM-heavy server GPUs may not match the assumed exponent distribution and bandwidth regime, so the benefit can shrink to parity or below.
