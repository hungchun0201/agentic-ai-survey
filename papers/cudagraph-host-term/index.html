Does the Latency Mechanism Survive CUDA-Graph Capture?

A closed-form model predicts one decode step by splitting it into a GPU-compute term and a host-overhead term. CUDA graphs are the production feature built to erase host overhead. Enabling graph capture removes a substantial cost, but measurement shows it is not the part the model calls ‘host’ that disappears. The paper reports that discrepancy faithfully and characterizes what graphs actually remove.

IISWC 2026 (under review) Workload Characterization CUDA Graph · vLLM Pre-registered kill-switch (fired)

A falsifiable test of the host-dispatch term in vLLM decode — Llama-3.1-8B on A100-40GB / H100 / H200 (+ RTX 5090 check)

1. Why This Test, Why Now

This section walks a reader who has never seen the model into the reason the test is both necessary and decisive, before any of the paper's own findings appear. The argument is built from the deployment reality of 2025-era serving, one concrete failure of the untested assumption, the size of the gap left open, the obvious fix that does not settle the question, and the structural reason a simple subtraction is the right instrument.

1.1 Why now: graphs became the production default while the model stayed in eager mode

Until late 2023, the reference vLLM decode loop issued every kernel from Python on every step, so a host-overhead term was directly observable and a model that named it could be validated in that mode. By 2025, CUDA-Graph capture is enabled by default in vLLM v1 and eager execution is the opt-out: a production decode step replays a captured graph with a single launch rather than 394 separate Python launches. The mechanism model this paper tests, however, was constructed and validated entirely in eager mode, the mode operators are abandoning. Every prior review round of the model raised the same deferred concern, namely whether any of its host decomposition survives once the host-erasing feature is switched on. The shift from eager-by-default to graph-by-default is the change in the world that makes the test necessary today rather than two years ago.

1.2 A concrete failure: the model misleads a production planner

Consider a capacity planner for a code-assistant endpoint who must keep each decode step near a 10 ms budget while serving Llama-3.1-8B at batch 16 and context 512 on an H200, and who turns to the mechanism model to estimate how much enabling graph capture will save. The model decomposes the predicted 9.6 ms step into a GPU-compute branch, a kernel-dispatch floor, and a scheduler residual that grows with batch. Because the GPU-compute branch already exceeds the dispatch floor in this cell, the model's combiner takes the maximum and the dispatch floor contributes nothing, so the model tells the planner that graph capture recovers only the small batch-growing residual, on the order of 4.3 ms at batch 16 falling to 1.3 ms at batch 1. The measurement contradicts this directly: graph capture removes about 4.4 ms at batch 16 and a nearly identical 4.2 ms at batch 1, a flat profile rather than a rising one. The planner who trusted the model would budget graph savings that scale with batch and would be wrong about both the level and the shape on the very first cell of the deployment.

1.3 The baseline pain: a 22% over-prediction in the configuration the model was never fit on

Before introducing any improvement, the status quo error is worth stating plainly. On the common five-by-three decode grid, the unmodified predictor over-predicts the eager step by 21.9% pooled (15.0% on H100, 19.0% on H200, 31.8% on A100-40GB), and the signed error is positive, meaning the model consistently expects the step to be slower than it measures. This is the controlled, never-fit-on configuration, so the error reflects genuine model bias in this regime rather than noise. A 22% over-prediction is large enough that a capacity planner sizing a fleet from the model would provision substantially more decode headroom than the hardware actually needs.

1.4 The strawman: just re-fit the host term in graph mode

An obvious response is to re-fit the host constants directly against graph-mode measurements and declare the model repaired. This does not settle the scientific question the paper poses. Re-fitting a free parameter to the target data can absorb almost any discrepancy, including one whose true source is a misattributed mechanism, so a good post-hoc fit would not distinguish a correct decomposition from a wrong one that happens to have enough free parameters. The question is not whether some curve can be made to pass through the graph-mode points; it is whether the host term the model already defined corresponds to the cost graph capture actually removes. That is a claim about mechanism, not about goodness of fit, and only a prediction made before measurement can test it.

1.5 The fundamental obstacle: a wall-clock subtraction cannot read GPU counters

The structural difficulty is that the quantity of interest, the exposed host cost on the critical path, cannot be read off a single hardware counter. The decode step interleaves GPU execution with CPU dispatch, and the host work for the next step partly hides behind the current step's GPU work; what reaches wall-clock is only the portion that did not fit in that shadow. A profiler can attribute device time to kernels, but the non-overlapped host span is precisely the residual that no per-kernel counter captures. The paper's instrument therefore subtracts two wall-clock measurements, eager minus graph at matched batch and context, relying on the fact that graph replay provably runs the identical 394 kernels so the GPU-compute time cancels. This makes the difference a clean host quantity in expectation, but it is an inference about mechanism from wall-clock evidence, not a counter reading, and the paper is careful to claim only what that evidence supports.

1.6 Position vs prior work

The page sits among four concrete prior works. The Williams roofline model predicts device throughput from compute and bandwidth ceilings but stops at GPU compute and leaves the host path unmodeled. PagedAttention, the kernel-and-memory foundation of vLLM, drives the per-step kernel schedule this paper times but offers no closed-form latency prediction for it. NVIDIA's CUDA Graphs integration in PyTorch removes per-step launch overhead and is the production mechanism under test here, yet its published characterizations report device-timeline launch savings without connecting them to a serving-latency model. Serving-throughput simulators in the Vidur and LLMServingSim line model the scheduler queue but treat the per-step kernel cost as an opaque calibrated constant rather than decomposing it into GPU and host terms. The mechanism model under test is the first to carry an explicit, named host-dispatch term into a closed-form decode predictor, and it is exactly that named term every prior review asked to see tested under graph capture. What all four left on the table is a falsifiable confrontation between a model's host term and the production feature designed to delete host overhead, which is what this paper supplies.

2. The Whole Story in One Minute

With the motivation established, the result can be summarized in one pass. When a language model writes one token, the GPU runs a long fixed list of small programs called kernels, about 394 of them per step for Llama-3.1-8B, and two costs accumulate: the GPU actually computing, and the host, namely the CPU and Python runtime, dispatching and bookkeeping each step. Because the prior mechanism model predicts the total by adding a GPU-compute term and a host term, and because CUDA-Graph capture records the whole kernel list once and replays it with a single launch that removes almost all of the per-step host work, the model implies that enabling graphs should subtract exactly its host term. This paper runs that adversarial test on three datacenter GPUs, and the consequence is the partly-negative result summarized below.

The four cards below separate the result into the confirmed bandwidth trend, the falsified host-term attribution, the predictor calibration error, and the pre-registered reporting discipline.

1 · Graphs help, and the trend is right

Graph capture reduces the step by 26.7% on A100-40GB, 34.2% on H100, and 46.0% on H200. The fraction it removes increases monotonically with memory bandwidth, which is the qualitative gradient the model predicts: the same host cost is a larger slice of a smaller GPU floor on faster GPUs. That part is confirmed.

2 · But it is the wrong host term

The model attributed the recoverable cost to a batch-growing scheduler residual. The measured gap behaves in the opposite way: it is roughly batch-constant at a few milliseconds, and it anti-correlates with the predicted residual (regression slope negative, R² = 0.17). In compute-bound long-context cells the gap collapses to zero, and slightly below.

3 · The predictor over-predicts here

On the common grid the model over-predicts the eager step by about 22% and the graph step by about 33%. The measured eager step is nearly flat in batch (about 9.5 to 10 ms on Hopper for N from 1 to 16), while the predictor's terms grow steeply. The host term therefore requires recalibration for this regime; the gap is a real effect the decomposition omits.

4 · The discipline is the point

Before running, we recorded a pass/fail kill-switch: if graphs do not recover the modeled host residual, report a bounded negative characterization rather than a confident wrong story. The kill-switch fired. We name the removed cost a non-overlapped host term on mechanistic grounds; we did not isolate GPU work with hardware counters, and we do not over-claim.

Why this is good science, not a failure: A latency model's central selling point was an explicit host-overhead term. The cleanest way to stress-test it is to remove the host overhead and observe whether the predicted amount disappears. It mostly did not, and the experiment now establishes precisely what graphs remove (a batch-constant non-overlapped host cost), where the model is wrong (it omits that cost and over-predicts the level), and where it is right (the bandwidth gradient). A characterization of an effect the model does not represent is itself the contribution.

3. What Happens in One Decode Step

No background is assumed here. Four ideas are sufficient to follow the rest of the page: what a decode step is, what host overhead means, what a latency mechanism model is, and what CUDA-Graph capture does. Each is developed in plain language before any vLLM-specific name appears.

3.1 A decode step is one token and about 394 small programs

To write the next token, the model runs its full forward pass once. On the GPU that means, for each of Llama-3.1-8B's 32 layers, four matrix multiplications for the projections, one attention computation, and a handful of small elementwise operations, plus a final output projection and a sampler. Each of these is a kernel, a small program the GPU runs to completion before the next one begins. Summed across the network, one decode step launches about 394 kernels, and the model repeats this tens of thousands of times to write a paragraph.

3.2 Two clocks run at once: the GPU and the host

While the GPU executes kernels, a CPU-side host, namely the Python scheduler and the runtime, is busy too: deciding which requests to serve, allocating memory, and issuing the launch command for each of those 394 kernels. A step's wall-clock time is therefore a race between two costs, the GPU-compute time of running the kernels and the host time of deciding what to run and instructing the GPU to run it. When things go well, the host work for the next step hides in the shadow of the current step's GPU work; when they do not, that host work spills onto the critical path and the GPU waits for Python. Whatever host work does not fit in the shadow becomes exposed wall-clock time, and that exposed host cost is exactly what CUDA graphs attack.

3.3 A mechanism model is a roofline calculator, not a fitted curve

The model under test is a closed-form predictor built earlier. It writes one step as a single formula, shown below, and the point of the formula is that the GPU efficiencies are architecture-derived rather than fitted to served latency, so the model should generalize.

(1) $$T_{\text{step}} = \max\!\big(T_{\text{blocks}},\; N_{\text{kern}}\,t_{\text{launch}}\big) + \alpha(N)\,S(N) + T_{\text{samp}}$$

In words, the model takes the larger of the GPU-compute time $T_{\text{blocks}}$, a roofline sum over every kernel, and the dispatch floor $N_{\text{kern}}\,t_{\text{launch}}$, the cost of issuing 394 launches, then adds an exposed scheduler residual $\alpha(N)\,S(N)$, the host bookkeeping that did not fit in the shadow, and a small sampling term $T_{\text{samp}}$. The paper does not retrain anything; it asks whether the existing host decomposition is correct.

3.4 CUDA-Graph capture: record once, replay with one launch

In eager mode, Python issues all 394 launches on every step and the scheduler runs on the critical path. CUDA-Graph capture records the fixed kernel dependency graph once and replays it with a single launch, removing the per-step launch cost and shrinking the host span to bookkeeping the runtime can pipeline a step ahead. The GPU still runs the same 394 kernels, because graph replay removes launch overhead, not compute, so $T_{\text{blocks}}$ is identical in both modes by construction.

Why this makes a clean experiment: Because the GPU work is provably unchanged between eager and graph mode, subtracting eager minus graph at the same batch and context cancels the GPU compute and leaves a pure host amount. The model claims to predict that amount, so a simple subtraction becomes a falsifiable probe of the model's host term, with the caveat revisited below that this is a wall-clock subtraction rather than a hardware-counter isolation.

4. The Core Idea: A Clean Eager−Graph Subtraction

The method isolates one decode step with a version-robust subtraction over the high-level generation API, so it survives internal engine refactors. The pre-registered hypotheses, the per-step isolation formula, and the two honesty controls are developed in turn below, so the reader understands what is predicted before any measurement is shown.

4.1 The pre-registered hypotheses

Four hypotheses and one kill-switch were recorded before the measurements were taken, which is what makes the eventual negative result a finding rather than a surprise. The model makes a sharp prediction in advance: across every cell of the decode grid the GPU-compute branch already exceeds the dispatch floor, so the maximum in Equation (1) selects $T_{\text{blocks}}$ and the dispatch term is shadow-hidden, contributing zero to the prediction. The only modeled cost left for graphs to recover is therefore the scheduler residual $S(N)$, which is small at batch 1 and grows with batch.

The pre-registered hypotheses and kill-switch. H1 holds that dispatch is invisible because it is shadow-hidden; H2 holds that the measured gap tracks the batch-growing scheduler residual $S(N)$; H3 holds that the relative benefit rises with HBM bandwidth across SKUs; and H4 holds that the predictor agrees with the measured step. The kill-switch states that if the removed cost is not the modeled residual, the paper reports a bounded negative characterization rather than re-fitting its way to a positive claim.

4.2 Isolating one decode step

The per-step cost is recovered by a subtraction that cancels the fixed prefill and startup overhead, so the result is the decode work alone. The isolation formula is shown below.

(2) $$\text{per\_decode\_ms}(N,\text{ctx}) = \frac{\text{wall}(g) - \text{wall}(1)}{g - 1}$$

A batch of $N$ prompts of length ctx generates $g$ tokens, with exactly $g$ forced by the ignore-eos flag. The one-token wall captures prefill plus fixed overhead; the difference isolates the $g-1$ decode steps; dividing yields the per-step cost. The measurement runs in two separate processes, with eager execution on and off, over a grid of batch size $N \in \{1,2,4,8,16,32\}$ and context $\{512, 2048, 8192\}$, taking 15 timed repetitions per cell on Llama-3.1-8B. Because the subtraction is defined over the high-level $\texttt{LLM.generate}$ entry point rather than an internal step function, it remains valid across vLLM engine refactors.

4.3 Two honesty controls

Two controls protect the result from quietly favorable choices. The predictor's GPU and dispatch terms are left untouched, and only the one empirical host floor is set to a disclosed engine-context value, $S(1) = 1.30$ ms, not the shipped generation-protocol floor of 14 to 24 ms; the gap and the cross-SKU ordering are shown to be insensitive to its exact value because the GPU branch dominates. A 95% confidence interval is bootstrapped on every per-SKU gap, with 5000 resamples at a fixed seed, so a near-zero gap, the kill-switch condition, is interval-bounded rather than asserted. These controls matter because a near-zero or anti-correlated gap is the outcome the paper has to be able to detect honestly, and an undisclosed floor or an un-bracketed point estimate would let a favorable reading slip through unchecked.

5.1 The bandwidth gradient (H1, H3): the right trend

The relative graph benefit rises monotonically with HBM bandwidth, from 26.7% on A100-40GB through 34.2% on H100 to 46.0% on H200, confirming H3 on the three measured SKUs. The mechanism is as predicted: the absolute host cost removed is largely bandwidth-independent at a few milliseconds on every SKU, so it forms a larger fraction of the smaller, faster GPU floor on bandwidth-rich SKUs. H1 also holds in its narrow sense, because in every cell the GPU branch exceeds the dispatch floor, which means the model treats dispatch as shadow-hidden and the removed cost is therefore not the dispatch floor.

5.2 But the gap is the wrong shape (H2): falsified

The model attributed the recoverable cost to the batch-growing scheduler residual $S(N)$, and the measurement falsifies that attribution. Regressing the measured per-cell gap on the predicted $S(N)$ gives a negative slope on both grids; on the common grid the slope is −0.43 with intercept 4.82 ms, R² = 0.17, and r = −0.41. The recovered amount is roughly batch-constant, for example H200 holds 4.2 to 4.7 ms from batch 1 to batch 16 while $S(N)$ would climb from 1.3 to 4.3 ms, and it collapses toward zero, and slightly below, in the compute-bound long-context cells, reaching −0.6 ms for H200 at batch 32 and context 8192 and +0.8 ms for A100-40GB at batch 16 and context 8192. Graphs therefore remove a host cost whose batch-shape is the opposite of the modeled residual.

5.3 And the level is off (H4): the model over-predicts both modes

The predictor does not predict this controlled decode step accurately, and it over-predicts in eager and in graph mode alike. Eager-mode MAPE against the full prediction is 21.9% pooled on the common grid (15.0% on H100, 19.0% on H200, 31.8% on A100-40GB), with a signed error of +13.1%. Graph-mode MAPE against the GPU-only prediction is 33.2%, because removing the host term drops the measurement about 33% below the GPU-only floor, which means the closed-form GPU branch itself over-predicts this regime at this vLLM version. Since both modes are over-predicted by a similar margin, the eager-minus-graph gap remains a robust real effect even though the absolute level needs recalibration.

The kill-switch fired. The pre-registration stated that if graph mode does not recover the modeled host residual, the paper reports a negative characterization: the host term is not a clean dispatch-plus-scheduler split, and the paper quantifies what graphs actually remove. That is the outcome. Graphs remove 26.7 to 46.0% of the step, but its shape is neither the dispatch floor, which H1 treats as shadow-hidden, nor the modeled residual $S(N)$, which H2 falsifies as anti-correlated. The removed cost is a non-overlapped per-step host cost the model's combiner omits, named on mechanistic and batch- and bandwidth-shape grounds rather than on a hardware-counter isolation of GPU work.

5.4 Blackwell smoke check (test-only)

An RTX 5090 run, which is not a predictor SKU and is reported only to validate the benchmark and bound the magnitude, shows the same direction: graph capture reduces the step by 0.70 to 1.07 ms, between 6.4 and 9.0%, and the gap grows with batch, from +0.81 ms at batch 1 to +1.07 ms at batch 4. No predictor-accuracy claim is drawn from Blackwell, because it lies outside the predictor's SKU table; the run is a sanity check that graph capture removes a modest, batch-scaling host amount in the predicted direction.

6. Why a Partly-Negative Result Is Worth Reading

The value of the result divides cleanly by audience. For systems researchers it is a measured counterexample to a common attribution; for model builders it is a precise statement of where a roofline mechanism model is trustworthy and where it requires recalibration.

For systems researchers

In steady-state LLM decode, CUDA graphs do not recover a kernel-dispatch floor, which is already hidden in the GPU shadow, and they do not recover a batch-growing scheduler residual. They recover a roughly batch-constant, non-overlapped per-step host cost that disappears in compute-bound cells. A latency model that attributes graph savings to dispatch or to a scheduler curve has a measured counterexample here.

For model builders

The bandwidth gradient is real and predictable, because graph benefit scales with HBM bandwidth, so the same engineering yields more on faster GPUs. The absolute decode-step level from a roofline mechanism model, however, needs regime recalibration: a 22% over-prediction in this controlled, never-fit-on configuration is the honest accuracy a builder should expect before tuning.

7. Limitations — Read Before Citing

The claims are deliberately bounded, and the boundaries are stated here so that no reader infers more than the evidence supports. Each item names a specific way the result could be over-read and the precise scope that remains valid.

  • This is a wall-clock subtraction, not a GPU-counter isolation. The removed cost is named a non-overlapped host term on mechanistic and shape grounds. The paper does not prove the GPU work cancels exactly; it tests the term's batch- and bandwidth-shape for consistency rather than measuring it with hardware counters.
  • The host floor is a disclosed calibration. The paper uses an engine-context $S(1) = 1.30$ ms rather than the shipped 14 to 24 ms generation-protocol floor. The gap and the cross-SKU ordering are insensitive to this choice, but the absolute MAPE depends on it.
  • The predictor over-predicts this regime in both modes, by about 22% in eager and about 33% in graph. H4, predictor agreement, is a negative result. The closed-form GPU branch itself over-predicts at this vLLM version, so absolute latency needs recalibration.
  • One model, three SKUs, single GPU. The study covers Llama-3.1-8B only; the L40S campaign was still queued at submission; and the batch-32 A100 row was dropped to fit the queue, so all cross-SKU claims use the common five-by-three grid.
  • Blackwell is test-only. The RTX 5090 is absent from the predictor's SKU table; its numbers bound magnitude and validate the benchmark, nothing more.
  • Prefill cancels in expectation, not per token. The eager-minus-graph subtraction assumes prefill and GPU compute cancel; matched prompts make this hold in distribution rather than identically.
